## Timers: one slow firing no longer stops the others

- NocoReach's timers share one schedule executor that runs one firing at a time, and each source awaits its whole read inside its firing: GitHub trends' first read of a project slept about 6.5 seconds between some 70 searches, and Google sync, GitHub backfill, competitor research or AI questions can take minutes to hours. Meanwhile the task, sync and every other timer stood still, and shutdown waited for the firing to end. A firing still running after 60 seconds, or when the server shuts down, is now left to finish on its own: nothing is cancelled, so each source keeps its retries, spending and status; the other timers run again, the slow timer's next firings are skipped until it ends, and the log says which timer overran and how it ended, and again every 10 minutes while it still runs. Shutdown waits at most 15 seconds more for such work.
- A timer firing still running at shutdown after those 15 seconds sends and writes nothing more, so the network closing under it is not recorded as a failure and nothing is sent whose result could not be kept: a Google sync job stays running with its attempts and resumes on the next start, a day of GitHub trends is not marked as read, an article that firing was publishing is not marked failed, and no DataForSEO run is opened for a request that will not be sent (one whose request was already out stays running, as after a killed process). Work a firing started and left running after it ended is not covered, as before. Google sync and GitHub trends also stop their reads before the network closes.
- GitHub trends no longer waits between searches for a demo or simulated project, which is answered in process: a demo's first read of two projects took about 15 minutes of pauses and now takes moments. Each GitHub request keeps its 20-second deadline, and a request that gets no answer is reported with the run's other errors.
