## Server: task scans, task lists and the Google data check no longer hold every request

- The periodic task checks (Article publishing every minute, release verification every five minutes, effect observation every hour and after a start, and the one-time repairs at start) read every task 100 at a time with an offset, so the database read and sorted all tasks again, with their content, for each 100, and no other request was answered until the check finished. They now read each 100 after the last task read, answering other requests between reads, and visit the same tasks in the same order. A task added during a check is no longer read twice and none is skipped. Measured locally on copies of the demo data with 10,000 tasks (medians): each check took about 18 seconds and held every request that long, and the first task tick after a start 53 seconds; a check now takes 1.6 to 1.8 seconds and the first tick 5 seconds, and a request arriving meanwhile waits at most 0.05 to 0.07 seconds, or 0.4 seconds during effect observation, whose work on each task read is still done in one go. With 2,000 tasks a check held requests for 0.7 to 1 second; now for 0.04 to 0.1 seconds.
- A project's task list (Tasks, the Tasks badge, and snoozed tasks coming back, checked every minute) and the tasks in the Agent's data summary read the project's task ids once in their order, then the tasks by id, 200 at a time, answering other requests between reads. The lists are the same as before, element for element. With 5,000 tasks in each of two projects, the task list took 4.3 seconds on the server and the Tasks badge 4.4, holding every request that long, and snoozed tasks held them 9.3 seconds every minute; now 0.8, 0.7 and 1.2 seconds, with other requests answered between reads.
- Data sources › Website source and Results read a project's tasks by id the same way.
- On every data view request and sync tick, NocoReach checks whether a project's synced Google reports changed since its snapshots were built, up to about 17 times a minute for an active project even while nobody uses the app. To find the latest write, SQLite read through every stored daily report's data while every other request waited: measured locally, about 17 ms with 510 reports of 68 KB, 92 ms with 2,430 and 175 ms with 4,860. A new index answers it in 2 to 4 ms, however large the reports are. The check's result is unchanged, so snapshots kept before the upgrade are still restored instead of rebuilt.
