# NocoReach Development Constraints

This document covers application adaptations to the template and business boundaries prone to regressions. Read the relevant sections when changing those features. Follow the [application development Skill](../.agents/skills/nocobase-app-development/SKILL.md) and its references for general development; explicit application adaptations below take precedence over template examples.

See the [changelog](../CHANGELOG.md) and [port plan](PORT-PLAN.md) for historical context. Legacy Agent and AI configuration, deployment steps, and outstanding items in the port plan reflect their time, not current implementation requirements. Dependency versions come from `package.json` and the lockfile.

## Frontend

Before changing `client/`, read the [frontend workflow](../.agents/skills/nocobase-app-development/references/frontend/ui-workflow.md) for task-specific component, styling, interaction, and validation guidance. Preserve the application differences below.

### Business pages and copy

- Ported business pages and components live in `client/pages/` and `client/components/`. Requests use the `nocobaseClient.action()` contract in `client/lib/nocoreach-api.ts`; toasts use `client/lib/toast.ts`.
- Business copy uses stable, module-scoped English semantic keys (`common.save`, `playbooks.communityReplyInstruction`, `dataHealth.retryScheduled`). Use lower camelCase segments, reuse only the same meaning/context, and keep keys stable when wording changes. Do not use Chinese keys, whole sentences, hashes, or numbered identifiers. Both translations live in `shared/i18n/en.json` and `zh.json`, registered in the application client/server locales. Preserve translation values, numeric `{0}` interpolation, and intentionally empty measure words. Business pages use `$t()` / `$tj()` from `client/i18n`; deferred messages still follow the application runtime's resolved locale.
- `shared/i18n/legacy-keys.json` is a compatibility manifest for pre-migration system text, not the active dictionary. `$t()` does not resolve Chinese aliases. Only `$legacyText()` / `$legacyJsx()` at historical API/snapshot boundaries may read them; `$legacyFragment()` reads whole system-owned short fragments such as change chips, whose templates are too short for sentence recognition. Keep custom/edited playbooks, user names, queries, notes, and interpolation values literal. Dynamic keyword groups retain their persisted Chinese identities and map explicitly to semantic display keys. Glossary lookups accept original server metric labels and translated display labels; these lookup identities are not translation keys.
- This translation migration does not change database fields, task status values, URL semantics or persisted message formats. Do not introduce data migrations or serialized message markers for i18n. Keep server error messages, codes and control-flow predicates unchanged; use response metadata and presentation mappings to translate existing dynamic system text.
- Server-owned copy is emitted with `systemMessageText(semanticKey, params)`. The Chinese default preserves existing stored/display text and older clients. Text stored for an Agent, such as the goal label of a task brief, uses the request locale from `ctx.getCurrentLocale()` so it matches the client-built brief. Data-health `*Text.key` metadata now carries semantic keys while the legacy fields retain their original Chinese values. API errors preserve status, reason and raw message, and add semantic metadata when recognized; the request adapter re-renders that key when language changes. Historical rendered text, built-in playbook snapshots, audit/analysis labels, and old errors are read through the explicit compatibility manifest/pattern reader. Do not rewrite executed migrations or stored user data for key renames.
- Business navigation keeps its existing `nocoreach.nav.*` keys in `client/locales/`; shell and administration copy retains application locales and official namespace overrides. Upstream plugin keys are outside this migration. Run semantic locale coverage and affected bilingual component/server tests when changing copy; coverage rejects Chinese keys and checks both resources, legacy aliases and interpolation parity.
- Internal imports use `package.json#imports` mappings such as `#components/*`. Directory entry points explicitly target `index`; do not add Vite aliases or TypeScript paths.

Markdown links to same-origin task details (`/actions/:id`) within the runtime application base path use React Router navigation, preserving query/hash parameters and existing draft blockers. All other links retain browser navigation. Keep this behavior in the shared Markdown link component so online and Runner conversations follow the same policy. Project-scoped navigation badges must reset only their own data: never key the provider wrapping the shell by project ID, which would destroy the header and active conversation during cross-project task navigation.

### Routes, identity, and shell

- Business routes are declared in `client/nocoreach-routes.ts` and guarded by membership and project checks in `client/pages/nocoreach-page.tsx`. Business pages use explicit framework page grants; official Agents pages retain plugin grants. APIs independently enforce the business action and project grants documented in [Access](ACCESS-DEVELOPMENT.md).
- A page's tabs and the overlays opened over them are plain child routes (`authz: 'skip'`, no `gated()`): the parent page already passed the gates, and a second gate would wrap the tab in another content container. Because the gate is what follows the language, each tab and overlay component calls `useNocoReachLocale()` itself; components rendered through an `Outlet` do not re-render with the page.
- All pages use `defineAppRoutes()` and the single `AppLayout`. The retired `/settings` UI, administration routes, and dedicated source are removed; unmatched URLs follow the normal home fallback. Keep backend plugin services and stored authorization independent of UI availability. Do not restore `defineSettingsRoutes()`, `defineDevRoutes()`, or a second administration shell.
- NocoReach identity and request caches belong in the authenticated subtree of `client/routing/app-router.tsx`, using official session boundaries and authorization revisions. Do not move them to the application provider layer. Failed identity reads or missing roles grant no access. Isolate persisted reports by user/session/revision. Requests must not update unmounted component state or refill a disposed authentication/authorization cache. Route changes may let pending reports complete into the same active session cache; explicit invalidation must fence older responses from refilling it.
- `SessionPreparation` sits inside `RequiredAuthentication` and outside `MeProvider`, `WorkspaceCacheProvider`, draft guards and navigation badges. Wait for the authenticated realtime handshake and its synchronous permission invalidation before mounting these consumers. Keep the ten-second failure screen, retry and sign-out path; guest routes remain independent of realtime. Later reconnects and permission changes must still invalidate and unmount protected content.
- Preserve sign-out error checks and notifications, permission snapshot clearing on account changes, and page rechecks triggered by authorization revisions. Hide protected content while checks are pending or have failed.
- Task drafts share the authenticated session boundary. Keep their navigation guard beside the authenticated Outlet so guest/optional history navigation cannot silently destroy drafts after leaving a task page. Navigation confirmation acknowledges the current dirty entries without clearing them; unchanged acknowledged drafts must not prompt again on each menu click. New edits require confirmation again, and browser unload protection remains active until drafts are saved or discarded. Retained stage drafts belong to their original artifact; show older drafts for comparison instead of rebinding them to a newer artifact/revision. Keep task mutations mounted until they settle. The brand link targets `/home` directly so the root redirect cannot ask draft guards a second time and leave an empty page when cancelled.
- Layouts render breadcrumbs; pages only declare their trails. NocoReach departs from the template's "trail on every page" (guideline L6, `page.md` §7) in `client/components/breadcrumbs.tsx`: a top-level page's trail is only its own title, which its `PageHeader` repeats right below, so the header hides it until the page's first `h1` scrolls out from under the header (`AppLayout` passes its content scroller), then fades it in rising 6px (fade only with reduced motion). A page below another one — a covering child page, a record's own page — always shows its full trail, and every such page declares one with `usePageBreadcrumb` whose parent level carries the parent's search; it has no `BackButton`, so a new child page must declare its trail rather than rely on a one-level route trail, which would be hidden like a top-level page's. Navigation groups stay out of trails: the sidebar shows them and they lead nowhere. Below `md` the header is compact: no trail, the compact brand on top-level pages and `BreadcrumbParentLink` ("‹ Keywords") on pages below another one. The project switcher lives in `client/layouts/app-layout.tsx`. Demo status replaces the existing sidebar-footer shield in place, with localized hover/focus details; never add a separate row or page-wide banner. App uses the desktop collapse preference `nocobase:sidebar:collapsed`; mobile menu state remains local. Preserve permission filtering, group expansion state, collapsed tooltips/popovers, and keyboard interaction.

- The sidebar template version is compiled from this application's `package.json` → `nocobase.defaultTemplateVersion` by `vite.config.ts`. Public `app.version` describes application identity, not template ancestry, and embedded Studio metadata must not override this baseline. Rebuild after a template source upgrade; missing or invalid metadata displays the localized unknown state.

- `AppLayout` passes `sections={false}` to the template's `NavigationMenu`, keeping top-level groups collapsible instead of always-open sections, and shows the Insights, Opportunities and Tasks pending counts through its `badges` prop, keyed by route name (`usePendingNavigationBadges`, fed by `client/components/app-shell/nav-badges.tsx`). The counts are orange (`--attention`) via `client/theme/presentation.css`. Customize the permission-filtered tree in `client/lib/navigation-transform.ts`, not in the menu component.

- NocoReach retains its header inbox shortcut and unread title badge as application-owned UI; the upstream template no longer supplies that entry. Keep its notification permission and session checks.

### Themes and components

- Use existing shadcn/ui components and semantic theme tokens. Add missing primitives through the CLI rather than rewriting generated components. Page overlays use route components; read the [overlay reference](../.agents/skills/nocobase-app-development/references/frontend/references/overlay.md) first.
- `client/styles.css` follows the template and owns the shared interaction, focus, navigation, table, overlay, alert and toast treatment. `client/theme/presentation.css` holds only NocoReach's additions: legacy `.nr-page` tables (the same header as official tables, via `--hover`) and the orange navigation counts. For semantic status labels use `StatusBadge`; `size='sm'` is the small badge beside a title or on a dense card. App retains `app-brand-surface`. Preserve NocoReach branding, semantic Tag colors, both densities, and browser preferences; do not restyle one page independently.
- Calculate the wide task table minimum width from spacing units needed by fixed columns and the title column. Reserve enough status width for both languages in compact density. At narrower container widths, hide secondary columns; on phones, show the number and status above the fully wrapping title while retaining row actions. Mobile headers retain compact branding (replaced by the parent link on pages below another one), project icons, and smaller button gaps. Show breadcrumbs at md and above; retain full project names in the switcher menu and accessible text.

Follow the application Skill references for [routes](../.agents/skills/nocobase-app-development/references/server-routes.md), [HTTP contracts](../.agents/skills/nocobase-app-development/references/http-api.md), [services](../.agents/skills/nocobase-app-development/references/services-and-jobs.md), and [data access](../.agents/skills/nocobase-app-development/references/database-and-data.md). ### Compatibility layer and authorization

- `server/nocoreach/*.ts` contains ported classic services, retaining dense formatting and `// @ts-nocheck`. Put NocoBase 3 adaptations in `server/nocoreach/legacy/` and business behavior in services. Do not rewrite the entire compatibility layer as incidental cleanup.
- The compatibility layer rebuilds repositories, filters, transactions, resource actions, timers, and other classic interfaces. Classic advisory locks use keyed in-process locks. Store settings in `nrVariables` and seal secrets. Users come from NocoBase 3 accounts; transactional reads use the caller's connection.
- `server/providers/nocoreach.ts` assembles the layer and manages timers. `server/routes/nocoreach.ts` dispatches `/api/nocoreach/<resource>/<action>`. Each action checks current framework permission-set assignments through `server/access/service.ts` and `server/nocoreach/policy.ts`. The retained `nr-members` snapshot is a migration/rollback artifact, never a runtime role source. System administrators retain business access; scoped keys still constrain them. Page or collection grants do not replace business authorization. See [Access](ACCESS-DEVELOPMENT.md) and the Chinese [cutover procedure](ACCESS-CUTOVER.md).
- Notifications use the official Notification plugin and its configured in-app channel; inbox adaptation lives in `legacy/notifications.ts`. Daily analysis is the Scheduler target `nocoreach.daily-analysis`, with runs available through the official Scheduler API/CLI. `pm.get('workflow')` and `workflows` are compatibility names in `legacy/schedule.ts`; official Workflow was removed and must not be reintroduced.
- Google OAuth callbacks require the current signed-in account to match the state initiator. Re-read enabled account status and current NocoReach administrator eligibility before token exchange and after upstream I/O, before saving credentials. Callback attempts consume state once and clear the nonce cookie; signing out or switching accounts requires restarting authorization.
- Server routes own their authorization; page `auth`/`authz` is not server protection. Register background work through providers rather than directory discovery.

### Transactions and synchronization

- Reddit collection persists its fixed query scope, business cutoff and per-term request keys in the existing snapshot before paid I/O. Successful terms are retained during a partial round. Only explicit terminal errors allowed by DataForSEO's [error reference](https://docs.dataforseo.com/v3/appendix/errors/) and [live endpoint guidance](https://dataforseo.com/help-center/best-practices-live-endpoints-in-dataforseo-api), with an explicit zero total cost, retry automatically (at most twice, after 1h and 6h). Transport, malformed and missing-cost failures require reconciliation and remain blocked across cache expiry. Legacy failed snapshots also pause because their billing evidence is missing. Manual checks obey the same limits; pre-request connection/budget refusals can recheck the original key after settings are corrected. Polling and not-due scans only compute scheduling; an executing batch adds one short snapshot transaction before its existing final transaction. No HTTP runs inside either transaction, and no new lock or scheduler is introduced.

- SQLite uses one connection. Do not wait for another database connection inside a business transaction. User reads must use the caller's transaction. Keep model gateway requests outside business transactions.
- Google sync claims work in a short transaction, collects outside transactions, then validates and commits in another short transaction. Never wait for OAuth or Google APIs while holding a transaction. A single-instance `busy` guard protects in-flight batches. Pausing cancels the old batch; its results must not be committed even if immediately resumed. Limit collection to two minutes per batch and retain bounded retries.
- `transactionContext()` in `legacy/database.ts` isolates snapshot caches and construction promises. A transaction must neither wait for snapshot construction outside its scope nor publish uncommitted results to shared caches.
- Do not edit executed migrations or migration history tables to silence checksum errors. Collection files are generated caches; see the [migration reference](../.agents/skills/nocobase-app-development/references/migrations.md). Preserve compiled migration and seed `.manifest.json` generation; do not regenerate manifests for installed dependencies.

### Google report caches

- Default unfiltered web search totals read durable `nrSyncPartitions` overview rows, independently of report-cache expiry. Missing partitions, successful empty arrays (Google returned no record), and numeric zero rows are distinct. Never generate zero rows from omitted dates.
- `nrGoogle/syncNow` retains the existing administrator check. With `{scope:'gscOverview',startDate,endDate,mode:'missing'|'refresh'}` it queues only final, unfiltered web overview work, clamped to the last 16 calendar months and the Los Angeles final cutoff (today minus three days). Reject filters and non-web types. Without `scope`, the existing 7/28/56-day combined sync remains. The response contains `jobs`, `earliest`, and `cutoff`; `history-fill` and `history-refresh` are persisted trigger values in the existing job table. Missing mode subtracts stored days and active/paused/failed job intervals; explicit retry/resume uses `syncControl`. History jobs do not update the combined sync timestamps or schedule and never create query-page partitions.
- `nrDataViews/search` returns summary/coverage by default; `details:true` queries separate query/page aggregates. `coverage.current` and `coverage.previous` expose requested bounds, recorded/no-record/missing days and intervals, plus last-save time; `coverage.earliest` describes the default overview backfill boundary. Both periods need daily records for comparisons. `history.jobs` and `history.scheduleEnabled` are read outside the six-hour report cache. Active pages poll this read endpoint every five seconds; only the initial administrator view or an explicit action submits writes. Detail/breakdown/row comparisons use the summary's `compare` qualification, and live date queries are not clipped to locally stored days.
- Each active poll repeats the report request: authorization and connection checks, snapshot-version reads, preliminary-cache reads where applicable, and the current-resource job read. A cache miss may also read partitions or stored report caches. This is more than one database query; polling itself does not enqueue work or refresh Google. Connection changes invalidate both versioned summary keys and JSON-scoped detail keys only for the affected project.
- `GoogleReportCache` retains GA4's existing `ga4-reports:<project>` snapshots and uses separate GSC/local namespaces. It shares pending reads only within the service instance, clones responses, and bypasses shared reads/writes inside a transaction. Keep authorization and `sync.link()` checks before cache access. Include project, resource, captured authorization identity, actual dates/filters, and `network.mockCacheKey()` in applicable identities; concurrent token refreshes use the same captured scope.
- Upstream historical reports expire after six hours; partial dimensions/sitemap children retry after five minutes. Successful empty reports are cacheable. Reused reports preserve their original `cacheExpiresAt`; synced aggregate versions invalidate when partitions change. Cache aggregated live search tables rather than raw query-page matrices. Limits are 2 MiB per entry, 8 MiB per project/namespace snapshot (32 entries), and 16 MiB per cache instance in memory (128 entries). These are serialized-byte budgets, not process heap limits; oversized results are returned without retention.
- Frontend reports use the authenticated `WorkspaceCache` and its session storage. Search performance, overview, content and sitemap views have a one-minute freshness window; index progress/details use thirty seconds and retain running-job polling. Historical breakdowns/details honor server expiry. Include the selected properties in report keys and invalidate Google reports after resource/authorization changes, and affected local views after website-content mutations. Do not cache mutation responses or use long report TTLs for job state.

### Demo data

- `demoConfigurationToken` owns persisted revisioned schedule, write rules and mock switches. Register capabilities/adapters in `demo-data/adapters.ts`; call `runWrites()` only around a precisely scoped business operation after normal authorization. The classic dispatcher lists the actions a read-only demo may let write, with their capabilities, in `DEMO_WRITES` (`server/routes/nocoreach.ts`); online conversations in demo projects use `nocoreach.onlineConversations` in `server/routes/online-agents.ts`. Rules are empty until an administrator enables them. Never wrap the entire dispatcher or trust a client demo flag. Scoped knowledge writes share `nr_snapshots` with sensitive/global records, so they deliberately have no whole-table capability. Request policy is snapshotted before business transactions to avoid nested SQLite connection deadlocks; updates apply to subsequent requests.
- Configuration read/configure and data read/manage are independent settings grants. The route checks the `page:demo-data` grant like every other page, which roles get with `app.settings` together with both settings grants; inside the page, `useDemoAccess()` decides which sections show, and every server action checks its own grant and enabled environment. Keep demo checks out of the shared navigation. Editors protect revision conflicts, stale identity responses and unsaved navigation through the public navigation guard.
- Daily freshness uses `context.clock.seed/sample(key)` and relative dates; automatic daily reset requires explicit configuration. Mock adapters fail closed when disabled, and proxied demo runs never create official Agent executions. Interrupted running simulations settle as failed after five minutes; queued simulations replay through the same authorized adapter.

- Settings › Demo management (`/demo-data`, `client/pages/demo-management/index.tsx`) drives `@nocobase/app-plugin-demo-mode`'s demo data through `useDemoData()`. Install the published plugin version declared in `package.json`; plugin implementation and build artifacts belong to its upstream repository. The route must bypass `ProjectGate` so a new installation can import its first projects. Administrators hold `settings:demoMode.data` through `app.settings` (`server/access/roles.ts`); the plugin checks that grant before each action. Authorized import, clear and reset handlers run outside the request's async-local write guard; concurrent requests remain guarded. The dataset provides one full-business `clear`, so all lifecycle mutations require `read-only` or `observe` mode in the lifecycle service, including CLI and Scheduler calls. See [DEMO-DATA.md](DEMO-DATA.md).
- The dataset lives in `server/nocoreach/demo-data/`: `steps.ts` writes through the business services (projects, roles and accounts, the real connection and collection flows, tasks, knowledge, opportunities); `content.ts` holds both languages (the Chinese one reuses `demo-content.ts` and `demo-opportunities.ts`); `answers.ts` is what the simulated model says. Demo projects carry `demo: { dataset: 'nocoreach' }` in their project record; `demoProjectsOf()` reads it before the services load, and each process checks the persisted marker before an unknown project can send a request. A lookup failure refuses the request; a cleared demo stays blocked in that process so queued work cannot fall through to live networking.
- A demo project never reaches the network. `OutboundNetwork.useDemoUpstream()` answers its `fetch`, `send` and `fetchCollector` calls in process from the mock plugin's fixture responses (dated by the real clock), and `download()` in `public-sources.ts` takes the same path instead of resolving DNS. Unmatched requests fail with `NR_DEMO_OFFLINE`. A new outbound path must go through these entry points or await `network.inDemoProject()`. Runner dispatch uses the typed application-owned `demoAgent` proxy in `agents-runtime.ts` for analysis, build drafts and article drafts. The demo Agent (`demo-data/demo-agent.ts`) scripts a Runner-like transcript from the run's own materials — thinking, `Bash`/`WebFetch`/`Read`/`Write` tool calls whose results come from the task input, the demo site fixtures and the project knowledge, the summary and usage — and the runtime plays it back over about half a minute, appending each event to the business run's `transcript` and stopping between events once the run is asked to stop. `nrTaskWork.get` returns that transcript in the official progress shape, so Technical details renders it with `RunTranscript`; the task view leaves transcripts out. `NOCOREACH_DEMO_AGENT_PACE` scales the pauses (tests use `0`). Persist the proxy ID with queued runs and reload policy on recovery; disabled proxies never fall back to real runners. Demo task status exposes a virtual demo choice without modifying official agents or project defaults. Reviewed demo changes end with `release.state=simulated`, never a merge or live receipt. Business AI in demo scope always answers in process through `demoModels.complete()`, regardless of the selected default model. Reload the demo model binding before in-process generation; the HTTP model route reloads it before authenticating each call.
- All clear/reset and failed/interrupted-import recovery use `demo-data/clear-all.ts`. Remove project business rows, visitor additions, orphan rows, snapshots, owned blobs, credentials and execution history; preserve system identities, global configuration and the persistent environment model. Cleanup must tolerate partial imports and refuse while work is active. `clear.ts` retains the collection/namespace catalog and scoped cleanup helpers; it is no longer the lifecycle rollback contract.
- Demo models are provisioned at environment startup and survive data operations. Demo Agents use environment mode (`demoConfiguration.enabled`, then `proxy.prepare()`); record markers choose fixture content, not whether real execution is permitted. Unknown projects in a demo deployment remain offline. Daily reset has one persisted management-UI configuration, without a deployment cron override.
- Automatic daily analysis (the minute tick and the Scheduler run in `daily-analysis.ts`) skips demo projects, so their hand-written insights and opportunities stay until someone runs an analysis by hand; the daily demo reset refreshes them.
- Demo roles use member scope and join only the two demo projects. Never grant a published demo account access to all projects. The plugin records account ownership separately from import tracking: only owned accounts may be re-enabled; a pre-existing username aborts the import.
- Register the plugin CLI in `cli/plugins.ts`; `demo-mode data` uses the same lifecycle service as HTTP and Scheduler. Standalone builds install it as a regular production dependency. Do not copy plugin builds into the application or edit generated Skills.

The Agent proxy is registered through `demoConfiguration.registerAgent({ id, title, execute })`; the application owns its input/output schema. Keep explicit `nocoreach.taskCreation` and `nocoreach.opportunities` write scopes around authorized opportunity handoff only. Existing task mutations keep their project/task ownership checks.

## Outbound networking

When changing collection, OAuth, connection tests, or project-scoped background network calls, check this section and the transaction constraints above.

- `server/nocoreach/proxy-profiles.ts` seals global Profiles, the deployment's default proxy and project/connection references together in `nrVariables`. A live deployment routes a connection through the project's choice, or the default proxy when there is none; `DIRECT` keeps one connection off it. Mock deployments and connections read through collectors (Bilibili, Xiaohongshu, YouTube) never take the default. Design: [NETWORK-EGRESS.md](NETWORK-EGRESS.md). `outbound-network.ts` uses instance-scoped AsyncLocalStorage. Inject this transport layer into new collection services. Wrap all project-ID-bearing background/internal entry points in `network.bind`; URL-only previews inherit project scope from the route.
- Explicitly pass the project fetcher to Google OAuth/sync. Derived Google/DataForSEO features share the actual connection's settings. Project icon homepage and image requests share the website egress. The connection switch (live) and profile choice (mock) live in `client/components/connection-network.tsx`; Settings › Network is `client/pages/network.tsx`, which shows the Profile list in `client/pages/proxy-profiles/` in mock deployments. A live deployment shows `proxy-profiles/network-settings.tsx`: the proxy's state, edited in the `proxy` child-route dialog, then every proxy-capable connection of the current project with its switch and an on-demand check. Checks call `testConnection` per connection and are cached under `checkKey` by route, so changing a switch or the proxy re-checks only what changed. `testConnection` returns an unanswered request as `reachable: false` with a `reason` (timeout, reset, refused, dns, certificate, other) and whether it went through the proxy; configuration and shutdown errors still fail the call. Keep the list in `networkSources` in step with `CONNECTIONS`.
- A request that gets no answer fails with `networkFailure()` from `outbound-network.ts`: status 502, the original diagnostic `code` and `name`, plus `reason`, `proxied` and the `host` it was for (the site's name, never a pinned IP). Its message is the NETWORK-EGRESS §3.3 sentence for that reason and route, keyed in `shared/network-failures.ts`; a rejected redirect or an oversized body keeps its earlier message. Direct public reads in `public-sources.ts` (DNS, socket, TLS and the 15-second timeout) fail the same way; cancellations and other errors pass through unchanged. Do not change codes or retry predicates to add hints. A caller that wraps a failure keeps it as `cause` and reads it with `unreachableOf()` (Google's `googleJson` and connection routes, website-content discovery). The client recognizes these sentences in either language, alone or behind the part that failed (`client/lib/network-failure.ts`), and `$legacyText()` translates them there too. Connection panels and the Skill link dialog show errors with `ConnectionError` (`client/components/connection-error.tsx`), which adds a link to Settings › Network and the certificate ⓘ; saved collection errors use `NetworkSettingsLink`; Google's code-only `network_*` errors pass `network`.
- Fixed APIs reuse bounded pools by origin and Profile version; public fetching and connection tests use separate dispatchers. Do not change global fetch/dispatchers or Studio environment variables. Profile updates send new requests through new connections; release old connections after in-flight requests finish. Close pools on application shutdown.
- Public fetching must use `download` public-IP validation and fixed-IP tunnels while retaining TLS verification for the original hostname. Proxy failures must not fall back to direct connections.
- `socks-proxy.ts` establishes SOCKS tunnels: `socks5` resolves locally and `socks5h` through the proxy. Public fetching connects to validated IPs with either protocol. Clean up sockets during connection establishment and retain bounded pools.
- Collector HTTP responses, subprocess output and browser-extracted output are capped at 20 MiB across both application and Collector boundaries. Automatic content ingestion retains its JSON string-length check with a 20,000,000-character cap and 500-record batch limit. These are per-response/batch limits, not cumulative site storage quotas.
- Collector connections can be configured by administrators through `nrCollectors` and the shared Data connections card. `CollectorConnections` seals project/platform overrides in `nrVariables`; deployment-owned `browserCollectors` remains the fallback only when no override exists. Saves are session-bound and revision-checked, reserve against source operations before awaiting I/O, and atomically invalidate verification with the credential write. Never expose tokens or reuse them at a changed address. See [connection setup](COLLECTOR-CONNECTIONS.md).
- Collector platforms (Xiaohongshu, Bilibili, YouTube) show their saved records on Community data pages (`client/pages/data-<platform>.tsx`) through a `<resource>/report` action built with `collectorPeriod()` in `server/nocoreach/collector-views.ts`. Collectors return a publication date and the counts read at collection time, never a series: count records by publication date (first-collected date when unknown) and present counts as latest snapshots, not growth. Connection panels keep configuration and collection controls with a saved count and a link to the data page; do not render result lists in them. Reports compute metrics, the publishing `trend` (daily, weekly or monthly by window length) and origin `groups` over every saved record of the period, but return only the first `limit` records in the requested `sort`/`order`; sort on the server, never the shown page. A Bilibili video counts under its search terms; only a video found by link alone counts under that link (detail reads add a `video` source to searched videos). Pages share the layout in `client/pages/collector-content.tsx` (trend card, sortable table with Agent hand-off, origin card) like the other Community pages. While a collection runs, poll the lightweight `status` (YouTube `summary: true`) and read the report again when it ends. Grant each new `report` action through the platform's `use` capability and add the page to `REACH_PAGES`.

- Collector connection panels (not the data pages) expose project/platform-scoped `clear` actions under each platform's `configure` capability. Keep two sequential confirmations bound to the initiating session, project, revision and permission lifetime; the dispatcher requires the confirmation-session header for all three platforms. Clearing rejects active collection, reserves against new reads before awaiting storage, rotates the source revision, and removes saved records plus collection/analysis metadata while retaining connection credentials and discovery criteria. YouTube also removes captions and pauses automatic collection. Reload the panel status after success and never reuse a previous project's report as mutation input.
- Collector data page reports use the authenticated `WorkspaceCache` under `collectorReportKey(resource, project)`, keyed by period, limit and order. Reuse a report read the same local day when the page opens again; read again on a new day, an explicit read/search, Retry, or the end of a polled collection. Connection-panel changes (including clearing) invalidate the platform's keys for that project. Keep data page headers to the single read/search action used by the other Community pages.
- Bilibili sync refreshes saved video details independently of the first search page, oldest collection first, and enriches up to 20 search discoveries. Deduplicate BV requests within a batch, retain the shared deadline and refusal handling, and preserve known values on incomplete refreshes. Successful saved-record refreshes adopt the current configuration revision and new metric timestamps; never carry old freshness metadata onto newly fetched values.
- YouTube production collection uses `HttpYouTubeProvider` and project Collector overrides or deployment-owned `browserCollectors` entries with the `youtube` platform. Select exactly one project-eligible entry; require protocol-v1 identity/freshness/field validation and keep the source/library transaction boundary intact. Production YouTube collection is metadata-only: Collector omits subtitle fields from yt-dlp output and never selects or downloads captions. The protocol-v1 empty transcript is a compatibility placeholder, not evidence that captions are missing. Do not show caption status in the UI. All yt-dlp I/O belongs to Collector. Never reintroduce a local process, direct-caption, alternate-collector or proxy fallback. The default proxy never applies to YouTube; an explicitly selected YouTube proxy left from before fails with migration guidance until an administrator turns it off in the YouTube connection, the only place its switch appears. Fixture normalization requires injected I/O and must remain isolated from production. See [YouTube deployment](YOUTUBE.md).
- Runner execution and application model calls do not use these proxy settings. Do not turn them into a host-wide network policy.

### Enqueueing, selection, and retries

- `server/nocoreach/execution/agents-runtime.ts` registers the `nocoreachTask` subject. Enqueue official runs inside the business transaction, emit events after commit, and synchronize results through `pluginRunId`. Keep review, revision, and cancellation checks in business services.
- `nr-task-agent:<project>` preserves existing Agent defaults and repository constraints. Select the Agent on each task through `evidence.work.agentId`, which overrides any stored default; administrators configure or clear the current project default on `/agents/runner` through `nrAgent.saveDefault`, with revision and enabled-agent checks. - Non-demo tasks, including research and drafts, require a Runner Agent. Persistently marked demo projects use the registered Demo Agent proxy instead. Online agents are chat-only and must never appear in task options or dispatch paths. Evaluate Runner readiness using the current user's official eligibility, outside business transactions to avoid single-connection deadlocks.
- Manual takeover uses `runs.withdrawQueued` in the same transaction to exclude simultaneous official claiming. The read-only subject `assemble` must not change business state. Cancellation must complete even when the Agent is unavailable; record failed PR cleanup and instruct the user to close it manually.

### Results and execution records

- `/results` projects existing task evidence through `nrTaskWork.board` (the dashboard), `results` (`/results/all`) and `result` (the drawer); it has no result table or navigation badge. The dashboard counts only the project's own work — site-wide metrics belong to Insights and the data pages. Keep target creation, source and successful submission mapping in the existing strategy transaction. Retry the same frozen request with the same UUID; creation never starts execution. Preserve source when an opportunity is handed off, and keep basic submission deduplication separate from similarity detection.
- Daily analysis keeps a re-raised opportunity's id, number and first-seen day by identity, by a matching `existingId`, or as the same thing in other words (`shared/strategy-pending.ts` `sameOpportunity`): the same cited signals and the same target, or the same title apart from digits. Signals alone never merge, since one digest signal can back different actions; a card whose latest copy was handed off is not reused. An undecided card stays pending for `opportunityKeepDays` (14) after the newest batch that raised it, counted from the latest analysis, unless a later card replaced it: the same opportunity, or the same target, raised again by a newer analysis, whatever was decided on that card. Restoring keeps a card pending. The Opportunities page and the menu count share `opportunityState`.

- The task page is written for the people who run marketing: a header with one line of evidence and the playbook's steps, one stage card that holds what the task needs now (and the effect once live), and an activity timeline that lists delivered versions. Keep pull requests, branches, file paths, check output, Runner/model details and error codes off it. They belong in the Technical details dialog (`?details=result|runs`), which reuses official `RunHeader` / `RunTranscript`; `?run=` selects a historical run and opens that dialog on its runs. Only participants and administrators may read transcripts. Show the actual model/Runner, tool inputs/outputs, and permission denials there. Business failures take precedence over tool-turn completion.
- Validate `report.kind` separately for research, community replies, and content results. Preserve `sources`, `asOf`, and `uncertainties` before human review. `report.asOf` allows up to 1000 characters; do not truncate timing notes covering multiple sources. Instructions and validation share the limit, and oversized-result errors identify the field and limit.
- `task result --content-file result.json` uses the existing `nocoreach.tasks/propose` capability. It validates and stores one immutable result per business run; identical submissions are idempotent. Corrections happen before acceptance, with at most two correction retries instructed to the Agent. The official completed event consumes this snapshot; cancellation/failure never consumes it. The final summary remains a fallback for Agents without the command. Do not add a second executor, change plugin-owned run storage or parse arbitrary prose for JSON.
- Result sources are either `{title,url}` (HTTP/HTTPS without credentials) or `{title,material}` (`context`, `sources`, `knowledge`, `skills` within the producing run). Only exact historical mount aliases and that task's `nocoreach://task/<id>` normalize to materials. Render materials as text, never filesystem links. The compatibility parser removes only the exact `Local continuation saved: <path> (<40-hex commit>); not pushed.` footer; retain the original official summary for diagnostics.

Read official completion outside the business transaction, then recheck owner/admin authorization, actor/owner eligibility, cancellation, current stage/artifact, and absence of active work inside it. Preserve the original failure, audit the recovery and never replay build/merge/revert operations or grant approval automatically. See [task result help](TASK-RESULTS.zh-CN.md).

Build results must include release notes, page validation evidence, and change comparisons, returning explicit empty values when verification is unavailable. - Business tests live in `tests/nocoreach/`. `agents-app.test.ts` covers the official Runner protocol against real plugins and a database. Check relevant coverage when changing enqueueing, materials, cancellation, retries, or CLI distribution.

### Article publishing

See [ARTICLE-PUBLISHING.md](ARTICLE-PUBLISHING.md) for the model, states and limits, and [ARTICLE-API.md](ARTICLE-API.md) for the `http` protocol.

- Publishing targets are per-project settings sealed in `nrVariables` (`server/nocoreach/articles/targets.ts`); credentials never reach the browser or the Runner, and changing a target's address or repository requires its key again. Saves need the browser confirmation session, like collector credentials. Validate the complete settings before persisting them, including the ten-target limit, so rejected additions leave existing settings readable. Editing a target keeps its position; `defaultTargetId` (`setDefaultTarget`, cleared when that target is removed) decides which target a new task starts with, falling back to the first. `playbookTargets` (`savePlaybookTargets`) overrides it per playbook with a target id or `'repo'`; removing a target drops the entries naming it, and no new target may take the id `repo`.
- A task's delivery is frozen at start in `work.delivery`. Article change steps run in mode `article` without a repository; the source article is an immutable snapshot delivered as the `article.json` material, and the proposal is validated against the target both by `task result` and on acceptance. Keep target I/O (link, the slug lookup in other targets at start, rebase, publish, export and drift checks) outside business transactions and recheck state under the task lock before recording an outcome. A release to several targets keeps one record per target and derives `release.state` from them; touch a record's state only through the leg helpers in `article-flow.ts` (`legsOf`, `stateOf`, `settle`) so single-target releases from before keep working.
- Publishing writes only the approved artifact's changed fields, adopts a write that already landed, treats a field both sides changed as a conflict, and blocks on a Git-only edit when the target exports to Git. Never publish from a later draft than the approved artifact, and never mark a release live from a CMS save alone: export and page checks are separate states.
- `nocobase-api` is check-before-write and cannot prevent a stale editor form from overwriting a publish; the overwrite watch only reports it. Do not describe it as guaranteed. Build changes to files a target's exporter owns are blocked (`pr.protected`).
- Export and overwrite checks compare every written field against the approved artifact, including its normalized publication status. Manual draft edits preserve the existing draft status when editing content fields. New articles on a target that stores a status default to `draft` on the server; publishing one directly is an explicit choice in the editor. Omitting status from that baseline falsely reports a new draft as overwritten.

### Continuous integration

- `.github/workflows/ci.yml` runs independent `tests` and `build` checks on pull requests, `main` pushes, and manual runs using Ubuntu 24.04, Node 24, and the pnpm version in `packageManager`. - Fix the Runner application identity and CLI name to `nocoreach`, matching `package.json`'s `nocobase.cli.bin` and published archives. Do not derive them from `/main` or the deployment path.
- CLI release versions are immutable installer cache keys: changing CLI branding, authentication, or packaged code requires a new application version (or an explicit `nocobase.cli.version`). Rebuilding under the same version does not replace existing installations, even when the archive checksum changes. The browser-auth release is `1.0.0-beta.67`; the template source marker is independent and unchanged.
- Validate distribution by downloading into an empty cache, verifying, unpacking, and executing. Also test upgrading an existing earlier installation: confirm the new archive is fetched, `current` switches to the new version, the packaged brand includes `auth` and `login` reaches the device-code endpoint in an isolated transport test, and old versions and user state remain intact. Help text alone is not evidence of runtime authentication support. Verify embedded Studio deployments through the actual application; standalone success does not establish correct host paths. See the [CLI distribution record](CLI-DISTRIBUTION-beta63.md) for steps and historical context.

### Configuration and static assets

- Do not hard-code deployment prefixes in routes. Use `resolveAppUrl` for pages, APIs, and dynamic artifacts, and `resolveAssetUrl` for static files. Use shared `AppPaths` on the server and preserve configuration, host logging, and lifecycle binding through `createAppFromRuntime(runtime)`.
- The browser origin must match `app.publicOrigin` / `APP_PUBLIC_ORIGIN`. Do not disable origin checks to resolve authentication failures. Writes through a remote development proxy affect the target backend.
- `CDN_BASE_URL` is a build variable requiring a full HTTPS URL and trailing `/`. It defaults to `./` and is ignored in development. Precedence is process environment, `.env.local`, then `.env`. Upload the complete `dist/client/` assets and configure CORS; the application server still retains its client directory and HTML injection. Docker source builds use the same build-arg name; runtime changes cannot alter compiled asset URLs.
- Development watching excludes this application's entire `dist/`, but not linked workspace dependencies. Auxiliary Vite tests use isolated temporary `cacheDir` values; never clear or rewrite the cache of a running development server.

### Classic data import

`pnpm nocobase app import-classic` is implemented in `cli/commands/import-classic.ts`. Run it on a machine that can access classic Postgres through `CLASSIC_DB_*`. It calls the target application's `nrImport` actions over HTTP with a root user's `NOCOREACH_API_KEY`, rather than connecting directly to Studio's database. Decrypt classic secrets on the source machine and reseal them at the target. Import is a separate data migration task, not a routine deployment step; consult the [port record](PORT-PLAN.md) before proceeding.
