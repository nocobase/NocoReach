# NocoReach Development Constraints

This document covers application adaptations to the template and business boundaries prone to regressions. Read the relevant sections when changing those features. Follow the [application development Skill](../.agents/skills/nocobase-app-development/SKILL.md) and its references for general development; explicit application adaptations below take precedence over template examples.

See the [changelog](../CHANGELOG.md) and [port plan](PORT-PLAN.md) for historical context. Legacy Agent and AI configuration, deployment steps, and outstanding items in the port plan reflect their time, not current implementation requirements. Dependency versions come from `package.json` and the lockfile.

## Frontend

Before changing `client/`, read the [frontend workflow](../.agents/skills/nocobase-app-development/references/frontend/ui-workflow.md) for task-specific component, styling, interaction, and validation guidance. Preserve the application differences below.

### Business pages and copy

- Ported business pages and components live in `client/pages/` and `client/components/`. Requests use the `nocobaseClient.action()` contract in `client/lib/nocoreach-api.ts`; toasts use `client/lib/toast.ts`.
- Business copy uses stable, module-scoped English semantic keys (`common.save`, `playbooks.communityReplyInstruction`, `dataHealth.retryScheduled`). Use lower camelCase segments, reuse only the same meaning/context, and keep keys stable when wording changes. Do not use Chinese keys, whole sentences, hashes, or numbered identifiers. Business translations live in `shared/i18n/`: `en.json`, `zh.json`, and one JSON file per additional locale, registered in the application client/server locales. The UI offers English, Simplified Chinese, Traditional Chinese, Japanese, Spanish, Brazilian Portuguese, French, German, Vietnamese, and Indonesian; keep both loader maps aligned with `shared/i18n/locales.ts`. New or changed copy needs all ten languages in the same pull request, including shell keys in `client/locales/translations/`; `tests/logic/additional-locales.test.ts` names missing and extra keys and changed placeholders, but cannot tell when a translation is stale. Keep helper modules outside the locale directory roots: `nocobase locales check` treats each root-level locale file as a language. Preserve translation values, numeric `{0}` interpolation, and intentionally empty measure words. Business pages use `$t()` / `$tj()` from `client/i18n`; deferred messages still follow the application runtime's resolved locale.
- Review translations against call-site parameters, not English wording alone: platform/domain placeholders are names, and hand-off counts include the displayed examples. In `common.moreActions`, `{0}` is a task title or keyword, never an action count; `dataChat.lastRead` describes the collector run time, not a user viewing messages. Translate task objectives as requested changes or desired outcomes, never as claims that the work is already complete. Check query-ranking, tracked-keyword ranking, search-click and indexing objectives against their hand-off callers, including when the English source is ambiguous. Select complete sentences for combined mention/citation states and keyword hand-off titles rather than concatenating translated labels; keyword titles select writing or improving and one or several keywords before interpolation. Keep the old `aiQuestions.alreadyUs` key only for historical text compatibility. Data coverage dates identify the latest collected day, not service or authorization expiration.
- `$t()` and `$tj()` interpolate positional values but do not select grammatical plural forms. Quantity-bearing business templates must remain grammatical for zero, one and multiple items. Prefer a complete count-neutral phrase or a category label followed by its value; preserve every fact and interpolation slot when rewriting a sentence. Do not add `_one` / `_other` keys without a caller that selects them, infer counts from formatted strings, or concatenate a quantity with a separately translated noun. A template with several quantities needs correct agreement for each independently. Plugin copy rendered through the framework can use its existing plural support or count-neutral labels. Selection toolbar labels are independent categories placed before their counts, not noun suffixes. Rule thresholds use `analysis-rules/labels.ts` to choose explicit singular forms for the recognized server-owned answer, page and place units; custom units remain literal.
- `shared/i18n/legacy-keys.json` is a compatibility manifest for pre-migration system text, not the active dictionary. `$t()` does not resolve Chinese aliases. Only `$legacyText()` / `$legacyJsx()` at historical API/snapshot boundaries may read them; `$legacyFragment()` reads whole system-owned short fragments such as change chips, whose templates are too short for sentence recognition. Keep custom/edited playbooks, user names, queries, notes, and interpolation values literal. Dynamic keyword groups retain their persisted Chinese identities and map explicitly to semantic display keys. Glossary lookups accept original server metric labels and translated display labels; these lookup identities are not translation keys. To reword Chinese system copy that is stored in snapshots (built-in step names, for example), keep its old text as the alias, add the key to `currentSystemText` in `shared/i18n/messages.ts` so the new text is recognized too, and record the change in the locale coverage test's `changedLegacyCopy`; `client/pages/playbook-snapshot.ts` compares system text by message key, so older snapshots still count as canonical.
- This translation migration does not change database fields, task status values, URL semantics or persisted message formats. Do not introduce data migrations or serialized message markers for i18n. Keep server error messages, codes and control-flow predicates unchanged; use response metadata and presentation mappings to translate existing dynamic system text.
- Server-owned copy is emitted with `systemMessageText(semanticKey, params)`. The Chinese default preserves existing stored/display text and older clients. Text stored for an Agent, such as the goal label of a task brief, uses the request locale from `ctx.getCurrentLocale()` so it matches the client-built brief. Data-health `*Text.key` metadata now carries semantic keys while the legacy fields retain their original Chinese values. API errors preserve status, reason and raw message, and add semantic metadata when recognized; the request adapter re-renders that key when language changes. Historical rendered text, built-in playbook snapshots, audit/analysis labels, and old errors are read through the explicit compatibility manifest/pattern reader. Do not rewrite executed migrations or stored user data for key renames.
- Business navigation keeps its existing `nocoreach.nav.*` keys in `client/locales/`; shell and administration copy retains application locales and official namespace overrides. Plugin namespaces retain their upstream keys. When changing translations, validate resource keys and interpolation with a one-off check. Review wording in its calling context: distinguish approval from transport, read-only access from reading a subset, diagnostic states from instructions, publishing in progress from a live result, action effects from current state, and existing PR links from commands. Verify metric comparison windows against the producer and interpolation arguments rather than copying an ambiguous source translation. Reuse existing semantic locale coverage and affected component/server tests for changes to translation behavior. New client/server locale modules register their business dictionaries with `registerBusinessLocale` when loaded. Load the target locale through the framework before calling `systemMessageText` outside a request. The synchronous business adapter follows the full resolved locale, including Traditional Chinese, and never maintains a separate persisted preference.
- Additional shell translations live in `client/locales/translations/`. Their `plugins-<locale>.json` files, together with the server equivalents in `server/locales/translations/`, supply application-owned translations for installed plugin namespaces that lack those languages; recheck their keys against installed plugins after upgrades. Keep product names, commands, URLs, placeholders, user content, and stored system identities unchanged. Distinguish the Runner program from the execution environment that hosts it; a terminology cleanup must not replace both with the same term. Preserve external navigation labels such as GitHub’s Insights → Traffic so instructions match the destination interface. Keep examples that are actual search or detection inputs literal. The community-reply instruction must preserve the parser’s `Link`, `Asking`, `References`, `Docs gap`, `### Reply` and `None` markers even when the surrounding instructions and field values are localized. UI language is separate from the existing project setting for AI-written content.
- A data source named in a list shows its mark through `SourceLogo` (`#components/reach/source-logo`), which resolves catalog, Data health, analysis-rule and package-registry ids to a brand mark from `client/components/reach/brand-logos.ts` (Simple Icons path data, CC0; black marks use the text colour) or a matching lucide icon. Add a new source's id there rather than drawing a mark in place; the sidebar navigation keeps its own icons.
- Dates, numbers and changes go through `client/lib/format.ts` (`formatDate`, `formatDateTime`, `formatCount`, `formatPercent`, `formatSigned`, `formatChange`, `formatDuration`) and a change shown on its own through `Delta` (`#components/reach/delta`): Chinese dates are "2026-10-21", without the year in the current year, times without seconds or a time zone; a change is an arrow, a space and its size ("↑ 12%"). Do not hand-write `toLocaleString`, `toFixed(1)}%`, ▲/▼ or a "+" in a template, which is how eight date styles and "+-7/week" came about. Chart axes may keep their compact `MM-DD` ticks.
- Shared controls look the same on every page: every refresh or update control — reading the page again, fetching new data from a source ("Update now", `common.updateNow`), running the analysis again, suggesting again, checking connectivity — is `RefreshButton` (`#components/reach/refresh-button`): an icon-only ↻ with its label as tooltip and accessible name, last among the page header's actions — a refresh for a whole tab goes there too, through `HeaderActions` (`#components/reach/page`); only a refresh of one card stays at that card's right (2026-10-22 user decision: one look, icon only, explanation on hover); a "pick one of a few" control — date range, period, metric, checkpoint, a table's row filters — is `Segmented` (`#components/reach/segmented`), square with a grey ground for the chosen one, never pills or outline buttons (2026-10-22 decision D1); line tabs only switch a page's sections under its header, and a table's row filters are `DataTableTabs`, a segmented control at the left of the table's toolbar row with its search (`tools`) and actions on the same row (`segmentedListClass` / `segmentedItemClass` for markup that needs tab semantics); filters use the application's `Select` with the I12 popup class, never a native `select`; a tab bar of links or plain buttons takes `lineTabClass` and `lineTabListClass` (`#components/reach/line-tabs`), which look exactly like `TabsList variant='line'`, and a tab's count follows its name without brackets; a hand-drawn table's `thead` takes `data-slot='table-header'` for the shared header ground; chips listing terms take `chipClass` (`#components/reach/chip`); a note about a card, chart, form or tab is an ⓘ (`InfoTip`, or a `Section`'s `description`, which `SectionHeading` draws as one) beside its title, never a grey line under it or brackets in the title (2026-10-22 decision D5); a data page's status line reads "[scope] · Updated <time> ⓘ" with how often it runs in the ⓘ (decision D2), and a page's description covers all its tabs and does not change with them (decision D3); a table footer shows only when there is more than one page.
- Internal imports use `package.json#imports` mappings such as `#components/*`. Directory entry points explicitly target `index`; do not add Vite aliases or TypeScript paths.

Markdown links to same-origin task details (`/actions/:id`) and opportunities (`/opportunities`, which the daily analysis tool links) within the runtime application base path use React Router navigation, preserving query/hash parameters and existing draft blockers. All other links retain browser navigation. Keep this behavior in the shared Markdown link component so online and Runner conversations follow the same policy. Project-scoped navigation badges must reset only their own data: never key the provider wrapping the shell by project ID, which would destroy the header and active conversation during cross-project task navigation.

### Routes, identity, and shell

- Business routes are declared in `client/nocoreach-routes.ts` and guarded by membership and project checks in `client/pages/nocoreach-page.tsx`. Business pages use explicit framework page grants; official Agents pages retain plugin grants. APIs independently enforce the business action and project grants documented in [Access](ACCESS-DEVELOPMENT.md).
- A page's tabs and the overlays opened over them are plain child routes (`authz: 'skip'`, no `gated()`): the parent page already passed the gates, and a second gate would wrap the tab in another content container. Because the gate is what follows the language, each tab and overlay component calls `useNocoReachLocale()` itself; components rendered through an `Outlet` do not re-render with the page.
- All pages use `defineAppRoutes()` and the single `AppLayout`. The retired `/settings` UI, administration routes, and dedicated source are removed; unmatched URLs follow the normal home fallback. Keep backend plugin services and stored authorization independent of UI availability. Do not restore `defineSettingsRoutes()`, `defineDevRoutes()`, or a second administration shell.
- NocoReach identity and request caches belong in the authenticated subtree of `client/routing/app-router.tsx`, using official session boundaries and authorization revisions. Do not move them to the application provider layer. Failed identity reads or missing roles grant no access. Isolate persisted reports by user/session/revision. Requests must not update unmounted component state or refill a disposed authentication/authorization cache. Route changes may let pending reports complete into the same active session cache; explicit invalidation must fence older responses from refilling it.
- `SessionPreparation` sits inside `RequiredAuthentication` and outside `MeProvider`, `WorkspaceCacheProvider`, draft guards and navigation badges. Wait for the authenticated realtime handshake and its synchronous permission invalidation before mounting these consumers. Keep the ten-second failure screen, retry and sign-out path; guest routes remain independent of realtime. Later reconnects and permission changes must still invalidate and unmount protected content.
- Preserve sign-out error checks and notifications, permission snapshot clearing on account changes, and page rechecks triggered by authorization revisions. Hide protected content while checks are pending or have failed.
- Task drafts share the authenticated session boundary. Keep their navigation guard beside the authenticated Outlet so guest/optional history navigation cannot silently destroy drafts after leaving a task page. Navigation confirmation acknowledges the current dirty entries without clearing them; unchanged acknowledged drafts must not prompt again on each menu click. New edits require confirmation again, and browser unload protection remains active until drafts are saved or discarded. Retained stage drafts belong to their original artifact; show older drafts for comparison instead of rebinding them to a newer artifact/revision. Keep task mutations mounted until they settle. The brand link targets `/home` directly so the root redirect cannot ask draft guards a second time and leave an empty page when cancelled.
- Layouts render breadcrumbs; pages only declare their trails. NocoReach departs from the template's "trail on every page" (guideline L6, `page.md` §7) in `client/components/breadcrumbs.tsx`: a top-level page's trail is only its own title, which its `PageHeader` repeats right below, so the header hides it until the page's first `h1` scrolls out from under the header (`AppLayout` passes its content scroller), then fades it in rising 6px (fade only with reduced motion). A page below another one — a covering child page, a record's own page — always shows its full trail, and every such page declares one with `usePageBreadcrumb` whose parent level carries the parent's search; it has no `BackButton`, so a new child page must declare its trail rather than rely on a one-level route trail, which would be hidden like a top-level page's. Navigation groups stay out of trails: the sidebar shows them and they lead nowhere. A top-level page with page-level tabs (shadcn `Tabs`, route links or `?tab=` buttons) declares the selected tab's label, without counts, with `usePageTab` from `#hooks/use-page-tab`; the revealed trail then reads "GitHub › GitHub hot topics", and the page's level leads to its default tab scrolled to the top. A tab is not a trail level: never declare it with `usePageBreadcrumb`, which would make the page read as one below another. Tabs inside a block, such as report table tabs, declare nothing. Below `md` the header is compact: no trail, the compact brand on top-level pages and `BreadcrumbParentLink` ("‹ Keywords") on pages below another one. The project switcher lives in `client/layouts/app-layout.tsx`. Demo status uses the ten-language dictionary in `app-plugins/nocoreach-mock/client/indicator-copy.ts` and replaces the existing sidebar-footer shield in place, with localized hover/focus details; never add a separate row or page-wide banner. App uses the desktop collapse preference `nocobase:sidebar:collapsed`; mobile menu state remains local. Preserve permission filtering, group expansion state, collapsed tooltips/popovers, and keyboard interaction.

- The version at the bottom of the account menu (`client/layouts/components/app-version.tsx`) is compiled from this application's `package.json` → `nocobase.defaultTemplateVersion` by `vite.config.ts`; the sidebar footer shows only the slogan. The slogan, the sign-in panel and the README headers share one agreed wording (AI growth operations platform; Find the opportunities in your data. NocoReach puts them into action.) in every interface language; change them together. Public `app.version` describes application identity, not template ancestry, and embedded Studio metadata must not override this baseline. Rebuild after a template source upgrade; missing or invalid metadata displays the localized unknown state.

- `AppLayout` passes `sections={false}` to the template's `NavigationMenu`, keeping top-level groups collapsible instead of always-open sections, and shows the Insights, Opportunities and Tasks pending counts through its `badges` prop, keyed by route name (`usePendingNavigationBadges`, fed by `client/components/app-shell/nav-badges.tsx`). The counts are orange (`--attention`) via `client/theme/presentation.css`. Customize the permission-filtered tree in `client/lib/navigation-transform.ts`, not in the menu component.

- NocoReach retains its header inbox shortcut and unread title badge as application-owned UI; the upstream template no longer supplies that entry. Keep its notification permission and session checks.

### Themes and components

- Settings › Demo management supplies a stable `DemoSettingsComponents` map to the plugin: the application PageHeader, RefreshButton, line tabs, Section adapters and Button. The client registration disables the floating entry with `showFloatingAccountSwitcher: false`, keeping account-menu switching. Demo administrators use `admin` / `Demo@2026` in both dataset languages; account creation and advertised credentials must match, and non-demo username conflicts must still abort import. Keep the plugin responsible for permissions, query tabs, mounted drafts, confirmations and revision checks; declare its localized active tab through `usePageTab`. Preserve one PageContainer, and wrap tab/action/footer rows at narrow widths. Do not patch the plugin DOM with global CSS or define adapters inside the page render.

- Use existing shadcn/ui components and semantic theme tokens. Add missing primitives through the CLI rather than rewriting generated components. Page overlays use route components; read the [overlay reference](../.agents/skills/nocobase-app-development/references/frontend/references/overlay.md) first.
- Pages fill the content area. NocoReach departs from guideline L4, which limits form and reading pages to `max-w-2xl`–`max-w-4xl`: no `PageContainer` or page-level wrapper takes a `max-w-*`, so no page leaves an empty band on the right. Where a field would read badly at full width, cap that input (the role form's name and identifier use `max-w-md`), never the page. Overlays, popovers, table cells, search inputs, the header description's line length, Markdown reading measures and centred single-card states (sign-in, Not joined, the first project) keep their own widths.
- `client/styles.css` follows the template and owns the shared interaction, focus, navigation, table, overlay, alert and toast treatment. `client/theme/presentation.css` holds only NocoReach's additions: legacy `.nr-page` tables (the same header as official tables, via `--hover`) and the orange navigation counts. For semantic status labels use `StatusBadge`; `size='sm'` is the small badge beside a title or on a dense card. App retains `app-brand-surface`. Preserve NocoReach branding, semantic Tag colors, both densities, and browser preferences; do not restyle one page independently.
- A record opened from a list slides in a right-hand `Sheet` instead of sitting in a panel beside the list (Opportunities, Playbooks, Skills). To widen it, use `data-[side=right]:sm:max-w-*`: the Sheet's own `data-[side=right]:sm:max-w-sm` outranks a plain `sm:max-w-*`. Group long lists with line tabs or headings rather than fold-out sections.
- Calculate the wide task table minimum width from spacing units needed by fixed columns and the title column. Reserve enough status width for supported languages in compact density. At narrower container widths, hide secondary columns; on phones, show the number and status above the fully wrapping title while retaining row actions. Mobile headers retain compact branding (replaced by the parent link on pages below another one), project icons, and smaller button gaps. Show breadcrumbs at md and above; retain full project names in the switcher menu and accessible text.

Follow the application Skill references for [routes](../.agents/skills/nocobase-app-development/references/server-routes.md), [HTTP contracts](../.agents/skills/nocobase-app-development/references/http-api.md), [services](../.agents/skills/nocobase-app-development/references/services-and-jobs.md), and [data access](../.agents/skills/nocobase-app-development/references/database-and-data.md). Database APIs are documented in the [database Skill](../.agents/skills/nocobase-db/SKILL.md).

### Compatibility layer and authorization

- `server/nocoreach/*.ts` contains ported classic services, retaining dense formatting and `// @ts-nocheck`. Put NocoBase 3 adaptations in `server/nocoreach/legacy/` and business behavior in services. Do not rewrite the entire compatibility layer as incidental cleanup.
- The compatibility layer rebuilds repositories, filters, transactions, resource actions, timers, and other classic interfaces. Classic advisory locks use keyed in-process locks. Store settings in `nrVariables` and seal secrets. Users come from NocoBase 3 accounts; transactional reads use the caller's connection.
- `server/providers/nocoreach.ts` assembles the layer and manages timers. `server/routes/nocoreach.ts` dispatches `/api/nocoreach/<resource>/<action>`. Each action checks current framework permission-set assignments through `server/access/service.ts` and `server/nocoreach/policy.ts`. The retained `nr-members` snapshot is a migration/rollback artifact, never a runtime role source. System administrators retain business access; scoped keys still constrain them. Page or collection grants do not replace business authorization. See [Access](ACCESS-DEVELOPMENT.md) and the Chinese [cutover procedure](ACCESS-CUTOVER.md).
- Notifications use the official Notification plugin and its configured in-app channel; inbox adaptation lives in `legacy/notifications.ts`. Daily analysis is the Scheduler target `nocoreach.daily-analysis`, with runs available through the official Scheduler API/CLI. `pm.get('workflow')` and `workflows` are compatibility names in `legacy/schedule.ts`; official Workflow was removed and must not be reintroduced.
- Google OAuth callbacks require the current signed-in account to match the state initiator. Re-read enabled account status and current NocoReach administrator eligibility before token exchange and after upstream I/O, before saving credentials. Callback attempts consume state once and clear the nonce cookie; signing out or switching accounts requires restarting authorization.
- Server routes own their authorization; page `auth`/`authz` is not server protection. Register background work through providers rather than directory discovery.

### Transactions and synchronization

- Reddit collection persists its fixed query scope, business cutoff and per-term request keys in the existing snapshot before paid I/O. Successful terms are retained during a partial round. Only explicit terminal errors allowed by DataForSEO's [error reference](https://docs.dataforseo.com/v3/appendix/errors/) and [live endpoint guidance](https://dataforseo.com/help-center/best-practices-live-endpoints-in-dataforseo-api), with an explicit zero total cost, retry automatically (at most twice, after 1h and 6h). Transport, malformed and missing-cost failures require reconciliation and remain blocked across cache expiry. Legacy failed snapshots also pause because their billing evidence is missing. Manual checks obey the same limits; pre-request connection/budget refusals can recheck the original key after settings are corrected. Polling and not-due scans only compute scheduling; an executing batch adds one short snapshot transaction before its existing final transaction. No HTTP runs inside either transaction, and no new lock or scheduler is introduced.

- SQLite uses one connection. Do not wait for another database connection inside a business transaction. User reads must use the caller's transaction. Keep model gateway requests outside business transactions.
- Google sync claims work in a short transaction, collects outside transactions, then validates and commits in another short transaction. Never wait for OAuth or Google APIs while holding a transaction. A single-instance `busy` guard protects in-flight batches. Pausing cancels the old batch; its results must not be committed even if immediately resumed. Limit collection to two minutes per batch and retain bounded retries.
- `transactionContext()` in `legacy/database.ts` isolates snapshot caches and construction promises. A transaction must neither wait for snapshot construction outside its scope nor publish uncommitted results to shared caches.
- Do not edit executed migrations or migration history tables to silence checksum errors. Collection files are generated caches; see the [migration reference](../.agents/skills/nocobase-app-development/references/migrations.md). Preserve compiled migration and seed `.manifest.json` generation; do not regenerate manifests for installed dependencies.
- Data health (`server/nocoreach/data-health.ts`) gives each row needing attention a `fix`: `retry`; `settings` for a refusal only a changed setting cures (Google `invalid_grant` or `resource_changed`, a refused GitHub token, X's spending cap, a paused daily analysis, a competitor refusal with a 4xx status other than 408 and 429, recorded as `lastRun.configError`); `verify` for an uncertain DataForSEO result (`lastRun.uncertain` from Rank tracking and Trends, retried with `retryUncertain`); or `wait` while Google retries by itself. Settings › Data sources › Data health runs Retry all on `retry` rows the person may retry and asks before a `verify` retry. A source that adds a failure kind records it where the error is caught; do not classify by message text.

### Google report caches

- Default unfiltered web search totals read durable `nrSyncPartitions` overview rows, independently of report-cache expiry. Missing partitions, successful empty arrays (Google returned no record), and numeric zero rows are distinct. Never generate zero rows from omitted dates.
- `nrGoogle/syncNow` retains the existing administrator check. With `{scope:'gscOverview',startDate,endDate,mode:'missing'|'refresh'}` it queues only final, unfiltered web overview work, clamped to the last 16 calendar months and the Los Angeles final cutoff (today minus three days). Reject filters and non-web types. Without `scope`, the existing 7/28/56-day combined sync remains. The response contains `jobs`, `earliest`, and `cutoff`; `history-fill` and `history-refresh` are persisted trigger values in the existing job table. Missing mode subtracts stored days and active/paused/failed job intervals; explicit retry/resume uses `syncControl`. History jobs do not update the combined sync timestamps or schedule and never create query-page partitions.
- `nrDataViews/search` returns summary/coverage by default; `details:true` queries separate query/page aggregates. `coverage.current` and `coverage.previous` expose requested bounds, recorded/no-record/missing days and intervals, plus last-save time; `coverage.earliest` describes the default overview backfill boundary. Both periods need daily records for comparisons. `history.jobs` and `history.scheduleEnabled` are read outside the six-hour report cache. Active pages poll this read endpoint every five seconds; only the initial administrator view or an explicit action submits writes. Detail/breakdown/row comparisons use the summary's `compare` qualification, and live date queries are not clipped to locally stored days.
- Each active poll repeats the report request: authorization and connection checks, snapshot-version reads, preliminary-cache reads where applicable, and the current-resource job read. A cache miss may also read partitions or stored report caches. This is more than one database query; polling itself does not enqueue work or refresh Google. Connection changes invalidate both versioned summary keys and JSON-scoped detail keys only for the affected project.
- `GoogleReportCache` retains GA4's existing `ga4-reports:<project>` snapshots and uses separate GSC/local namespaces. It shares pending reads only within the service instance, clones responses, and bypasses shared reads/writes inside a transaction. Keep authorization and `sync.link()` checks before cache access. Include project, resource, captured authorization identity, actual dates/filters, and `network.mockCacheKey()` in applicable identities; concurrent token refreshes use the same captured scope.
- Upstream historical reports expire after six hours; partial dimensions/sitemap children retry after five minutes. Successful empty reports are cacheable. Reused reports preserve their original `cacheExpiresAt`; synced aggregate versions invalidate when partitions change. Cache aggregated live search tables rather than raw query-page matrices. Limits are 2 MiB per entry, 8 MiB per project/namespace snapshot (32 entries), and 16 MiB per cache instance in memory (128 entries). These are serialized-byte budgets, not process heap limits; oversized results are returned without retention.
- Frontend reports use the authenticated `WorkspaceCache` and its session storage. Search performance, overview, content and sitemap views have a one-minute freshness window; index progress/details use thirty seconds and retain running-job polling. Historical breakdowns/details honor server expiry. Include the selected properties in report keys and invalidate Google reports after resource/authorization changes, and affected local views after website-content mutations. Do not cache mutation responses or use long report TTLs for job state.

### Demo data

- `demo-data/samples.ts` exports `generateNocoReachSamples`, the shared business generator. The demo dataset calls it through `generate(context)`; weighted stages remain internal to the generator. A future ordinary sample registration may call the same function with an application-owned context, but must not call demo reset/import. This application does not automatically populate ordinary installations. Demo resets never modify sample seed history, ordinary initialization seeds or migrations.

- `demoConfigurationToken` owns the persisted revisioned schedule, collection exceptions and mock switches. Register mocks and the Demo Agent in `demo-data/adapters.ts`. A demo deployment (`NOCOBASE_DEMO_MODE=true`) refuses request writes except the collections an administrator opens on Visitor writes (logical names such as `nrOnlineAgentRecords`, `nrSnapshots`, `nrTasks`); the plugin has no per-operation or per-record write capabilities, so normal business authorization decides who may write what. Never trust a client demo flag. Request policy is snapshotted before business transactions to avoid nested SQLite connection deadlocks; updates apply to subsequent requests.
- Skills list/detail and Agent material reads overlay missing built-ins in memory, including an older library's pending additions. Persist those additions only during mutation or the existing startup upgrade; browsing Playbooks or project knowledge must not write snapshots or require a demo write exception. Preserve user edits and deletions when merging built-ins.
- Keyword detail market/SERP reads persist provider results in `nrKeywordRuns`. Demo deployments must allow this collection through Visitor writes before exercising those pages; mocked outbound responses alone do not bypass the database guard. Preserve the other selections and schedule when updating the revisioned configuration, and verify response-level `ready` statuses, not just HTTP 200.

### Enqueueing, selection, and retries

- `server/nocoreach/execution/agents-runtime.ts` registers the `nocoreachTask` subject. Enqueue official runs inside the business transaction, emit events after commit, and synchronize results through `pluginRunId`. Keep review, revision, and cancellation checks in business services.
- `nr-task-agent:<project>` preserves existing Agent defaults and repository constraints. - All tasks, including research and drafts, require a Runner Agent. Online agents are chat-only and must never appear in task options or dispatch paths. Evaluate Runner readiness using the current user's official eligibility, outside business transactions to avoid single-connection deadlocks.
- Manual takeover uses `runs.withdrawQueued` in the same transaction to exclude simultaneous official claiming. The read-only subject `assemble` must not change business state. Cancellation must complete even when the Agent is unavailable; record failed PR cleanup and instruct the user to close it manually.
- Task runs are enqueued with one attempt, so a run whose Runner the Agents sweep takes back (`runnerOffline`, `leaseExpired`, `startTimeout`) fails at once. Every deploy restarts NocoReach, and a run working through the restart loses its lease that way. `server/providers/nocoreach.ts` takes the instance's start at registration (Studio restarts the application inside its host process, so not the process start), `TaskService` keeps the latest starts in `nr-app-starts`, and `restarts.ts` attributes such a failure to a start between the run's hand-over and the failure, at most five minutes before it. The business run records `restartedAt`; a `plan`/`build`/`article` run still current on its Agent step is started again once per step for each restart through `queueAgentRun` (`retryAfterRestart`, recorded as the system's `retryStage` with note `serverRestart`, the new run carrying `autoRetry`), acting for the same person after rechecking their authorization. Review, publishing (merge), close and revert runs, a run someone asked to stop, and a step that moved on are never retried this way.
- `server/app.ts` registers `server/routes/agent-retry-guard.ts` before plugin routes, blocking generic HTTP/CLI retry only for `nocoreachTask`. ### Results and execution records

- `/results` projects existing task evidence through `nrTaskWork.board` (the dashboard), `results` (`/results/all`) and `result` (the drawer); it has no result table or navigation badge. The dashboard counts only the project's own work — site-wide metrics belong to Insights and the data pages. A result's `phase` is `live` once the observe stage started, `pendingLive` while its flow still has an observe stage ahead, otherwise `delivered`; page totals add each live change's latest checkpoint only when that source's days are all covered. New observation snapshots record valid GSC/GA4 date coverage. Shared comparison presentation treats unknown or incomplete coverage as unavailable and a zero baseline as an absolute difference only; do not backfill old snapshots or infer causality.
- `nrStrategy.createFromResult` freezes the server-read observation in `resultSource`. Strategy JSON stores `resultOpportunities` and `resultSubmissions`; manual cards bypass daily analysis identity merging and expiry. Keep target creation, source and successful submission mapping in the existing strategy transaction. Retry the same frozen request with the same UUID; creation never starts execution. Preserve source when an opportunity is handed off, and keep basic submission deduplication separate from similarity detection.
- Daily analysis keeps a re-raised opportunity's id, number and first-seen day by identity, by a matching `existingId`, or as the same thing in other words (`shared/strategy-pending.ts` `sameOpportunity`): the same cited signals and the same target, or the same title apart from digits. Signals alone never merge, since one digest signal can back different actions; a card whose latest copy was handed off is not reused. An undecided card stays pending for `opportunityKeepDays` (14) after the newest batch that raised it, counted from the latest analysis, unless a later card replaced it: the same opportunity, or the same target, raised again by a newer analysis, whatever was decided on that card. Restoring keeps a card pending. The Opportunities page and the menu count share `opportunityState`. An ignored opportunity keeps the changes it cites off Insights' to-do whichever analysis raised it (`signalDisposition`), since the analysis never raises it again. Every save of verdicts (the daily analysis, `reviewSignal`, `reviewSignals`) runs `settleVerdicts` (`verdict-coverage.ts`): a change judged `do` that no opportunity of the latest analysis cites becomes `skip` with the reason when a task (handed off from it, from an opportunity citing it, or about its page), a pending opportunity (citing it or about its page) or an ignored one covers it; otherwise an opportunity is written from the change (`confidence: verify`), reusing an earlier card for the same thing. Pages compare without scheme, `www.`, trailing slash, query or fragment. Reasons use the project's analysis language.

- The task page is written for the people who run marketing, on one skeleton for every state (`client/pages/task-detail/layout.tsx`, `styles.ts`): a two-line header (the title with its T-number in grey, the status Tag and the menu; then one grey line with the playbook's steps and where the task stands now), then on the left the card for what to do now (`StageCard`; only its content changes between states, and the effect shows there once live) and the activity card with the one-line message to the Agent, and on the right, always in this order, ✦ Why (the reason and View evidence; Why this change while a change waits for review), Properties and Performance. Below 1280px the columns become one: Why, Properties, now, Performance, Activity. The page uses four text styles only (`text.title`, `text.cardTitle`, `text.body`, `text.muted`; labels are `text.muted`), every card is the shared `Card` with the same radius, padding and spacing, and a card holds a single level of boxes: fields and controls, never another bordered or shaded box (diffs, before/after tables, warnings and reply drafts are drawn with rules and tints). Do not add another size, weight or shade, or a card of a different shape. Once live, the card names what changed in one line (`LiveChange`: the article's changed fields or the page change's visible changes) and opens that version's change on demand; the activity's View opens the same (`VersionChange`), with an article compared field by field against the version it was written from (`ArticleReview` with `settled`, which leaves out review-time conflicts). Keep pull requests, branches, file paths, check output, Runner/model details and error codes off it. They belong in the Technical details dialog (`?details=result|runs`), which reuses official `RunHeader` / `RunTranscript`; `?run=` selects a historical run and opens that dialog on its runs. Only participants and administrators may read transcripts. Show the actual model/Runner, tool inputs/outputs, and permission denials there. Business failures take precedence over tool-turn completion. A failed run's card (`failureOf` in `client/pages/task-detail.tsx`) explains the official `failureReason` in plain words and may name the computer and the coding tool from the run's latest execution snapshot when the failure is about them (sign-in, connection, network, quota), never a machine hidden from the reader; the tool's own `failureDetail` goes to Technical details only, for those who may inspect the run. Where trying again cannot help (sign-in, setup, model), Try again stays available but is not the primary action. The card is an error notice (`StageCard` with `error`) whose other actions are Switch Agent (opens the Agent picker in Properties) and Message the Agent (focuses the composer), shared through the `TaskActions` context; completing the step by hand is in the ⋯ menu, never on the card. Copy never points at a position (above, below, top right): it names the card or field, because the columns reflow below 1280px. The Why card reads `evidence.why` first (plain text, at most 300 characters; hand-off drafts send it as `why`, else the opportunity's `reason` is kept), then falls back as `whyText` in `task-detail/evidence-model.ts` lists, ending with `firstSentence` of the objective or brief. A run with `restartedAt` says NocoReach was updating instead of naming the computer, and is left out of the card's failures in a row; a run with `autoRetry` says it started again after the update, and Technical details › Runs gives the restart time and the official reason.
- Validate `report.kind` separately for research, community replies, and content results. Preserve `sources`, `asOf`, and `uncertainties` before human review. `report.asOf` allows up to 1000 characters; do not truncate timing notes covering multiple sources. Instructions and validation share the limit, and oversized-result errors identify the field and limit.
- `task result --content-file result.json` uses the existing `nocoreach.tasks/propose` capability. It validates and stores one immutable result per business run; identical submissions are idempotent. Corrections happen before acceptance, with at most two correction retries instructed to the Agent. The official completed event consumes this snapshot; cancellation/failure never consumes it. The final summary remains a fallback for Agents without the command. Do not add a second executor, change plugin-owned run storage or parse arbitrary prose for JSON.

The compatibility parser removes only the exact `Local continuation saved: <path> (<40-hex commit>); not pushed.` footer; retain the original official summary for diagnostics.

Read official completion outside the business transaction, then recheck owner/admin authorization, actor/owner eligibility, cancellation, current stage/artifact, and absence of active work inside it. ### Article publishing

See [ARTICLE-PUBLISHING.md](ARTICLE-PUBLISHING.md) for the model, states and limits, and [ARTICLE-API.md](ARTICLE-API.md) for the `http` protocol.

- Publishing targets are per-project settings sealed in `nrVariables` (`server/nocoreach/articles/targets.ts`); credentials never reach the browser or the Runner, and changing a target's address or repository requires its key again. Saves need the browser confirmation session, like collector credentials. Validate the complete settings before persisting them, including the ten-target limit, so rejected additions leave existing settings readable. Editing a target keeps its position; `defaultTargetId` (`setDefaultTarget`, cleared when that target is removed) decides which target a new task starts with, falling back to the first. `playbookTargets` (`savePlaybookTargets`) overrides it per playbook with a target id or `'repo'`; removing a target drops the entries naming it, and no new target may take the id `repo`.
- A task's delivery is frozen at start in `work.delivery`. Article change steps run in mode `article` without a repository; the source article is an immutable snapshot delivered as the `article.json` material, and the proposal is validated against the target both by `task result` and on acceptance. Keep target I/O (link, the slug lookup in other targets at start, rebase, publish, export and drift checks) outside business transactions and recheck state under the task lock before recording an outcome. A release to several targets keeps one record per target and derives `release.state` from them; touch a record's state only through the leg helpers in `article-flow.ts` (`legsOf`, `stateOf`, `settle`) so single-target releases from before keep working.
- Publishing writes only the approved artifact's changed fields, adopts a write that already landed, treats a field both sides changed as a conflict, and blocks on a Git-only edit when the target exports to Git. Never publish from a later draft than the approved artifact, and never mark a release live from a CMS save alone: export and page checks are separate states.
- A failed publish says where it stopped and why (`PublishFailure` in `delivery.ts`, recorded on the leg by `article-flow.ts` and logged at warn level). The detail comes from `errorDetail()` in `provider.ts`: an `ArticleError`'s own message, the network layer's code, reason and host, or another error's name and message, one line, clipped and with credentials masked. Provider catches of a request that got no answer keep the transport error as the cause (`unreachable()`); do not drop it with a bare `catch`. The task card keeps the plain-words reason; step, code and detail appear in Technical details only.
- `nocobase-api` is check-before-write and cannot prevent a stale editor form from overwriting a publish; the overwrite watch only reports it. Do not describe it as guaranteed. Build changes to files a target's exporter owns are blocked (`pr.protected`).
- Export and overwrite checks compare every written field against the approved artifact, including its normalized publication status. Manual draft edits preserve the existing draft status when editing content fields. New articles on a target that stores a status default to `draft` on the server; publishing one directly is an explicit choice in the editor. Omitting status from that baseline falsely reports a new draft as overwritten.

### Continuous integration

- `.github/workflows/ci.yml` runs independent `tests` and `build` checks on pull requests, `main` pushes, and manual runs using Ubuntu 24.04, Node 24, and the pnpm version in `packageManager`. Wait for the next second before booting again, as `schedule-timezone-app.test.ts` does. Await asynchronous permission or effect checks with `waitFor` rather than asserting right after the first render; the deploy workflow runs the suite again on a slower runner.

It calls the target application's `nrImport` actions over HTTP with a root user's `NOCOREACH_API_KEY`, rather than connecting directly to Studio's database. Import is a separate data migration task, not a routine deployment step; consult the [port record](PORT-PLAN.md) before proceeding.

While an import writes, `ImportHold` (`server/nocoreach/legacy/app.ts`) keeps NocoReach's background work off the data, which would otherwise act on a project as soon as its snapshot lands. Every `nrImport` call except `plan` takes or renews a five-minute lease at its start and end; `finish`, or a `begin` that fails, releases it, so a CLI that dies midway lets the timers run again five minutes after its last call. The provider runs each timer firing through `LegacyApp.tick()`, which skips (does not queue) a firing while held; the Scheduler's daily analysis firing completes as `cancelled`, and the minute timer catches the day up afterwards. `begin` waits up to 30 seconds for work already running before it clears or writes anything, and answers 409 otherwise: timer firings, the analysis job, and the run `DailyAnalysis.start()` leaves in the background, all registered with `importHold.track()`. Register any new background work that outlives the tick or request that started it the same way, or `begin --replace` can clear tables under it. The hold is in memory and assumes NocoReach and its timers run in one process, as on Studio; requests people make in the application during an import are not held.
