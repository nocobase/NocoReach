# NocoReach 内容优化开发计划

更新：2026-09-30。本文是当前开发入口，替代原 M0–M5 实施顺序。产品方向来自本轮讨论；阶段拆分、四列看板和具体交互为本计划建议，随首个切片细化。第一阶段现已实现并部署到本地，真实业务验收待合法测试身份；详细状态见 [第一阶段交付记录](../S1-DELIVERY.md)。第二至第四阶段尚未开始。

## 开发结论

在现有产品基础上修改。保留 NocoBase 3、Portal、连接插件和现有数据；重点重做任务体验、收敛导航，并补上本地 Agent 到内容仓库的执行链路。当前没有证据需要更换技术栈或另起应用。

产品定位：面向官网与博客运营者的 AI 内容优化工作台，根据网站表现确定值得优先优化的内容，协助修改，并跟踪效果。

第一条验收路径：已有博客的数据与建议 → 讨论确认修改范围 → 本地 Agent 修改仓库 → 查看差异和预览 → 确认发布 → 回看表现。内容撰写、官网调整和市场调研沿用这套工作组织方式，不强制经过相同的创作节点。

## 现有能力如何处理

以下根据源码入口及已有验收记录核对，不代表本轮重新运行测试。

| 能力与源码入口 | 处理方式 | 已知限制 |
| --- | --- | --- |
| Google 接入、analytics.ts、period.ts、sync-data.js | 复用授权、同步、指标与周期逻辑 | 数据覆盖、同步延迟和宿主稳定性欠项继续保留 |
| strategy 目录、strategy-service.js、opportunity-board.js | 复用洞察、冻结证据、讨论与确认任务 | 建议质量及机会到任务的完整真实回归仍需验证 |

| task-work.tsx、task-execution-panels.tsx、任务看板 | 重做用户交互，保留可用页框、差异与历史组件 | 当前方案与逐步审核表单过重，看板缺少拖动 |

M0 的组件与契约试验作为技术材料保留。M1 的代码复用和产品体验验收分别处理：技术实现有价值，不代表六阶段体验符合需求。旧 M1 不因计划改版而标记通过，也不要求先把旧流程全部做完再转向新流程。

## 首版范围

主要入口收敛为概览、优化工作、内容；连接、仓库与 Agent 配置进入设置。原分析页可从指标或页面详情深入查看，机会库作为概览下的历史入口，旧路由继续可访问。

概览呈现网站表现和少量有依据的优化建议。优化工作承接讨论、执行、预览及确认。内容仅索引线上页面、对应仓库文件、数据与修改记录，正文以仓库为准，不另存可独立编辑的正文副本；审核所需的不可变快照可以保留。

暂不建设完整 CMS、独立项目管理、通用工作流编辑器、独立收件箱、多 Agent 调度平台、多渠道发布和 OpenSEO 全套页面。已有能力保留并调整入口，不删除历史数据。第一版仍服务当前单项目试用，面向其他团队前另行完成初始化和权限隔离。

## 第一阶段 收敛页面和工作方式

复用现有路由、数据页面、机会讨论和任务模型，完成三个入口的导航与信息层级。简化任务详情为目标与依据、讨论、当前结果和下一步操作；执行日志、技术信息、版本历史按需展开。简单修改确认范围后即可执行，不强迫填写多步方案和逐步审核表单；复杂长文允许按需确认提纲或初稿。

建议看板使用待处理、进行中、待确认、已完成四列，并支持列内排序和符合条件的跨列拖动；同时提供菜单操作，兼顾键盘与窄屏。任务业务状态与 Agent 排队、运行、离线、失败状态分开。

拖动是实际持久化操作，不是纯视觉移动。待处理与进行中的移动不自动启动 Agent；进入待确认需要有可查看的成果。拖到已完成时打开必要的完成确认：发布类工作须具备发布回执，调研类可确认成果后结束。缺条件时说明原因并恢复原位置，不能通过拖动伪造发布或审核。效果观察独立于任务完成状态，不要求等到指标上涨才能完成。

本阶段同时落实最小内容索引：可从已有页面数据选择 URL，展示表现和关联工作；支持人工确认仓库相对路径。无数据的仓库内容明确标注，未知路径留空，重复 URL、重定向与一页多文件不擅自猜测。首次选定一个目标网站，不开发通用内容爬虫。

退出条件：旧机会、任务和证据仍可查看；四列可拖动、排序刷新恢复、保存失败回退；内容可关联优化工作；菜单及旧路由正常；用户能在页面内理解下一步，无须理解 Run 或执行协议。以真实宿主验证，组件预览不能代替业务验收。

## 第二阶段 跑通一篇博客的仓库修改

复用 M1 的运行与成果记录，增加一个本地 Agent 适配器。先确定当前实际使用的 Agent、目标内容仓库、博客格式、构建命令和现有预览部署方式，只实现这一种组合。

用户确认修改范围后，系统把页面、相关文件、数据证据与修改要求交给 Agent。在线 AI 负责现有数据分析与讨论，本地 Agent 负责读取仓库、改文件、运行必要检查；界面按能力选择可用执行方式，缺少 Agent 时提示连接，不要求用户理解员工与运行时结构。

Agent 在隔离分支或 worktree 修改，保留用户未提交内容；回传任务 ID、运行 ID、基础提交、修改摘要、差异、检查结果和当前提交。首次接入先在合成内容或明确指定的测试分支验证，再用于真实博客。

默认推送分支并创建 PR。PR 创建、推送响应未知时先查询已有结果，重连和重试不能重复创建 PR 或覆盖人工提交。Agent 离线、权限不足、冲突和失败都保留进度及原因。未接入时不展示假执行成功。

退出条件：在目标测试路径真实完成任务 → Agent 接单 → 文件修改 → 必要检查 → 推送分支及 PR → 系统显示差异与预览入口；刷新、断连恢复和人工改动冲突有明确结果。缺少预览设施时需在本阶段确定并补齐一个可用方案，不把 diff 当作页面预览。

## 第三阶段 确认发布和回看效果

复用网站现有 Git 发布方式，只接入一个渠道。NocoReach 展示 PR、内容差异、预览与检查结果，用户在此确认发布。授权绑定仓库、目标分支和确切提交；确认后产生新提交必须重新审阅。

发布前重新核对 PR 当前提交与必要检查，优先使用仓库平台支持的提交匹配约束防止并发变更。合并成功与部署成功分别记录；线上确认来自部署回执及目标页面核查。超时或状态未知先核对，不能把 PR 合并直接标成已上线，也不自动重复外部写入。需要回滚时提供关联提交与可审核的回退路径。

内容索引关联实际上线时间、提交、工作与页面指标。保存修改前基线，按可用完整日做等长周期比较；建议观察 7／28 天，但数据不足时延长或显示继续观察。首版支持用户主动刷新和回看，后台定时复查后续再做。记录同期其他修改和数据缺口，不将波动直接判成修改效果。

退出条件：用户从同一工作页完成预览、确认与发布状态核查；失败、未知、已合并未部署状态真实；能回看修改记录、基线和后续数据。以一篇真实博客完成端到端验收，数据尚不足时只能验收记录与观察能力，不能宣称增长已验证。

## 第四阶段 根据使用结果扩展

先将同一链路用于新文章、官网文案及页面调整，调研任务允许以报告完成。遇到真实的关键词或 SERP 研究需求，再按既有费用授权与缓存规则适配 OpenSEO 页面。

持续观察、自动复查、提醒、更多内容格式和团队使用分别排期。通过建议采纳、实际修改、用户重复使用和节省时间判断优先级；试用其他团队前补干净环境初始化、合法身份和成员／项目隔离。暂不承诺自动化增长效果或通用 SaaS 能力。

## 数据兼容与实施顺序

先建立旧状态到新看板的只读映射：方案待确认映射待处理，待推进映射进行中，成果待审核或待人工执行确认映射待确认，旧待验证记录具有实际执行证据时映射已完成并保留待观察标记，缺少执行证据时映射待确认并显示待核对；旧已完成任务保留历史完成标记，不补写虚构回执。旧记录的原始 stage、方案、成果与证据完整保留；最终映射用代表性旧记录核对。

新工作状态独立承接业务交互，不只更名六个阶段，也不依赖强制逐步骤推进。存储先评估 nrTasks 与已有 snapshot 的扩展，沿用 revision、请求幂等及不可变成果，避免并行创建第二套任务系统。

每一阶段按源码修改、针对性测试、构建、目标宿主部署、真实浏览器验收顺序交付。发布前记录源码版本和产物标识，发布后核对实际加载版本并执行刷新验证，避免再次出现本地改了但用户仍看到旧版。旧数据兼容及 Google 核心读取作为受影响回归范围。Git 提交、推送、部署和业务验收分别记录。

第一阶段开始前完成现有未提交改动的文件清单与基线记录；不得把其他工作或敏感资料一并提交。现有合法测试身份问题、Docker 稳定性和 M1 在线适配真实性需要在依赖它们的阶段解决，不能靠单元测试代替。开发文档不要求重置数据库或迁移运行目录。

## 首个开发切片

先实现第一阶段，不同时移植 OpenSEO 或搭建通用 Agent 平台。工作顺序：核对旧记录映射及页面结构 → 收敛导航与详情 → 实现看板拖动和持久化 → 最小内容关联 → 真实回归与发布。需要的目标仓库、内容格式、Agent 和预览方式在第二阶段接入前从现有配置核对，缺失时再向用户确认。

本计划不提供未经实现评估的工期承诺。每阶段满足退出条件后再进入下一阶段；第一至第三阶段合起来才是首个完整产品闭环。

#### 3. 在线与本地执行的分工

执行位置由步骤的工具、资源和持续运行需求决定，不按“写作／编码”的职业名称授予权限。

| 工作 | 默认执行方式 | 交付与授权 |
| --- | --- | --- |
| 数据解读、机会讨论、行动方案 | 在线 AI 员工 | 引用已授权来源，方案经人确认 |
| 提纲、稿件、文案修订 | 在线 AI 员工 | 资料齐备时产出待审版本；保留人工编辑 |
| 浏览器调研、复杂文件及素材处理 | 本地 Agent，或已具备相同工具的在线执行者 | 明确访问资源及输出附件，回传证据 |
| 官网／文档仓库修改、预览、测试 | 本地 Agent | 指定仓库、隔离目录、变更对比和测试结果 |
| CMS 发布／外部写入 | 受控连接器，必要时本地 Agent | 最终版本、目的地和授权绑定；未知结果先核对 |
| 数据同步、缓存、状态转换 | 确定性后端服务 | 不交给模型决定事务与权限 |
| 后续效果分析 | 持久调度＋在线 AI 员工 | 数据足够才评价，缺失继续观察 |

本地运行时可以在个人电脑或团队服务器上。任务选择可用执行者，步骤可交接；一次 Run 固定执行者及授权范围。离线、能力不足或需要额外工具时明确等待或交回人，不偷偷切换执行位置或扩大权限。

#### 4. 统一业务与执行契约

业务任务、步骤、Run、成果版本、审核决定、发布记录分别追踪。概念拆分不代表全部立即新建独立集合；准备阶段确定可兼容存储与必要新表，运行事件等增长数据不持续堆入 task JSON。

- 真人负责人承担审核责任；执行者可以是人、在线 AI 员工或本地 Agent。
- Run 至少关联项目、任务、步骤、授权人、负责人、执行者／运行环境、输入证据及方案版本、触发原因、幂等键、状态、时间、错误和结果引用。
- 唯一触发入口检查方案／步骤授权后创建 Run；模型输出、普通 Agent 评论和客户端刷新不能自行创建后继运行。
- 在线执行与本地执行共用业务结果契约：成功产出、失败、取消、等待人处理。长任务需后端持久执行，不能依赖浏览器保持打开。准备阶段验证在线服务调用与会话归属；不直接改造原机会聊天为后台任务。
- 本地协议覆盖认领、续租、开始、事件、成果提交、完成、失败、取消与版本协商。失效租约、重复事件和过期 Run 的回传不可覆盖新结果。
- Run 成功不自动批准成果。审核指向确切成果版本；人工修改后旧批准失效；并发编辑、打回和重跑保留历史。
- 保留目前六列任务视图的业务含义：待确认方案、待推进、待审核、待执行、待验证、已完成。Run 的排队／运行／失败作为独立信号。具体内部状态映射先出契约，不能复制 NocoProject 的“交付验收即 done”。
- 发布成功必须有真实回执或明确标记的人工记录；成果导出、PR 创建及稿件审核均不等于发布。内容发布也不直接代表增长目标完成。

#### 5. UI 对齐范围

优先形成共用 PageContainer、PageHeader、工具栏、状态标签、执行者头像、空态及失败态，再用于业务页面。默认紧凑密度，验证紧凑／宽松和浅／深四种组合；筛选、视图与详情状态可在 URL 中恢复。

任务详情采用导航＋主内容＋属性右栏：主内容按目标与证据、等我决定、方案及成果、活动时间线组织；右栏放负责人、执行者、状态、运行记录和用量。整页滚动，右栏在可容纳时吸顶，窄屏折为单列。审核完整展示内容与修改对比，按钮紧邻被审核对象。

收件箱采用 NocoProject 的列表／详情结构，待我决定与通知分开，待决定数显示在侧栏；任务详情使用同一份决定对象与动作，防止两处各自审核。新增入口仅在实际可用时开放。

目标导航：个人入口（收件箱、我的任务）→ 洞察与内容工作（发现机会、机会库、任务）→ 现有分析与关键词研究 → Agent 团队 → 报表与设置。保留 /home 的发现机会首页，收件箱可用后置于侧栏首项；第一阶段保留现有导航。没有能力的技能、知识库或运行时管理入口不展示空壳。

OpenSEO 只贡献研究布局与交互，按钮、表格、色彩和密度统一到上述组件体系；避免保留两套主题。旧入口兼容，任务拖动若后续开放仍必须经过状态和审核门禁。

#### 6. 里程碑与退出条件

每个阶段都交付可演示的工作流程及对应验证。不预设日历工期；完成准备阶段的适配验证后再估算，遇到阻碍记录依赖，不虚报完成比例。

##### M0 开发准备和适配验证

1. 盘点当前未提交的源码和文档，按已有功能建立可评审基线清单；不清理或覆盖用户改动，不整体上传工作区。提交、GitHub 推送、部署各自记录真实结果。
2. 核对宿主版本、数据库、现有构建与必要回归，记录 Docker 稳定性问题；离线开发可继续，真实环境验收必须具备可用宿主。
3. 固定三个参考仓库的版本和复用文件，核对依赖／归属。OpenSEO 保留 MIT 声明；NocoProject 内部源码复用记录上游，发布前明确其 CLI 当前 UNLICENSED 元数据的授权归属。
4. 编写任务／Run／审核最小契约和旧数据映射；验证一个详情布局组件在 Portal 可用、一个 echo 执行载荷能按适配契约往返。不注册真实机器或操作生产仓库。

退出条件：有依赖对照、状态及接口契约、旧数据兼容办法、构建接入证据和演示验证记录；未解决问题带具体后续任务。2026-09-30：PREP-01～04 本地验证已完成，见 [M0 验收与接续任务](../m0/README.md)；真实业务接入仍属于 M1/M2。

##### M1 在线方案到成果审核与统一任务 UI

2026-09-30：源码与本地验证完成，真实宿主验收待可用测试身份，M1 尚未关闭。详见 [M1 记录](../m1/README.md)。

复用现有 task-work、方案和成果存储；补负责人／执行者语义、独立执行记录和按版本审核，迁入 NocoProject 风格的看板与详情。在线 AI 完成一个文本步骤并产生待审成果；最小时间线记录生成、人工修改、审核及打回。

退出条件：一条已有机会确认任务 → 在线方案 → 人确认 → 文本成果 → 人工编辑审核 → 打回再生成完整通过；刷新恢复，失败不丢稿，重复请求不重复运行，旧任务可打开，四种主题和窄屏可用。不做全站视觉翻新。

##### M2 本地 Agent 接单与交付

在 M0 契约和 M1 审核基础上适配 NocoProject daemon／运行服务。先支持一个已验证工具适配器，建议 Codex CLI；先 echo 再在明确指定的测试目录跑真实任务。交付机器连接与在线状态、能力匹配、执行记录、停止／失败恢复、附件或变更对比回传。

首个真实场景：已确认内容要求 → 本地 Agent 修改测试内容仓库 → 运行验证 → 回传稿件、diff 和预览材料 → 人审核或打回。首版无需真实外部发布即可验收执行闭环。

退出条件：断开电脑、续租失效、重复回传、过期回传、取消后迟到结果、权限撤销和版本不兼容均有正确行为；本次成果只进入待审核。机器凭证与任务授权分开，不能照搬关闭沙箱的启动配置而声称完成运行隔离；采用受控测试账户／目录验证，外部服务凭据不进入简报或日志。

##### M3 OpenSEO 研究到行动任务

复用关键词研究结果表格、SERP 详情、候选标签／批量保存／导出，继续使用现有 DataForSEO 后端与费用门禁。候选携带地区、语言、时间、研究条件和原始来源进入机会讨论，经人确认形成任务，接 M1／M2。

退出条件：已有结果查询、筛选、详情、保存、刷新与候选到任务闭环通过；浏览缓存不收费，额外 SERP 获取需明确确认，unknown 不自动重试。先使用脱敏测试数据验证；真实付费查询在给出条件和费用并获得授权后验收，未验证部分保持欠项。

M3 在 M0 及 M1 共用组件稳定后可独立推进；主线优先保证 M2 本地执行闭环，不以研究 UI 完成替代执行接入。

##### M4 收件箱与发布闭环

将方案待审、成果待审、运行失败／受阻、发布待确认汇入同一收件箱；收件箱和任务详情共用审核动作。扩充项目背景中的写作偏好和重点内容页；沿用独立行动目标。

选择一个真实发布渠道接入：如内容仓库或 CMS。发布确认必须绑定内容版本、目标及操作范围；人工发布回填路径保留。回执、失败和未知结果分别展示。

退出条件：收件箱完整查看材料并批准／打回，双入口重复决定幂等、旧版本批准失效；发布成功可追溯，未知结果先核对而不自动重发。准备发布材料与实际外部写入分别验收。

##### M5 持续观察与团队使用

补后端调度、暂停恢复、机会去重、效果复查和反馈沿用；规则由人配置并记录授权，数据更新不自动授权创作或发布。补齐新项目初始化及同一组织内多项目／成员权限，逐步扩展至团队使用。

退出条件：浏览器关闭后调度仍有效，服务重启可恢复，无可行动变化不生成重复待办；样本不足不输出效果结论；跨项目与角色权限验证通过，干净测试环境能够初始化。既有 Google 历史回补、公开来源覆盖及 Docker 稳定性欠项单独验收。

#### 8. 跨阶段验收与后续范围

共用门槛：后端权限与状态测试，任务／Run 的并发幂等与故障恢复测试，成果版本及人工编辑保护，实际浏览器路径、四种主题和窄屏检查。改变技能、提示词或模型时，用可公开或脱敏的固定样例检查事实引用、输出结构、人工修改尊重和越权拒绝，评测与技能一同维护。

观察六类指标：使用、AI 承担、建议接受与修改、可靠性、成本、人的待办负担。首版先保存必要事件与用量，仪表盘后续完善，不用未经测量的完成率证明价值。

域名分析、独立排名跟踪、完整网站审计、AI 可见性、外链、多 Agent 自动委派、多渠道发布和通用流程编辑器不进入首个闭环。数据同步可用与外部研究完整验收仍是后续扩展的前置条件。
