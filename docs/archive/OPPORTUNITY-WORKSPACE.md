# 发现机会与机会库设计

更新：2026-09-28。继承 SPEC，在既有 Portal、策略记录、讨论和任务基础上增量实现。本版替代“本次观察／优先关注／浏览更多机会”的首页结构。

## 首页的核心体验

用户进入后能够回答：发生了什么、为什么值得关注、有什么依据、下一步能做什么。不先要求统一目标，目标在具体机会讨论和行动中澄清。

首页仅有“重点发现”和“值得继续观察”两组。取消孤立的来源摘要和重复机会库的列表筛选，保留“查看全部机会”入口。每组最多展示六条精选，不保证填满；暂无可靠发现时明确说明，不编造机会。旧版分析仅保留在机会库，需要按新口径重新分析后进入首页。

每张卡片包含：

- 具体变化或问题，以及可能含义；事实、推断分别表达。
- 具体行动或验证建议，与观察相互对应。
- 实际来源、证据日期、比较口径和限制，点击展开查看。
- 优先级与理由、生命周期、证据更新时间和建议复查时间。
- 主操作进入独立讨论页，辅助操作持续观察、忽略；全部状态管理在机会库。

证据充分、未过复查期的机会进入重点发现；待验证、人工关注及超过复查期的记录进入继续观察。人工关注不会被 AI 覆盖。高优先级不等于高可信度；AI 判断不等于收益保证。

## 观察周期与数据时间

首页提供最近 7／28／90 天，默认 28 天；按自然日取窗，与紧邻前一个等长周期比较。切换只查看对应周期已保存结果，点击更新机会才进行新分析，避免切换就发起模型请求。全部周期共享机会身份、人工反馈、讨论与任务。

Google 分析以实际同步截止日为准，当前同步仍保留三天延迟；有两种来源时使用共同截止日。前后两窗覆盖均完整、指标均有值才输出变化；前期为零不输出百分比。少一天也标记不足，不把缺失日当作零，不拿最近若干条记录代替完整日窗口。查询和页面仍为截断样本，不能据此断言全站变化。

GitHub Star 使用实际采样日期作为自身截止日；官网正文和关键词资料标注采集时间，不冒充周期指标。各来源时间不同，不推断因果。分析时冻结证据快照，保存时沿用同一份依据。

## GitHub 的市场视角

主要关注 Star 净变化、仓库浏览量、GitHub 到官网的流量与关键事件。官网渠道来自 GA4 每日来源分区，和仓库自身的入站来源不同。关键事件不是成交，渠道归因不证明增长原因。

当前公开连接能读取 Star 总量。每次成功保存或刷新保留按日采样，只有观察窗两端日期都有实际采样才计算净变化；不是新增 Star 总数，不反推旧历史。暂未启用每日自动采样。

仓库浏览量需仓库权限，当前公开连接未授权；明确显示不可用，不用 Star、Issues 或 Releases 替代。Issues／Releases 继续保留为连接资料，但不作为首页模型的主要市场依据。GitHub Traffic 授权接入及短期数据持续归档列入后续切片；官方接口窗口不等于任意 90 天历史。

## 机会库和生命周期

机会库为全量列表，保留搜索、来源／类型／优先级筛选及排序分页。视图包括待处理、讨论中、持续观察、已转任务、已暂缓、已忽略、全部。列表显示首次发现、最近证据更新、观察窗口、建议复查日期。任务状态由真实任务关联推导。

生命周期为短期窗口、持续机会、观察信号；目前短期和观察信号建议七天复查，持续机会二十八天复查，属于复查建议而非收益预测或有效期保证。超过复查时间显示待重新评估，不删除或自动执行。后台复查、自动唤醒未启用。

新分析保留旧批次，人工优先级与状态独立保存。精确身份匹配继续复用；模型可引用已有编号，服务端校验目标、对象和受众后沿用，不以日期或周期新建身份。未识别到引用或语义变化较大时仍可能产生重复，语义查重和人工合并后续实现。旧记录不自动删除。讨论沿用稳定编号，任务保留确认时依据。

## 实现边界

每轮输出 0–12 条机会，保留逐来源审阅供审计，但不再作为孤立首页模块。来源 ID 按实际提供的证据过滤。当前仍为管理员单项目试运行；历史在原策略记录保存，规模增长后需独立集合与服务端分页。没有自动后台分析、自动执行或发布。
