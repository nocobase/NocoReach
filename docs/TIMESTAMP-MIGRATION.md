# 任务时间修复与历史数据转换

PM-375 修复任务列表和看板将缺失时区的更新时间误读为浏览器本地时间的问题。两处继续显示 `updatedAt`，保留原有分钟、小时四舍五入及日期展示规则。无法确定的时间显示空白，不猜测时区。

新增迁移 `202610140002_absolute_business_timestamps` 将原八张业务表及 YouTube、任务媒体的 `createdAt` / `updatedAt` 改为 `datetimeTz`。媒体 `expiresAt` 成组改型，使上传有效期、读取判断与后台清理保持同一绝对时间语义。原可空性、主键、唯一约束与索引不变。分区业务日期、其他字符串日期列、JSON 内部时间与第三方数据不在此迁移范围。

本实现支持 SQLite 和 Postgres。Postgres 部署必须已按应用文档安装官方 `@nocobase/db-postgres` 驱动并将其包含在发布产物中；不能只改运行配置引入未安装的驱动。其他方言在转换前失败，不在本次实现范围。线上数据库方言和 T-16 原始证据仍由有权维护者确认；隔离测试不代表线上根因已闭环。

## 时间契约

字段名不变，不新增业务协议字段或每行状态。合法时间统一输出 `YYYY-MM-DDTHH:mm:ss.sssZ`；输入接受有效 Date、epoch 毫秒以及带 Z / 显式偏移的时间。可空列的 null 保持 null。普通创建未提供时间时使用服务端当前时间，更新刷新 updatedAt。

无偏移时间、非法日期、空字符串和未知偏移 `-00:00` 不进入普通写入或导入。导入缺失的可空时间明确保留 null，不再静默伪造“现在”；非法值报错。需要恢复缺失历史时间时应核实来源再提供正确的绝对时间。

## 停写、备份和预检

本仓库 [deploy-studio.yml](../.github/workflows/deploy-studio.yml) 在 main push 后自动构建并部署，新版本首次启动自动执行迁移。默认把 **合并本身安排在准备好的维护窗口**，不能先合并再准备数据。工作流声明了 `environment: studio` 不证明已经配置有效审批；只有维护者实际核实并记录环境/Studio 审批确实能在部署前阻断时，才允许采用“先合并、后审批放行”的替代顺序。

1. 合并前完成代码评审，确认目标部署、实际方言、官方驱动版本、历史来源与可用恢复版本。固定候选提交及构建产物，先在独立副本演练；准备维护窗口并阻止其他 main 推送触发并行发布。本说明不代表已经更改任何线上门禁。
2. 在合并前进入维护窗口，停止应用、后台任务、旧系统导入、外部数据库写入者和自动重启/扩容；确认连接不再写入。核对旧版本迁移已全部完成；每个迁移独立提交，本迁移失败不会撤销更早迁移。新旧实例不得滚动混用旧 schema。
3. 停写后取得最终一致备份：SQLite 通过备份接口，或关闭所有连接后复制完整数据库，WAL 模式不能只复制正在使用的主文件；Postgres 使用 `pg_dump` 一致快照并演练恢复到独立空库，保留角色/扩展等必要前提。保存匹配旧应用版本、部署配置、完整库及校验值，验证 schema、原始时间及迁移历史。不要将完整库、凭据或业务正文上传 issue。
4. 以最终备份的独立副本运行候选版本 CLI 预检、转换、恢复与重试，确认全部逐字段来源映射匹配最终原值，不能只复用停写前的抽样结果。副本使用独立数据库、存储与禁用业务服务的 CLI，不启动后台写入者。保留原始 ID/字段/时间、来源证明、配置校验值、预检输出和前后 epoch 校验汇总；未知来源继续阻断。
5. 合并前通过部署现有配置管理，把下面的 `nocoreach.timeMigration` 合并进目标完整运行配置；保留其余配置，不用示例覆盖整份配置。配置通过持久挂载的 `config.yml` 或既有 `APP_CONFIG_FILE` 绝对路径在**新进程首次启动前**可读，不提交到仓库或打进公开产物。确认新旧发布读取的实际路径、文件权限、挂载和来源清单校验值；副本使用同一配置装载方式验证，不能等应用启动后再通过业务 API 写入映射。如现有托管部署不支持预置该文件，先由有权维护者完成配置交付机制，保持未合并，不能假设上传产物会自动携带运行配置。
6. 副本预检通过后，准备生产配置 `preflightOnly: false`，确认停写、最终备份、恢复步骤和首次启动配置均就绪，才在窗口内合并/放行已核实的审批门禁。启动迁移仍会再次预检原值，数据与 schema 同事务提交。也可由维护者在停写期间用同一候选产物手工执行迁移再启动，迁移完成记录使启动跳过。只有确认全部迁移成功、绝对时间/API/媒体清理和任务列表看板验收通过，才恢复写入与定时服务。

未知来源导致启动失败不能作为发布门禁。不能只关自动迁移却让新 legacy 代码读取旧 schema。失败时保持停写、停止新进程及自动重试，核查迁移历史与完整 schema；本迁移事务回滚不代表更早迁移回滚。需要回退时先恢复最终备份和匹配旧版本/配置，再启动旧版并验证后开放写入，不能先运行旧版连接已经转换的库。

## 逐字段来源映射

`nocoreach.timeMigration.sources` 是一次性维护配置，不是业务记录状态。每项精确匹配表、行、字段及预期原值，必须有来源证明，且只选 `timeZone` 或 `instant` 之一。下面仅说明格式，不能作为线上映射：

```yaml
nocoreach:
  timeMigration:
    preflightOnly: true
    sources:
      - table: nrTasks
        id: '123'
        field: createdAt
        raw: '2026-10-14T13:00:00.000'
        timeZone: Asia/Shanghai
        evidence: '已核实的写入批次及服务端时区记录'
      - table: nrTasks
        id: '123'
        field: updatedAt
        raw: '2026-10-14T16:00:00.000'
        instant: '2026-10-14T05:00:00.000Z'
        evidence: '源库原始绝对时间与导入批次对照记录'
```

createdAt、updatedAt 和媒体 expiresAt 分别归属。不同部署、时期、导入批次逐字段展开，不提供整表默认时区。当前 TZ 不代表历史来源。已有正确偏移、epoch 毫秒或合法 null 按原瞬间保真，不按映射再次移动时间；SQLite 历史数字毫秒字符串也保留 epoch。Postgres 的原列为原生 timestamp(3)，已写入无时区列的原偏移无法从目标恢复，必须提供来源；已有 timestamptz 列保留其存储瞬间。Postgres 映射的 `raw` 使用本迁移在事务内 `TimeZone=UTC`、`DateStyle=ISO,YMD` 下 `列::text` 的输出，可能是空格、无 `.000` 或 `+00`，须精确匹配，不能直接照抄 SQLite 示例。预检错误本身不回显原值，维护者用同样会话设置对必要 ID/时间列作只读投影取得原值。

无偏移墙上时间使用对应日期的 IANA 时区规则。墨尔本夏令时重复时间和不存在时间拒绝转换；取得原始绝对瞬间证据后可提供 instant。非法原值即使有映射也拒绝。源库曾被错误解码或重复导入时，对照源列类型、原始备份和导入记录，不能仅凭目标墙上时间反推。

在已停写的副本配置好来源后运行：

```bash
pnpm nocobase db apply --connection main --json
```

`preflightOnly: true` 故意以“preflight succeeded; no changes made”错误结束，携带仅含 ID、字段、原始时间、目标绝对时间和来源说明的审计清单。不修改目标数据或 schema，不记录本迁移完成；框架仍使用原有历史/互斥机制，不要手改这些内部表。

未知来源、非法值、时区歧义、重复映射、预期原值不符或多余映射都会失败，明细只有表/行/字段和原因，不含任务正文或变量值。有未解决项就阻断整次转换。真正无法恢复来源时须另行评审未知时间语义，不能统一追加 Z、固定加减八小时或清空值。

保存并核对审计清单后，将 preflightOnly 改为 false，在同一停写库执行相同命令。迁移先完成整批预检，再在一个事务中合并更新需要转换的行并改型。SQL 由 QueryAdapter compile 生成命名映射，使用迁移自身事务连接执行原始值读写，避免 execute 和旧 datetime 编码/解码引入二次转换。SQLite 物理时间类型仍为 text。Postgres 在同一事务连接将投影显式转为 text，绕过 pg 的 Date 解码；转换后的 UTC 值先写回旧 timestamp 列，再在事务局部 UTC 设置下改为 timestamptz(3)，防止 DDL 用原会话时区再次移动瞬间。已有 timestamptz 正确瞬间不变；局部设置随事务结束恢复。成功后重跑跳过本迁移。保存审计副本后从活动配置移除一次性来源清单；回退/副本重演需要原清单，不能将它用于另一个已变化的库。

## 旧系统导入

CLI 对源库使用只读、可重复读快照，先检查全部时间，再开始清理/写入目标。Postgres 时间列必须明确为 timestamp 或 timestamptz；通过文本读取，避免 pg 隐式使用导入机时区构造 Date。timestamptz 在源会话按 UTC 带偏移输出。

源 Postgres 支持最多六位小数，导入边界将毫秒以下小数位**截断，不四舍五入**，然后按原偏移或已证明来源时区转换到现有毫秒 API。`.123456` 和 `.123000` 都输出 `.123`，`.000001` 输出 `.000`，`23:59:59.999999` 保持同一秒的 `.999`，不进位跨日期或 DST 边界。这是毫秒协议明确的精度损失（小于 1 ms），不是时区修正；原始微秒值保留在源库/备份，API 字段不变。无偏移微秒值仍须显式来源，DST 歧义/不存在时间仍拒绝，非法精度/日期仍报错。其他非 ISO DateStyle 和特殊 domain 类型尚未覆盖，不推定其兼容。

已核实同一来源时区的无偏移批次可使用：

```bash
pnpm nocobase app import-classic --to <目标地址> --source-time-zone Asia/Shanghai --dry-run
```

dry-run 同样检查全部时间。来源未知时拒绝，混合源库不能随意选一个参数，应先整理来源明确的批次或源绝对时间。传输仍用原字段，不增加 HTTP 行协议字段。源快照保持到上传结束，额外全量预检读取只发生在离线导入。

## 恢复与验收

- 本迁移不可逆，不能简单将 datetimeTz 改回 datetime。失败事务回滚，修正映射后重试，不修改迁移历史。
- 降级先停写，恢复维护窗口前一致备份、匹配旧应用版本和配置，核对 schema、迁移历史和原始时间。重新开放写入后不能直接覆盖新增数据，须另行处理增量。
- 验收 UTC、上海、墨尔本冬夏和 DST 边界下的数据库创建、重读、API、刷新、更新及相对时间。20 分钟前的新任务显示约 20 分钟前，更新显示近期。
- 本地数据库/备份恢复/浏览器测试位于 tests/nocoreach；线上 T-16 的原始 API、物理列、历史时区、源类型、双方时钟与维护窗口仍由授权维护者补充。

每请求、轮询及普通创建/更新新增查询、写入、锁和事务均为 0，校验仅在内存执行。一次性迁移扫描十表的时间字段，内存和数据操作规模 O(行数)，每个需要转换的行一次合并更新，执行十次 Collection 改型、共 21 字段，使用一个迁移事务。Postgres 额外执行两次事务局部会话设置；DDL 可能取得排他锁，SQLite 驱动可能重建表并持有写锁，必须在副本测量维护时长；每个 IANA 转换采样 97 个小时点，还需测量 CPU 与内存。配置与预检不能代替备份和停写。
