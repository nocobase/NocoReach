## 阶段 2：仓库与 Agent

- 项目绑定内容仓库，安装 GitHub App；设置中登记允许修改的内容目录与检查命令。
- 通过 GitHub App 读取仓库文件与 frontmatter，自动建议网址与文件的对应，用户确认后生效。
- NocoReach Agent 命令行程序：电脑授权、检测 Claude Code、心跳与轮询、领取运行、离线等待与重启回收。
- 执行：独立分支与 worktree、任务说明、调用 Claude Code、实时执行日志、越界修改检测；由程序负责提交、推送与创建 PR，结果不确定时先查询已有 PR。
- 工作详情显示 PR 差异、CI 状态与预览链接；“要求修改”在同一分支发起新运行；失败、离线、停止的表达与重试。
- 技术方案已定（2026-10-01）：复用 NocoProject 的 daemon、运行协议与 CLI；本机 Agent 只执行流程中修改仓库的阶段。

**完成标准**：在测试仓库上真实完成：任务 → 在线 AI 写方案 → 批准 → 本机 Agent 修改 → 检查 → 推送分支与 PR → 在 NocoReach 查看差异与预览 → 要求修改一次；刷新、断开重连、人工提交冲突均有明确结果。

## 阶段 3：发布与效果

- 在 NocoReach 中确认发布：按审阅时的确切提交合并，遵守分支保护，失败原因如实展示。
- 上线核实：部署状态 → 页面内容检查 → 无法判断时人工确认并标注。
- 效果观察：基线、第 7/28 天对比、四档结论、同期修改与数据缺口标注；内容详情趋势图标出上线时间。
- 撤回：关联提交，生成可审阅的回退 PR。

**完成标准**：用一篇真实博客或文档从确认发布走到已上线，并能回看基线与后续数据。数据尚不足时只验收记录与观察能力，不宣称效果已验证。

## 阶段 4：每日自动分析

- 定时同步与分析；三条规则（高曝光低点击、排名 8–20、流量下滑）选出候选，在线 AI 判断并撰写建议。
- 没有新发现只留运行记录；相同建议不重复提出；第 7/28 天观察由同一定时任务推进。
- 需要 NocoReach 服务持续在线，本阶段开始前确定部署位置（服务器或云主机）。

**完成标准**：连续多日自动运行，建议可追溯到数据且不重复；服务重启后调度恢复。

阶段 4 之前，现有的手动生成机会与手动创建工作继续作为工作来源。

## 沿用的欠项

以下问题不因设计重写而消失，在对应场景需要时处理：

- 新项目自助初始化、干净环境安装与多项目／成员权限隔离；当前为单项目管理员试用，不是多租户产品。
- Google 同步的三天截止、长周期历史回补与覆盖说明。
- Google 明细只增不删：63 天时查询×页面明细约 70 MB，每次重建汇总约 3 秒、内存约 225 MB，随天数线性增长。已改为按数据版本缓存并在同步后预先重建（用户不再等待），但积累到 16 个月前需要改为写入时增量汇总或限制保留期。
- 同步在断网、授权失效、重启下的恢复验证。
- 第三方关键词研究结果到候选的完整业务验收（一次历史请求结果仍为 unknown）。
- 机会语义去重与人工合并。
- 前端大分包性能提示。
