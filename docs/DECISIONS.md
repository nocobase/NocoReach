# 设计决策

## 2026-10-01 — 每日分析由 NocoBase 工作流调度

用户要求增加每日自动更新，并提出用 NocoBase 工作流实现。

| 决定 | 原因 |
| --- | --- |
| 分析逻辑（信号、提示词、模型调用、校验、合并）留在插件，服务端运行 | 用工作流节点拼装难以测试，配置在数据库不在仓库，且需在工作流中保存调用 API 的凭据 |
| 调度用 NocoBase 工作流：插件注册“NocoReach 每日分析”节点并创建默认定时工作流 | 后台可见运行记录、可改时间、可追加通知；逻辑仍有版本与测试 |
| 前端节点在运行时加载工作流模块，加载失败则跳过 | 工作流插件停用时不影响管理后台 |
| “更新建议”改为触发同一次服务端运行 | 页面可以关闭，不再依赖浏览器中的对话生成 |

## 2026-10-01 — 一键发现、社区数据与数据健康

用户强调数据接入是最重要的功能，需要足够健壮以支撑大量 AI 分析；提出接入用户社区帖子，以及只输入网址即可自动导入。

| 决定 | 原因 |
| --- | --- |
| 数据连接页以“一键发现”为主入口：先发现、列清单，用户确认后接入全部公开来源 | 实测读取 nocobase.com 首页即可找到文档站、论坛、GitHub 与 X；但无法确认网站归属，授权与收费来源必须由用户操作，用户也应知道哪些数据进入分析 |
| 发现流程用固定规则，AI 负责解释 | 比让 AI 自由尝试更稳定、更快、可验证（与 OpenSEO 引导流程的取舍一致） |
| Discourse 社区为 P0，GitHub Discussions P1，Discord/Slack P2 | 用户社区是 forum.nocobase.com（Discourse），公开 JSON 无需凭据；社区高频问题是文档缺口最直接的证据 |
| 社区数据不保存用户名、头像等个人信息 | 分析只需要内容与互动数据 |
| 增加数据健康 | 数据可靠性需要可见：上次成功、截至日期、失败原因与重试 |
| 信号与本期观察排在上述三项之后 | 先把数据做扎实，信号能用的数据更多 |

## 2026-10-01 — 数据源与信号先行

用户指出：只围绕 GA4/GSC 曝光、排名、访问的固定规则过窄；平台会接入关键词、趋势、GitHub 等更多数据，规则应随之丰富。

| 决定 | 原因 |
| --- | --- |
| 规则由数据源提供，信号分为变化、缺口、时机、页面表现、转化五类 | 新数据源接入即扩展规则，不必重写分析逻辑；五类信号也对应不同的市场动作 |
| 概览始终显示 AI 的“本期观察” | 没有可行动建议时概览不空白，也能看到判断 |
| P0 数据源：GSC、GA4、网站内容、GitHub 基础数据、GitHub Traffic、GitHub Issues/Discussions；P1、P2 写入设计并在目录中展示为规划中 | 开源产品最关键的数据先做全；GitHub Traffic 只保留 14 天，越早归档越好 |
| 网站内容作为数据源，内容页自动列出页面 | 手动添加映射成本高；GSC/GA4 与 sitemap 已足以建立页面清单 |
| GitHub 凭据由用户提供或授权；长期用 GitHub App，过渡期用仅授权单仓库的只读细粒度 token | 产品不能内置任何人的凭据；一个 App 覆盖数据读取与后续 PR 发布 |
| 所有接入由 AI 引导，不给空白对话框 | 用户试用时的空白助手让人不知道该说什么 |
| 关键词研究移出菜单，后续以 OpenSEO 页面重做 | 页面尚未完成；OpenSEO 为 MIT 许可且技术栈一致 |
| 开发顺序改为数据源与信号 → 工作流程讨论 → Agent | 工作流程依赖信号与动作类型；Agent 依赖工作流程 |

## 2026-09-30 — 试用后简化界面

用户试用第一阶段后反馈：概览随观察周期给出不同建议，不知道该看哪个；卡片、标签、按钮过多，找不到起点；转为工作后讨论框、确认范围、生成按钮同时出现，不知道怎么推进；页面按钮多而左侧菜单过简。

| 决定 | 原因 |
| --- | --- |
| 概览固定近 28 天，建议只有一份，每天随新数据更新；需要其他时间范围到数据分析页面选择 | 市场上的待办类产品（按日修复建议、审计问题清单、翻新队列）都只有一份清单，时间窗口由规则内部决定；报表类才让用户选日期 |
| 概览最多 5 条证据充分的建议，每行只有要做什么、一句理由和一个按钮；待验证信号不上概览 | 信息过载导致无法判断从哪里开始 |
| 工作详情用步骤条，只显示当前步骤和一个主按钮；确认范围即开始执行；讨论移到侧边面板 | 让用户始终知道在哪一步、下一步做什么 |
| 页面跳转按钮收进分组的左侧菜单（工作、数据分析、设置），取代此前“次要入口不进主导航” | 页面按钮反而增加混乱；菜单分组同样能保持简单 |

## 2026-09-30 — 产品设计梳理与 SPEC 重写

背景：产品经过多轮迭代，SPEC 以日期补丁叠加，存在互相矛盾的描述（六列/四列、能否拖动、导航命名等）。用户要求先逐项讨论设计、梳理文档，再继续开发。讨论前做了市场调研，见 [调研记录](research/2026-09-30-ai-agent-content-tools.md)。

| 决定 | 原因 |
| --- | --- |
| 目标用户定为内容放在 Git 仓库的团队，重点是开源产品；写入 CMS 作为后续方向 | 开源产品的推广者多为技术用户；Git 与 PR 一个通道覆盖各类静态站点，差异、预览、CI、回滚可以沿用现有工具；CMS 需要逐个平台对接 |
| 主打差异点为“仓库原生”与“自带 Agent”；诚实的效果核实作为产品原则而非卖点 | 竞品多写入 CMS、使用云端托管 Agent；技术用户重视代码与凭据留在本地，也反感夸大的效果宣传 |
| 建议与优化工作分开，采纳后才成为工作 | 看板只放已决定要做的事，避免被 AI 建议淹没 |
| 本地 Agent 参考 Multica 做精简 daemon，首版只支持 Claude Code；提交、推送与 PR 由 daemon 负责，Agent 只改文件与运行检查 | 符合在看板上派活的体验；固定逻辑更易保证不重复写入；Claude Code 的非交互模式成熟、可精确限制工具，且擅长文字修改。Multica 许可证限制嵌入商用，只参考设计 |
| 在 NocoReach 内确认发布，合并绑定确切提交，之后再核实上线 | 发布确认与审阅的版本必须一致；合并不等于上线 |
| 在线 AI 保留，负责每日分析、讨论、修改要求起草与调研报告；只有修改仓库交给本地 Agent | 分析与定时任务不应依赖用户电脑开机 |
| 每日建议由固定规则选候选、AI 判断撰写；首版三类规则，文档缺口放下一版 | 可追溯、稳定、成本可控；文档缺口属于新内容，放在闭环跑通之后 |
| 首版 Agent 修改范围为站点仓库中的博客与文档 Markdown/MDX | 开源产品的搜索流量多来自文档，格式与博客相同；落地页代码风险高，README 无法用 GSC 衡量 |
| 内容索引通过 GitHub App 读取仓库自动建议映射，用户确认后生效 | 手工维护成本高；GitHub App 在确认发布时本就需要 |
| Agent 超出允许目录的修改不直接拒绝，标出并要求用户明确确认 | 有时确需改到相邻文件，强制拒绝会让任务卡住；关键是让用户知情 |
| 工作状态、运行状态、发布状态三层分开；拖动不启动 Agent；运行失败留在进行中；合并后留在待确认直到上线核实 | 让“已完成”始终代表真正上线；避免误触发 Agent；失败不被淹没 |
| 一个工作对应一个分支、一个 PR；首版不做批量修改 | 审阅范围可控 |
| 效果观察从上线时间起算，第 7/28 天对比，结论只有四档 | 只描述变化，不下因果结论 |
| 首版不做收件箱；机会库、分析页、关键词研究退为次要入口 | 单人试用时看板与角标足够；保持主导航简单 |
| 在线模型不绑定，沿用 NocoBase AI 配置 | 用户无偏好，保持可替换 |
| 每日自动分析放在第 4 阶段，部署位置届时决定 | 先跑通“修改 → 发布 → 看效果”这一差异化闭环；现有手动生成机会可暂作工作来源 |

## 2026年9月30日 内容优化与仓库执行

用户确认以 AI 数据反馈驱动内容优化，并要求产品越简单越好。完整 CMS 移出当前范围，正文由内容仓库维护；系统保存页面索引、优化工作、版本与执行回执。主要入口收敛为概览、优化工作、内容。建议继续在当前系统上修改：可复用的数据和执行基础保留，任务交互局部重做。具体四阶段开发及验收见 [当前计划](archive/INTEGRATED-DEVELOPMENT-PLAN.md)。旧固定六阶段及不允许拖动的产品设计被替代；拖动不得伪造审核或外部发布事实。此次仅设计更新。

以下按 2026-09-28 已确认结果整理，不伪造更早的确认日期。

| 决策 | 原因与约束 |
| --- | --- |
| Agent 贯穿工作流程，交互进入具体上下文 | 自然语言用于目标澄清、方案讨论和内容调整；原“页面内 AI”原则演进为对话与业务页面协同 |
| 导航按用户任务，而不是数据供应商 | 自有搜索、外部关键词研究职责分开，连接统一管理 |
| 迁移需求不进入产品 | 旧备份/旧实例与历史快照是本次初始化手段，不是市场用户核心功能 |
| 开源与市场趋势纳入数据方向 | 已由本次讨论确认；具体连接器待细化，口径独立，未实现不开放空页面 |
| 合并搜索概览与自有搜索表现 | 减少重复入口，将趋势与关键词证据集中展示 |
| 一级标题无图标、子菜单不同图标、全部展开 | 提高可发现性，避免折叠隐藏功能 |
| 行动计划为一级分组 | 任务列表保留；行动草案与效果复盘明确禁用占位，未交付不假装可操作 |
| 付费请求不自动重试 | 网络异常不等于未计费；unknown 保留并对账 |
| 旧三轮顺序已被端到端切片取代 | 旧顺序不再约束排期；每个切片所依赖的数据、权限与运行基础仍须满足 |
| GitHub 维护当前设计与交付事实 | SPEC 不堆叠互相冲突的历史结论；历史理由交由决策记录和 Git 追溯 |

后续变更需补充：提出原因、确认结果、影响页面/数据/API、验收变化。尚未确认的建议不写成既定规格。

## 2026-09-28 — 根据产品讨论重写主线

已确认：自然语言交代目标并多轮澄清；结合自身数据与市场变化持续观察；主动提出内容方案；人确认方案后 AI 执行；内容创作增加多轮人工审核和调整；最终确认后发布并观察反馈。

原因：原三轮按页面、接入、AI 拆分，未从开始把 Agent 组织进完整市场工作流程。

实施原则：现有产品为唯一演进起点，复用已实现能力；设计重写不授权从零重建。影响目标上下文、总览、内容机会、任务与后续创作发布流程；具体数据模型、API 和界面在切片内确定，本次未修改它们。

验收变化：保留历史证据与未完成的数据基础要求，新增目标澄清、持续观察、多轮审核、版本授权发布和复盘要求。具体审核节点尚未确认，讨论中的四节点示例不作为固定规格。

## 2026-09-28 — 以发现机会替代原总览

用户确认：首页概括全部已接入数据，再呈现 AI 洞察；围绕洞察对话形成多个行动方向，确认后直接进入任务。目标与对话作为持续上下文，详细分析页面作为证据入口。原因是独立目标页面、表单和任务之间割裂，入口难找。沿用 /home 和现有组件、集合，旧目标页重定向兼容，不新建平行产品。

技术增量：每轮对话读取已保存目标及证据；当前浏览器记住会话标识，恢复时仍由服务端用户权限确认可访问性；行动确认在事务内同时保存方案和创建任务。跨设备会话归属后续补齐。

## 2026-09-28 — 从统一目标先行改为机会先行

用户确认：先看数据反馈与 AI 洞察更符合市场工作；首页将证据和初步建议合为机会，讨论中形成行动目标。保留长期项目背景和历史目标，不以统一目标限制探索，不删除原任务。

## 2026-09-28 — 先统一数据接入体验，再分批落地来源

用户确认先编写数据接入产品设计。采用平台、资料、自定义连接三类入口，AI 协助接入且授权与范围由用户掌控。接入框架与第一批真实连接器共同演进；优先统一 Google 并增加公开官网／文档、GitHub，让新用户走到第一批机会。所有来源不必接齐，规划能力不得伪装可用。文档见 DATA-ONBOARDING.md，本轮不开发产品。

## 2026-09-28：发现机会按问题组织，时间作为证据口径

首页将数据观察和行动建议放在同一张卡片，让用户能直接追问依据；来源级摘要及完整筛选留给覆盖说明和机会库。7／28／90 天是分析窗口而非机会身份，保留同一机会的讨论与人工判断。GitHub 采用市场流量和关注度口径，技术更新样本不能替代增长证据。数据不完整时展示限制，避免用“有数据”冒充“可比较”。

## 2026-09-28 — 统一任务执行

四类机会共享任务状态机；机会分类不等于工作类型。AI 根据交付物提出工作步骤与审核点，用户确认。首版以 AI 文本能力和人工交接走通流程，外部写入须另接工具，不能把方案批准当发布授权。

## 2026-09-30 — 收录 OpenSEO 复用方案，待联合研究后开发

用户确认先将研究结论写入产品设计，并将在提供另一产品后统一开发。选择性复用 OpenSEO 的研究组件与交互，以补强市场证据和候选管理；沿用现有 NocoBase 3 与机会、任务主线。候选顺序、页面映射、技术差异及 MIT 归属要求见 [专题方案](archive/OPEN-SEO-REUSE.md)。

## 2026-09-30 — 联合研究进入开发准备

## 2026-09-30 — M1 持久记录与宿主适配

首版复用 nrTasks 和 nrSnapshots，以独立 key 存放 Run、成果版本、审核、方案与请求哈希；避免在未完成全量初始化的宿主上临时新增多张表，也避免将执行增长记录堆入任务 JSON。任务写锁与服务端鉴权保持统一，后续可迁移为专用集合。

在线文本调用使用当前 alpha.7 plugin-ai 的员工模型解析和 provider 接口，不照搬新版 NocoProject app 容器。后台执行从持久队列读取；未知调用不自动重跑。真实适配仍待合法测试身份验收，不能根据单元测试宣称模型闭环已通过。
