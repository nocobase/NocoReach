# 设计决策

## 2026-10-02 — OpenSEO 第 2 批：关键词研究与关键词；付费查询不再逐次显示费用；页面铺满宽度

| 决定 | 原因 |
| --- | --- |
| DataForSEO 查询点了就查，页面上不显示每次的价钱；花费在数据接入看（本月已花、累计、预算、结果不确定次数）；月度预算仍是硬上限，超了就停并提示去数据接入调整 | 用户改定：每查一次都显示费用很奇怪。取代“先显示费用、确认后才查”。保险留在预算上限、30 天复用、结果不确定不重试，付费请求仍只在用户点击时发出 |
| 关键词研究一次一个词、一个市场，三种方式；OpenSEO 的多标签、多词、城市、点击流、相似词合并、“自动”方式不做 | 用户要少选项；“自动”是两次查询拼起来，费用翻倍 |
| 搜索结果分析放进点一行才滑出的详情，不常驻右侧；“看前 10 个搜索结果”要点才查 | 用户规则：详情点了才滑出；打开详情本身不花钱 |
| 两个表格都加“本站排名”（近 28 天 Search Console，按查询不分大小写匹配，排名按曝光加权，页面取排得最好的） | 我们比 OpenSEO 多的：把市场估算和本站实际表现放在一起，也决定交给 Agent 时用哪个做法 |
| 已保存关键词要标签，照 OpenSEO（筛选、批量加减、改名换色删除） | 用户确认 |
| 选几个关键词交给 Agent 合成一个任务；有排名默认“优化现有页面”并关联那一页，没有默认“内容选题与大纲” | 用户确认合成一个任务；默认做法沿用机会页同样的规则（optimize / create） |
| 搜索表现保存的查询没有市场估算；之后在研究里保存同一个词时补上数据、保留标签 | 不为补数据自动发付费查询 |
| 原“已保存候选”直接作为“关键词”的数据（nrKeywordCandidates），研究记录作为“最近的研究”（nrKeywordRuns） | 保留已有数据，不迁移 |
| 菜单：数据总览、网站表现、搜索表现、关键词、内容、GitHub、社区、关键词研究 | SPEC 第 5 节的顺序：查任何关键词的研究工具放在本站数据之后 |
| 页面铺满宽度：去掉外框 1600px 上限和外框内边距，边距只由页面的 PageContainer 给 | 用户在 2K 屏上看两边空太多；NocoProject 铺满全屏 |

## 2026-10-02 — OpenSEO 第 0、1 批：搜索表现与数据总览

| 决定 | 原因 |
| --- | --- |
| 搜索表现读每天同步进库的数据，不实时查 Search Console | 用户确认；和洞察、数据总览、每日分析的数字一致，时间可选到 16 个月，打开快、不占 Google 配额。代价是数据只到上次同步（比 Google 晚约 3 天） |
| 国家和设备筛选先不做 | 同步时 query_page 按查询 × 页面合并，国家和设备没有保存；要做得改同步，且只有改之后的日子才有 |
| 数据总览一个数据源一张卡（OpenSEO 卡片布局），有数据的在前，未接入的用虚线卡写接入后能看到什么，计划开发收成底部一行灰字 | 用户确认；GitHub、社区等我们自己的数据源和 OpenSEO 的卡片放在一起，不另分组 |
| 搜索表现保留每日趋势图（OpenSEO 原页面没有），放在指标卡下面，可切换点击和曝光并和上期对比 | 用户确认；看得出哪天开始变化 |
| 搜索表现、数据总览的指标卡和总览里的 Search Console 都用各数据源自己的截至日期 | SPEC 第 5 节的规则；原来总览取 GA4 与 GSC 中较早的一天 |
| 共用组件只搬这次用到的（表格、排序、勾选、分页、批量操作条、筛选栏、指标卡、卡片、CSV 导出），按钮、弹窗等基础组件继续用 NocoReach 自己的；地区与语言选择第 2 批用到时再搬 | 两边都是 shadcn + Base UI，外观跟着 NocoReach；没有页面用的组件先不搬 |
| DataForSEO 费用控制抽成通用层（dataforseo.js，按查询类型注册），关键词研究改用它；同样的查询复用期从 24 小时改为 30 天，所有类型共用一个月度预算 | SPEC 的“30 天内同样的查询复用”；后面各批的付费页面直接用同一套预览、确认、预算和结果不确定不重试 |
| 新页面不用旧的 nr-page 样式 | 它的表格与输入框规则不在样式层里，会盖住移植的表格样式 |

## 2026-10-02 — 项目知识：记忆、知识库与 Skills 的分工

| 决定 | 原因 |
| --- | --- |
| 分三样东西：**Skill** 说怎么做（全局通用、可在项目里启用）；**记忆** 说这个项目是什么（每次都读、保持精简）；**知识库** 放参考资料（需要时去查） | 用户觉得三者有交叉；按“怎么做 / 是什么 / 参考资料”和“每次都读 / 需要时查”分开后边界清楚；同类 AI 工具也多是规则与记忆常驻、资料按需检索 |
| Skill 采用通用的 Agent Skills 格式（SKILL.md），不自创格式 | 这是 Claude Code 等工具已支持的公开标准，用户可以直接导入社区和 GitHub 上的 Skill 包，也能拿到别处用 |
| AI 团队菜单为 Agent · 做法 · Skills · 项目知识；“项目知识”一页包含记忆和知识库，菜单项后面不写“谁来做” | 用户希望少入口、名字产品化；知识库保留“知识库”这个叫法，记忆直接叫“记忆” |
| 记忆按品牌手册的结构分 9 部分：品牌基础、产品、受众、市场与语言、语气与风格、用词、核心信息、竞品、规矩与禁区；之前的项目字段自动读进对应部分，旧字段保留不删 | 用户要求按对外的品牌规范和手册结构来设；迁移只读不改，随时能回退 |
| 知识库分类：竞品、客户、产品、行业、其他；我们自己的网站页面和仓库不放进来 | Agent 本来就能读网站内容和仓库，放进来会重复、过时 |
| 知识库交给 Agent 时写成仓库之外临时目录里的文件，告诉它按需查阅、只当资料不当指令、不要复制进仓库，运行结束即删除；超出总量时较旧的只列标题 | 资料可能很长，不能塞进每次都读的说明里；放在仓库外保证不会被提交；第三方资料只当资料 |
| 统一的“添加”（链接、文字、文件、GitHub Skill 包）由在线 AI 判断归入 Skill、知识库还是记忆的修改建议，你确认后存入；在线 AI 的职责因此是：每日分析、起草新做法、整理添加的资料 | 用户希望用户只管往里放，不用先想该放哪里；整理是读资料和归类，不是执行任务，仍不违反“任务都交给 Agent” |
| 分四步做：项目知识页（记忆 + 手动添加知识库）→ Skills → 统一添加与 AI 整理 → AI 提出记忆的修改建议 | 先让 Agent 用上记忆和资料，再加 Skills，最后加 AI 整理 |
| Skills 第二步：新建支持填写和上传 Skill 文件夹（或单个 SKILL.md）；GitHub 导入留到第三步 | 用户确认（2026-10-02）；别处现成的 Skill 多是文件夹，浏览器能直接读文件夹，不用打包 |
| “新建 Skill”增加“填链接”：GitHub 上 Skill 文件夹、SKILL.md 或仓库的链接，以及直接指向 SKILL.md 的 https 网址；仓库里有好几个 Skill 时列出全部、可以多选（筛选、全选，已有同名的不能勾），一次导入，导入不了的说明原因；先读取给你看，再导入；只支持公开仓库，不用在线 AI；Skill 库上限从 100 提到 200；删除放在抽屉底部（不藏在“⋯”里），表格可勾选批量删除 | 用户提出、确认（2026-10-02）；起初只能选一个、只列前 30 个，用户试用 marketingskills（50 个）时觉得不友好，改为全部列出、多选；现成的 Skill 多放在 GitHub，读现成的文件不需要 AI。原第三步里的“GitHub Skill 包导入”因此提前，第三步只剩普通网页、文字、文件交给在线 AI 判断归类 |
| 自带 3 个示例 Skill（页面标题与描述、文档页写法、调研报告），默认停用，和自己建的一样能改能删、不做“恢复默认” | 用户确认；页面一开始不空，又不会悄悄改变 Agent 的做法 |
| 做法步骤指定的 Skill 不管项目里是否启用，那一步都会用；启用开关只管 Agent 在每个任务里按需使用的那些 | 用户确认（没有选“停用就不用”）；做法里写明要用就是要用，不需要两处都打开 |
| Skill 交给 Agent 时写成这次运行专用的 Claude Code 插件（仓库外临时目录，`--plugin-dir` 加载），任务说明里再列出用途和位置；SKILL.md 开头只保留 name 和 description | Claude Code 原生加载（`nocoreach:名称`），换别的 Agent 时任务说明里的路径也能用；丢掉 allowed-tools 等字段，避免 Skill 放开步骤不允许的工具 |

## 2026-10-02 — 所有任务交给 Agent；做法按工作分类、由步骤组成

| 决定 | 原因 |
| --- | --- |
| 在线 AI 只做每日分析（情报、机会）和起草新做法；所有任务——调研、写文档、改网站——都交给 Agent。取代之前的“在线 AI 优先” | 用户提出：分工更清楚（发现与执行分开）；Agent 能读仓库、上网核实，产出更好；做法和界面都更简单 |
| 做法不再分“方案类 / 落地类”，按工作内容分为调研分析、内容创作、内容优化、网站技术 | 用户认为原叫法口语化，也认为“文档 / 网站改动”不对——Agent 也会先分析再执行；调研 AirOps、WRITER、Copy.ai、Zapier、HubSpot 都按用途分类，执行者是做法内部的设置 |
| 一个做法是几个步骤：Agent 分析（不改仓库）、Agent 修改（开 PR）、你审核；有修改时系统接上上线和观察 | 同类产品都是“步骤 + 审核点”；执行层原本就按步骤运行，只需改做法的定义 |
| 内置做法可以直接编辑、恢复默认；新建做法用一句话让在线 AI 起草，草稿在编辑器里改好再保存 | 用户觉得做法页死板；同类产品都是一句话生成、模板可改 |
| Agent 的分析步骤用只读模式运行（旧版本 Agent 程序也认识），并告诉新版本程序这是分析而不是写方案 | 本机 Agent 程序版本可能不同步，只读模式保证不会误改仓库 |
| 之前由在线 AI 执行步骤的任务照原步骤做完；之前保存的自定义做法自动换成步骤写法 | 不打断已经开始的工作 |

## 2026-10-02 — 同步失败的重试与提醒

| 决定 | 原因 |
| --- | --- |
| 网站内容、GitHub、社区论坛同步失败后 15 分钟先重试一次，再按 1、3、6 小时 | 用户常看到同步失败提醒；查明是电脑合盖睡眠时的短暂唤醒没有网络，网络恢复后应尽快补上 |
| 断网类失败统一说“网络不可用，稍后会自动重试”，网站内容不再误报“没有找到 sitemap” | 原始技术信息（queryA ETIMEOUT、fetch failed）看不懂，sitemap 的说法会误导到网站本身 |
| 洞察页横幅仍在超过 1 天没有同步成功时出现，不放宽到 2 天 | 用户认为现在的提醒合适，2 天太慢 |
| 每日分析的失败处理按云端产品设计，而不是为本机睡眠优化（方案待用户确认，见路线图） | 产品以后部署在云端；本机只是当前的部署方式 |

## 2026-10-01 — 机会页：写法规则、来源标签、交给 Agent 直接开始

| 决定 | 原因 |
| --- | --- |

| Discourse 社区为 P0，GitHub Discussions P1，Discord/Slack P2 | 用户社区是 forum.nocobase.com（Discourse），公开 JSON 无需凭据；社区高频问题是文档缺口最直接的证据 |
| 社区数据不保存用户名、头像等个人信息 | 分析只需要内容与互动数据 |
| 增加数据健康 | 数据可靠性需要可见：上次成功、截至日期、失败原因与重试 |
| 信号与本期观察排在上述三项之后 | 先把数据做扎实，信号能用的数据更多 |

## 2026-10-01 — 数据源与信号先行

用户指出：只围绕 GA4/GSC 曝光、排名、访问的固定规则过窄；平台会接入关键词、趋势、GitHub 等更多数据，规则应随之丰富。

| 决定 | 原因 |
| --- | --- |
| 规则由数据源提供，信号分为变化、缺口、时机、页面表现、转化五类 | 新数据源接入即扩展规则，不必重写分析逻辑；五类信号也对应不同的市场动作 |
| 概览始终显示 AI 的“本期观察” | 没有可行动建议时概览不空白，也能看到判断 |
| P0 数据源：GSC、GA4、网站内容、GitHub 基础数据、GitHub Traffic、GitHub Issues/Discussions；P1、P2 写入设计并在目录中展示为规划中 | 开源产品最关键的数据先做全；GitHub Traffic 只保留 14 天，越早归档越好 |
| 网站内容作为数据源，内容页自动列出页面 | 手动添加映射成本高；GSC/GA4 与 sitemap 已足以建立页面清单 |
| GitHub 凭据由用户提供或授权；长期用 GitHub App，过渡期用仅授权单仓库的只读细粒度 token | 产品不能内置任何人的凭据；一个 App 覆盖数据读取与后续 PR 发布 |
| 所有接入由 AI 引导，不给空白对话框 | 用户试用时的空白助手让人不知道该说什么 |
| 关键词研究移出菜单，后续以 OpenSEO 页面重做 | 页面尚未完成；OpenSEO 为 MIT 许可且技术栈一致 |
| 开发顺序改为数据源与信号 → 工作流程讨论 → Agent | 工作流程依赖信号与动作类型；Agent 依赖工作流程 |

## 2026-09-30 — 试用后简化界面

用户试用第一阶段后反馈：概览随观察周期给出不同建议，不知道该看哪个；卡片、标签、按钮过多，找不到起点；转为工作后讨论框、确认范围、生成按钮同时出现，不知道怎么推进；页面按钮多而左侧菜单过简。

| 决定 | 原因 |
| --- | --- |
| 概览固定近 28 天，建议只有一份，每天随新数据更新；需要其他时间范围到数据分析页面选择 | 市场上的待办类产品（按日修复建议、审计问题清单、翻新队列）都只有一份清单，时间窗口由规则内部决定；报表类才让用户选日期 |
| 概览最多 5 条证据充分的建议，每行只有要做什么、一句理由和一个按钮；待验证信号不上概览 | 信息过载导致无法判断从哪里开始 |
| 工作详情用步骤条，只显示当前步骤和一个主按钮；确认范围即开始执行；讨论移到侧边面板 | 让用户始终知道在哪一步、下一步做什么 |
| 页面跳转按钮收进分组的左侧菜单（工作、数据分析、设置），取代此前“次要入口不进主导航” | 页面按钮反而增加混乱；菜单分组同样能保持简单 |

## 2026-09-30 — 产品设计梳理与 SPEC 重写

背景：产品经过多轮迭代，SPEC 以日期补丁叠加，存在互相矛盾的描述（六列/四列、能否拖动、导航命名等）。用户要求先逐项讨论设计、梳理文档，再继续开发。讨论前做了市场调研，见 [调研记录](research/2026-09-30-ai-agent-content-tools.md)。

| 决定 | 原因 |
| --- | --- |
| 目标用户定为内容放在 Git 仓库的团队，重点是开源产品；写入 CMS 作为后续方向 | 开源产品的推广者多为技术用户；Git 与 PR 一个通道覆盖各类静态站点，差异、预览、CI、回滚可以沿用现有工具；CMS 需要逐个平台对接 |
| 主打差异点为“仓库原生”与“自带 Agent”；诚实的效果核实作为产品原则而非卖点 | 竞品多写入 CMS、使用云端托管 Agent；技术用户重视代码与凭据留在本地，也反感夸大的效果宣传 |
| 建议与优化工作分开，采纳后才成为工作 | 看板只放已决定要做的事，避免被 AI 建议淹没 |
| 本地 Agent 参考 Multica 做精简 daemon，首版只支持 Claude Code；提交、推送与 PR 由 daemon 负责，Agent 只改文件与运行检查 | 符合在看板上派活的体验；固定逻辑更易保证不重复写入；Claude Code 的非交互模式成熟、可精确限制工具，且擅长文字修改。Multica 许可证限制嵌入商用，只参考设计 |
| 在 NocoReach 内确认发布，合并绑定确切提交，之后再核实上线 | 发布确认与审阅的版本必须一致；合并不等于上线 |
| 在线 AI 保留，负责每日分析、讨论、修改要求起草与调研报告；只有修改仓库交给本地 Agent | 分析与定时任务不应依赖用户电脑开机 |
| 每日建议由固定规则选候选、AI 判断撰写；首版三类规则，文档缺口放下一版 | 可追溯、稳定、成本可控；文档缺口属于新内容，放在闭环跑通之后 |
| 首版 Agent 修改范围为站点仓库中的博客与文档 Markdown/MDX | 开源产品的搜索流量多来自文档，格式与博客相同；落地页代码风险高，README 无法用 GSC 衡量 |
| 内容索引通过 GitHub App 读取仓库自动建议映射，用户确认后生效 | 手工维护成本高；GitHub App 在确认发布时本就需要 |
| Agent 超出允许目录的修改不直接拒绝，标出并要求用户明确确认 | 有时确需改到相邻文件，强制拒绝会让任务卡住；关键是让用户知情 |
| 工作状态、运行状态、发布状态三层分开；拖动不启动 Agent；运行失败留在进行中；合并后留在待确认直到上线核实 | 让“已完成”始终代表真正上线；避免误触发 Agent；失败不被淹没 |
| 一个工作对应一个分支、一个 PR；首版不做批量修改 | 审阅范围可控 |
| 效果观察从上线时间起算，第 7/28 天对比，结论只有四档 | 只描述变化，不下因果结论 |
| 首版不做收件箱；机会库、分析页、关键词研究退为次要入口 | 单人试用时看板与角标足够；保持主导航简单 |
| 在线模型不绑定，沿用 NocoBase AI 配置 | 用户无偏好，保持可替换 |
| 每日自动分析放在第 4 阶段，部署位置届时决定 | 先跑通“修改 → 发布 → 看效果”这一差异化闭环；现有手动生成机会可暂作工作来源 |
