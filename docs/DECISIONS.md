# 设计决策

## 2026-10-01 — 机会页：写法规则、来源标签、交给 Agent 直接开始

| 决定 | 原因 |
| --- | --- |
| 保留左边清单、右边详情；详情只留数据变化、建议做法、交给谁做三块，限制缩成一行小字，去掉“为什么值得做”“转为任务后”和搜索框 | 调研了 Google Ads、Ahrefs、HubSpot、AirOps、Writesonic、Profound、GitHub、Linear 的做法；也比较了卡片墙和整行列表两种示意，用户认为都不如左右两栏好 |
| 不设固定分类，用来源标签（来自哪些数据源）加主要依据的彩色事实标签 | 用户指出接入的数据源会越来越多，固定 4 类迟早不够 |
| “交给 Agent”建任务并立即按所选做法开始，页面不跳走、给“查看任务”链接；洞察页同一按钮做同样的事；做法由在线 AI 执行时按钮叫“交给 AI” | 用户确认直接开始；参考 GitHub 把告警指派给 Copilot、Profound 一键交给 Agent。人仍在看方案、看效果并发布处把关 |
| 不显示“预计提升” | 没有可靠的预测方法，硬算的百分比会误导；排序用优先级，标签写真实数字 |
| 写法规则：标题动作 + 对象不超过 18 字、不用空泛动词；理由一句带一个数字不超过 30 字；建议最多两句。程序检查，不合规的条目只改写一次，改写更好才采用，失败不重试 | 用户反馈 AI 写的机会绕口、不简洁；付费请求不自动重试的规则仍然适用 |

## 2026-10-01 — 洞察页以数字和变化为主

| 决定 | 原因 |
| --- | --- |
| 洞察页结构：一行“等你处理”提示 → 4 张带走势的指标卡 → “最新变化”（规则信号前 5 条，一行一条）→ 值得做的事（3 条）与最近改动的效果 | 用户反馈页面全是文字、抓不住重点；规则信号本身简短且带数字 |
| 去掉 AI 撰写的“本期观察”；指标卡固定搜索点击、搜索曝光、访问次数，第 4 张有 GitHub 时为新增 Star（近 28 天），否则关键事件 | 用户确认；整页统一 28 天窗口 |
| 每条变化右侧一个彩色事实标签（上升绿、下降红、需处理琥珀、排名蓝、发布紫），走势线按涨跌着色；标签由规则信号直接给出，旧信号由页面从原句读出 | 用户觉得实现不如示意图好看，问能否加彩色标签；颜色一眼区分好坏，标签只放一个最关键的数字，不增加文字 |
| 信号标题里的幅度写绝对值（“下降 76%”），方向只由文字和箭头表达 | 真实数据出现“下降 -76%”的双重符号 |
| 同类建议的“转为任务”按钮样式一致 | 原来只有第一条是实心按钮，用户问为什么颜色不一样；规范 S4.4 同类建议卡按钮一致 |

## 2026-10-01 — 任务的取消与归档，旧流程任务一次性归档

| 决定 | 原因 |
| --- | --- |
| 进行中的任务可以取消：停止执行、关闭未合并的 PR（本机 Agent 执行，分支保留），取消后不再推进；已完成、已取消、未开始的任务可以归档，从看板收起，可恢复 | 用户反馈任务开始后取消不了、会一直堆在看板上 |
| 早期流程的任务（分步方案、简单任务、手填发布）由系统一次性全部归档，标为“已归档（旧流程）” | 用户确认；新旧流程混在一起让看板很乱 |

## 2026-10-01 — 全部页面采用 NocoSolution 前端规范

| 决定 | 原因 |
| --- | --- |
| 产品里的所有页面按 NocoSolution《前端规范》（NocoProject 遵守的同一份）实现：统一页面容器与页头、区块卡片、淡色胶囊标签、加载／空／出错状态；新代码不得在单页里另做一版 | 用户反馈各页面边距、标题、颜色不一致；原因是各页手写样式且同一个类在多个文件里重复定义 |
| 搬入 NocoProject 的“紧凑／宽松”两档密度预设（默认紧凑，顶栏可切换）与语义色；页面只用间距、字号、圆角与颜色令牌，不写像素字号与固定颜色 | 规范 §4、§5：密度来自预设，颜色只用令牌 |
| 颜色只表达含义：主色用于主要动作、选中与正在进行；琥珀色只用于“需要你处理”；状态按“未开始灰、进行中蓝、待确认紫、需注意琥珀、完成绿、取消／归档石板灰、失败红” | 规范 §5.2、§5.3 |

## 2026-10-01 — 先走通整条流程，效果观察先做最简版

| 决定 | 原因 |
| --- | --- |
| 开发顺序改为：效果观察最简版 → 整条链路真实走一遍 → 服务部署位置 → 整体走查；试用中不阻塞流程的问题先记清单，走查时统一处理 | 用户认为最近陷入细节、花了很多时间，要先把产品流程走通 |
| 服务暂时放在用户本机，不部署服务器 | 用户确认；合上电脑时每日任务会停，部署位置之后再定 |
| 效果观察：上线当天不计，第 7／28 天与上线前同样长的日子对比；两段合计搜索点击至少 40 次看点击，否则看浏览量；变化至少 15% 且至少差 10 次才算上升或下降；数据同步到对比最后一天才算 | 规则简单、能解释；用真实数据试算时，部分页面曝光多但点击近零，按点击会一律“数据不足”，故按点击量选择主指标 |

## 2026-10-01 — 落地类改为“看效果并发布”，合并与上线核实自动完成

| 决定 | 原因 |
| --- | --- |
| 落地类流程为“修改 → 看效果并发布 → 上线 → 观察”，你只做一次决定；页面类做法默认不先出文字方案（技术修复默认先出），开关在做法里，不在开始时询问 | 用户认为原流程步骤多；文字方案看不出改成什么样 |
| “看效果”用改动对比（改前／改后内容，新增与删除标色）；PR 带预览链接时显示“打开预览页面”。不在本机跑网站截图 | 参照行业做法（托管平台的 PR 预览部署、CMS 草稿预览）；本机跑网站最复杂、最容易失败。用户选择简单方案 |
| 发布信息自动生成（合并哪次提交、检查页面、发布说明），发布说明可改 | 用户反馈让人填写发布信息很奇怪 |
| 合并由本机 Agent 用电脑上的 GitHub 登录完成，只合并看过的那次提交；上线核实由系统打开线上页面寻找 Agent 给出的核对文字，每 30 分钟一次，24 小时没看到就提醒 | 改仓库的事交给本机 Agent；暂不需要 GitHub App；测试仓库不会部署，提醒里可手动确认 |

## 2026-10-01 — 本机 Agent 第一版实现与 Git／CMS 并存结论

| 决定 | 原因 |
| --- | --- |
| Git 与 CMS 可以并存，但要按内容目录指定唯一“内容来源”：以 Git 为准／合并后写回 CMS（写回前比对版本，被改过就不覆盖，交给人决定或让 Agent 基于最新内容重做）／以 CMS 为落地目标（改动写成 CMS 草稿）。首版以 Git 为准，详见 SPEC 后续方向 | CMS 单向同步、整篇覆盖，两边都改会悄悄丢失 Git 的修改 |
| 提交、推送、开 PR 由 Agent 程序完成，Claude Code 不碰 git：出方案时不能改文件、不能跑命令；修改时只能读写文件 | 改动范围、分支和 PR 目标由程序固定逻辑保证 |
| 服务端校验 PR：地址必须在登记仓库内，分支必须是 `nocoreach/task-<任务号>`；超出允许目录的改动在审核时单独列出，必须勾选确认才能通过 | 防止 PR 开到上游或改到不该改的地方 |
| 电脑用连接时生成的密钥认证，密钥只显示一次、服务端只存哈希，可随时断开；心跳不改设置版本 | 不在服务端保存可用凭据；避免心跳与保存设置冲突 |
| Agent 程序不提交编译产物：在 NocoReach 源码目录运行 `node apps/agent/build.cjs` 后使用；推送用这台电脑的 gh/git 凭据，不经过 NocoReach | 产物不进仓库；GitHub 凭据不进 NocoReach |
| 测试仓库用私有的 estheryo/website-test（用户已同意新建；复制 fork 的 main，不是 fork，PR 天然开不到上游）；关闭该仓库的 Actions | 公开仓库的 fork 不能设私有；原有工作流会在每次推送和 PR 时构建并推送 nocobase/website 镜像，在副本里只会失败并消耗私有仓库额度 |
| Claude Code 修改时用 acceptEdits，不用 bypassPermissions | 只自动允许任务工作目录内的修改，目录外写入被拒绝（已用真实 Claude Code 验证） |

| 决定 | 原因 |
| --- | --- |
| 把 NocoProject 后台程序的核心（调用 Claude Code、工作目录、回传日志、取消、领取运行）搬出来，做成精简的 NocoReach Agent 程序，接口换成 NocoReach 自己的 | 提交、推送、开 PR 由程序按固定逻辑完成并检查改动范围；不必实现并追随 NocoProject 的整套服务端接口 |

## 2026-10-01 — 任务模型：做法、一个任务一个执行者、方案与落地分开

用户认为“官网修改”里在线 AI 写方案再交给本机 Agent 的同一流程很别扭，且工作类型远不止改官网和调研；调研主流 AI 营销产品（AirOps、Optimizely Opal、HubSpot Breeze、Profound、Writesonic、Jasper，见 [调研](research/2026-10-01-ai-marketing-insight-to-action.md)）后确定：

| 决定 | 原因 |
| --- | --- |
| 用“做法”模板容纳工作类型，代替阶段式流程编辑器；自定义即复制并用自然语言改写 | 主流产品都以 Playbook／Agent 模板容纳多种工作，类型可不断增加 |
| 分工原则：在线 AI 只出方案不执行；凡是落地的交给本机 Agent | 用户原则；方案类交付文档，落地类交付 PR |
| 一个任务一个执行者；先方案后落地拆成两个串联任务，接受时一键交给下一步 | 避免同一任务里两个执行者接力；用户提出方案可直接交给落地的 Agent |
| 交接的是任务说明（做什么、为什么、范围、验收、依据），Agent 读仓库后出具体方案并指出对不上之处 | 在线 AI 看不到仓库、模型偏弱；具体实现由有仓库上下文的一方决定 |
| 两边上下文互通：在线 AI 通过 GitHub App 只读仓库并按需查询数据；Agent 通过命令行或 MCP 查询数据；纠正可存为技能或项目记忆 | 提高方案质量并越用越准 |
| 模型不更换，由用户在 NocoBase AI 设置中自行配置 | 用户决定 |
| 读取、研究、起草自动；写到外部前必须确认；做法可加检查点 | 主流产品的统一确认规则 |

## 2026-10-01 — 用户可定义流程，在线 AI 优先，主线改名

用户认为按固定动作类型写死步骤不合理：不同团队的流程会自定义，应参照 NocoProject 中 Agent 执行流程的方式；站外发帖先不做，围绕官网修改与调研报告。

| 决定 | 原因 |
| --- | --- |
| 任务按流程推进；流程为线性阶段，每阶段设定执行者、指令、检查清单与审批；系统自带“官网修改”“调研报告”，复制后可改 | 团队流程各不相同；线性阶段比 NocoProject 的状态跳转图更适合做市场的人 |
| 能在线完成的由在线 AI 做（分析、调研、方案、起草、审核辅助）；凡是修改仓库的交给本机 Agent | 用户确定的分工原则；本机 Agent 只做非它不可的事 |
| 本机执行层复用 NocoProject 的 daemon、运行协议与 CLI | 不重复建设；NocoReach 专注证据、流程、发布与效果 |
| 任务页参照 NocoProject：等你处理卡、依据、成果、动态时间线与输入框、右侧属性栏，看板与表格切换 | 原步骤条式详情页体验不好 |
| 新增与主线并列的“AI 团队”分组：Agent、技能、流程、项目记忆 | 放在设置里会弱化 AI 驱动这条主线 |
| 主线改名为洞察 · 机会 · 任务，不加分组标题 | “工作”与“优化工作”重复；流程不只有优化；三个词分别对应发生了什么、值得做什么、正在做什么；代码中该对象本就叫 opportunity |
| 站外发帖与第三方渠道不做；首版不单独做收件箱，等你处理的事列在洞察页顶部 | 用户要求先聚焦官网修改与调研；决定变多后再加收件箱 |

## 2026-10-01 — 一键发现、社区数据与数据健康

用户强调数据接入是最重要的功能，需要足够健壮以支撑大量 AI 分析；提出接入用户社区帖子，以及只输入网址即可自动导入。

| 决定 | 原因 |
| --- | --- |
| 数据连接页以“一键发现”为主入口：先发现、列清单，用户确认后接入全部公开来源 | 实测读取 nocobase.com 首页即可找到文档站、论坛、GitHub 与 X；但无法确认网站归属，授权与收费来源必须由用户操作，用户也应知道哪些数据进入分析 |
| 发现流程用固定规则，AI 负责解释 | 比让 AI 自由尝试更稳定、更快、可验证（与 OpenSEO 引导流程的取舍一致） |
| Discourse 社区为 P0，GitHub Discussions P1，Discord/Slack P2 | 用户社区是 forum.nocobase.com（Discourse），公开 JSON 无需凭据；社区高频问题是文档缺口最直接的证据 |
| 社区数据不保存用户名、头像等个人信息 | 分析只需要内容与互动数据 |
| 增加数据健康 | 数据可靠性需要可见：上次成功、截至日期、失败原因与重试 |
| 信号与本期观察排在上述三项之后 | 先把数据做扎实，信号能用的数据更多 |

## 2026-10-01 — 数据源与信号先行

用户指出：只围绕 GA4/GSC 曝光、排名、访问的固定规则过窄；平台会接入关键词、趋势、GitHub 等更多数据，规则应随之丰富。

| 决定 | 原因 |
| --- | --- |
| 规则由数据源提供，信号分为变化、缺口、时机、页面表现、转化五类 | 新数据源接入即扩展规则，不必重写分析逻辑；五类信号也对应不同的市场动作 |
| 概览始终显示 AI 的“本期观察” | 没有可行动建议时概览不空白，也能看到判断 |
| P0 数据源：GSC、GA4、网站内容、GitHub 基础数据、GitHub Traffic、GitHub Issues/Discussions；P1、P2 写入设计并在目录中展示为规划中 | 开源产品最关键的数据先做全；GitHub Traffic 只保留 14 天，越早归档越好 |
| 网站内容作为数据源，内容页自动列出页面 | 手动添加映射成本高；GSC/GA4 与 sitemap 已足以建立页面清单 |
| GitHub 凭据由用户提供或授权；长期用 GitHub App，过渡期用仅授权单仓库的只读细粒度 token | 产品不能内置任何人的凭据；一个 App 覆盖数据读取与后续 PR 发布 |
| 所有接入由 AI 引导，不给空白对话框 | 用户试用时的空白助手让人不知道该说什么 |
| 关键词研究移出菜单，后续以 OpenSEO 页面重做 | 页面尚未完成；OpenSEO 为 MIT 许可且技术栈一致 |
| 开发顺序改为数据源与信号 → 工作流程讨论 → Agent | 工作流程依赖信号与动作类型；Agent 依赖工作流程 |

## 2026-09-30 — 试用后简化界面

用户试用第一阶段后反馈：概览随观察周期给出不同建议，不知道该看哪个；卡片、标签、按钮过多，找不到起点；转为工作后讨论框、确认范围、生成按钮同时出现，不知道怎么推进；页面按钮多而左侧菜单过简。

| 决定 | 原因 |
| --- | --- |
| 概览固定近 28 天，建议只有一份，每天随新数据更新；需要其他时间范围到数据分析页面选择 | 市场上的待办类产品（按日修复建议、审计问题清单、翻新队列）都只有一份清单，时间窗口由规则内部决定；报表类才让用户选日期 |
| 概览最多 5 条证据充分的建议，每行只有要做什么、一句理由和一个按钮；待验证信号不上概览 | 信息过载导致无法判断从哪里开始 |
| 工作详情用步骤条，只显示当前步骤和一个主按钮；确认范围即开始执行；讨论移到侧边面板 | 让用户始终知道在哪一步、下一步做什么 |
| 页面跳转按钮收进分组的左侧菜单（工作、数据分析、设置），取代此前“次要入口不进主导航” | 页面按钮反而增加混乱；菜单分组同样能保持简单 |

## 2026-09-30 — 产品设计梳理与 SPEC 重写

背景：产品经过多轮迭代，SPEC 以日期补丁叠加，存在互相矛盾的描述（六列/四列、能否拖动、导航命名等）。用户要求先逐项讨论设计、梳理文档，再继续开发。讨论前做了市场调研，见 [调研记录](research/2026-09-30-ai-agent-content-tools.md)。

| 决定 | 原因 |
| --- | --- |
| 目标用户定为内容放在 Git 仓库的团队，重点是开源产品；写入 CMS 作为后续方向 | 开源产品的推广者多为技术用户；Git 与 PR 一个通道覆盖各类静态站点，差异、预览、CI、回滚可以沿用现有工具；CMS 需要逐个平台对接 |
| 主打差异点为“仓库原生”与“自带 Agent”；诚实的效果核实作为产品原则而非卖点 | 竞品多写入 CMS、使用云端托管 Agent；技术用户重视代码与凭据留在本地，也反感夸大的效果宣传 |
| 建议与优化工作分开，采纳后才成为工作 | 看板只放已决定要做的事，避免被 AI 建议淹没 |
| 本地 Agent 参考 Multica 做精简 daemon，首版只支持 Claude Code；提交、推送与 PR 由 daemon 负责，Agent 只改文件与运行检查 | 符合在看板上派活的体验；固定逻辑更易保证不重复写入；Claude Code 的非交互模式成熟、可精确限制工具，且擅长文字修改。Multica 许可证限制嵌入商用，只参考设计 |
| 在 NocoReach 内确认发布，合并绑定确切提交，之后再核实上线 | 发布确认与审阅的版本必须一致；合并不等于上线 |
| 在线 AI 保留，负责每日分析、讨论、修改要求起草与调研报告；只有修改仓库交给本地 Agent | 分析与定时任务不应依赖用户电脑开机 |
| 每日建议由固定规则选候选、AI 判断撰写；首版三类规则，文档缺口放下一版 | 可追溯、稳定、成本可控；文档缺口属于新内容，放在闭环跑通之后 |
| 首版 Agent 修改范围为站点仓库中的博客与文档 Markdown/MDX | 开源产品的搜索流量多来自文档，格式与博客相同；落地页代码风险高，README 无法用 GSC 衡量 |
| 内容索引通过 GitHub App 读取仓库自动建议映射，用户确认后生效 | 手工维护成本高；GitHub App 在确认发布时本就需要 |
| Agent 超出允许目录的修改不直接拒绝，标出并要求用户明确确认 | 有时确需改到相邻文件，强制拒绝会让任务卡住；关键是让用户知情 |
| 工作状态、运行状态、发布状态三层分开；拖动不启动 Agent；运行失败留在进行中；合并后留在待确认直到上线核实 | 让“已完成”始终代表真正上线；避免误触发 Agent；失败不被淹没 |
| 一个工作对应一个分支、一个 PR；首版不做批量修改 | 审阅范围可控 |
| 效果观察从上线时间起算，第 7/28 天对比，结论只有四档 | 只描述变化，不下因果结论 |
| 首版不做收件箱；机会库、分析页、关键词研究退为次要入口 | 单人试用时看板与角标足够；保持主导航简单 |
| 在线模型不绑定，沿用 NocoBase AI 配置 | 用户无偏好，保持可替换 |
| 每日自动分析放在第 4 阶段，部署位置届时决定 | 先跑通“修改 → 发布 → 看效果”这一差异化闭环；现有手动生成机会可暂作工作来源 |
