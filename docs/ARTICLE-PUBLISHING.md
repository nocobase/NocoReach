# Article publishing

Blog and article tasks can publish a structured article to a configured **publishing target** instead of opening a pull request. The writing steps (outline, draft, rewrite, review) are unchanged; only the change step's deliverable and the release differ. Code and page-layout tasks keep the pull-request flow.

Administrators configure targets under Data sources › Blog CMS (in the Agent edits and publishing group), choose the default one and, per playbook, where its tasks publish (a target or the repository). A new task starts from where its page lives: the article found from the task's page in the target that publishes it, a page no target holds through the repository, a blog post as a new article in the playbook's target. Its owner can change this before starting, and also publish the same article to up to four other targets. Operator instructions in Chinese: [ARTICLE-PUBLISHING.zh-CN.md](ARTICLE-PUBLISHING.zh-CN.md). The HTTP protocol a site implements for the `http` kind: [ARTICLE-API.md](ARTICLE-API.md).

## Model

- `shared/article-publishing.ts` defines the article model (`slug`, `status`, `locales: { <locale>: { title, description, body } }`, Markdown bodies), the target schemas and presets, and each kind's capabilities.
- `server/nocoreach/articles/` holds the providers behind one interface (`provider.ts`): `nocobase-api.ts` (a NocoBase collection through its resource API — the same requests as the CMS pages, not direct database access), `http-protocol.ts` (the NocoReach article API), `git-files.ts` (Markdown files in a GitHub repository). `targets.ts` stores targets per project in `nrVariables`, sealed with their credentials; the browser receives views without credentials. `downstream.ts` checks the Git export of a target that exports to a repository. `delivery.ts` publishes a proposal.
- `server/nocoreach/execution/article-flow.ts` connects this to the task flow; `service.ts` only calls into it.

| Kind           | Concurrency                                                          | Idempotency       | Notes                                                                                                  |
| -------------- | -------------------------------------------------------------------- | ----------------- | ------------------------------------------------------------------------------------------------------ |
| `nocobase-api` | check before write (compare `version` field, by default `updatedAt`) | lookup by slug    | NocoBase has no conditional update. Action-bound workflows only run when listed in `triggerWorkflows`. |
| `http`         | conditional (`baseVersion`, 409)                                     | `Idempotency-Key` | See [ARTICLE-API.md](ARTICLE-API.md).                                                                  |
| `git-files`    | conditional (file blob SHAs; fast-forward-only ref update)           | lookup by slug    | Front matter or a JSON metadata file for title and description.                                        |

## Finding the article

- `slugFromPage` (`shared/article-publishing.ts`) reads a page address back through a target's `pages` patterns to a locale and slug. Hosts compare without `www.`, paths without a trailing slash; the query and fragment are ignored. Existing slugs may contain dots.
- `nrArticles:match { urls }` (`targets.ts` `match`, read-only, members) tries each address against every target, the default first, and returns the first article `findBySlug` finds as `{ targetId, articleId, slug, title, url, locales }`, `locales` being the languages it has a title or body in (`articleLocales`). `nrArticles:languages { targetId, articleId }` (read-only, members) reads the same for an article picked by hand, and `linkArticle` keeps them on `w.article.locales`. `unchecked` is true when a target that could hold the page could not be asked (no key, offline), so "not found" is not certain.
- The start card (`task-detail.tsx`, `article-model.ts`) sends `pageUrlsOf(data)`: the task's linked page, the page it was handed off with (`evidence.page`), the opportunity's target when it is an address, then the pages of the changes it cites or was handed off from (`evidence.signalKey`). `confirmDirection` keeps `page` (an http(s) address) and `signalKey` on the task's evidence, so a change handed off on its own from Insights or a data page finds its article too. `defaultDelivery` then chooses: the linked article; a playbook set to the repository; a blog post as a new article; the article found (linked by `linkArticle` as the task starts); the repository when the page is known, no target holds it, the playbook names no target and a repository is connected; otherwise a pick. `DeliverySummary` shows the decided destination in one line with Change, which opens `ArticleStart`.

## Task flow

1. Before start, `linkArticle` reads the article (outside the business transaction) and stores an immutable snapshot (`nr-task-article:*`). `startTask` freezes `work.delivery` (`{ kind: 'article', targetId, articleId|null, sourceKey, also? }`): the linked article, a chosen target (`delivery: { targetId }`, new article), `delivery: 'repo'` for a pull request, or without a choice the playbook's entry in `playbookTargets` (`savePlaybookTargets`; `'repo'` keeps the pull request) and, for `blog-post`, the default target (`setDefaultTarget`; else the first in the list).
   - `delivery.also: [targetId]` (at most four, `articles.tooManyTargets`) publishes the same article to other targets. For a linked article, each is searched for its slug before the lock (`articles.alsoUnreadable` when that read fails); a match is updated and its snapshot is that target's base, otherwise the article is created there. A new article is created everywhere; a slug already taken in another target is that target's conflict at publish time.
2. The change step runs in mode `article`: no repository, read-only Runner, capability `article.draft`. The source goes to the Runner as the `article.json` material. The result's `article` is validated against the target (locales, mapped fields, slug and, for a new article, a title and body in the primary language) by `task result` and again on acceptance; a draft that changes nothing is invalid. A rejection says in words what to change and names the languages (`DraftRejected`, `articles.draft.*`): `task result` returns it to the Agent, which rewrites and submits again, and the editor and Review again show the same message. The artifact keeps the proposal: `draft`, `changes` (field paths), `baseKey`, `baseVersion`, and `also[]` with one proposal per other target (`projectDraft` in `delivery.ts`): an existing article gets the fields the draft holds, a new one the whole article (the primary's source with the draft applied); locales and fields the target cannot hold are left out and listed in `skipped`.
3. Review compares each changed field with the base. `editArticleDraft` saves a new artifact version. On a target with a status (`supportsStatus`), a new article is a draft unless the reviewer chooses Published; the editor offers the choice and the server defaults a missing status to `draft`. Approval binds the artifact; `w.release` becomes `publishing` with a fresh idempotency key.
4. Publishing runs after commit (and from `tick()` for an interrupted attempt), outside transactions, and records the outcome under the task lock:
   - The target is read first. Changes already present are adopted (a retry after an unknown outcome never writes twice).
   - A field changed in the target since the base **and** changed differently by the draft is a conflict. Changes to fields the draft leaves alone are kept; only the draft's fields are written.
   - With a downstream export, a body or metadata field whose Git copy differs from the target and whose latest commit is not the exporter's blocks publishing (the export would replace a Git-only edit).
   - States: `exporting` (downstream) → `verifying` / `not_seen` → `live`; or `publish_failed` (`retryPublish`), `publish_conflict` (`rebaseArticle` keeps the approved draft, rebases it on the current article, records the conflicting fields and returns to review), `export_late` after six hours.
   - A failed target keeps its code in `error` (shown in plain words on the task), the step it stopped at in `errorStep` (`read`, `downstream`, `write` or `verify`), what the target or the error said in `errorDetail` and the time in `errorAt`; all four are cleared by `retryPublish` and by a successful publish. Each failed target is also logged at warn level as `NocoReach article publish failed` with the project, task, target, step, code and detail.
   - Several targets: `release.article` is the primary's record and `release.also[]` the others', each with its own `state` (`publishing | published | exporting | exported | publish_failed | publish_conflict`), key, conflict, export and drift. Targets proceed independently; `release.state` is the aggregate (`settle`): publishing while any publishes, then a conflict, then a failure, then pending exports, then the page check over every target's pages. `retryPublish` retries every failed target. `rebaseArticle` bases each conflicting target on its current article (a taken slug becomes an update of that article, a missing one a new article) and each published target on what it published (`carried` keeps its written fields tracked), so approval adopts what is already there and writes only the rest. A single-target release keeps the earlier shape (no state on its record).
5. Languages (2026-10-24): `startTask` may carry `delivery.locales`, the languages to write with the primary first, kept on `work.delivery` as far as the target has them; the start card and Accept and start send their choice, even a single language chosen out of several (`deliveryPlan` in `shared/task-start.ts`). Its absence keeps the earlier behaviour (every language at once). The Runner always gets `article.languages` (`primary`, `others`, `phase`, `write`); without chosen languages the phase is `all`, the target's first language is the primary and `write` is every language (2026-10-27). The article is written in these languages whatever the project's language (`language`, used for the Agent's notes and summary), the brief or the outline are in. A new article needs a title and body in the primary language on its own target; another target is checked once the translations are in, in its own first language when the task writes it. In phase `primary` only the primary language is kept from the result. Approving that version (`approveStage`, `needsTranslation`) publishes nothing: `approvePrimary` keeps it on `delivery.translateFrom` (its draft, the primary's text as readers see it, and the fields it changed), records the review as `approvePrimary`, and returns the step to the Agent. In phase `translate` the Runner gets the approved text in `languages.approved` (with every field it has, `fields`) and returns the other languages; `byPhase` merges them under the approved draft, so the primary stays as approved. The translated version is reviewed as any other and one approval publishes every language.
   - Update in place (2026-10-28, T-53): when an existing article already has some of the languages to write (`inPlaceLocales` in `shared/article-publishing.ts`, from the source snapshot's `articleLocales`), the run after approval is phase `update` instead. `languages.update` lists those languages, edited from their own text in the source with the primary's changes; `languages.translate` the ones the article lacks, translated from the whole approved text; `languages.changes` what the primary changed (`primaryChanges` in `server/nocoreach/articles/edits.ts`): the title and description before and after, the body as `edits` (`near`, `before`, `after`, block by block; `truncated` past 60,000 characters). `approvePrimary` returns `update` or `translate` as the approval's history note. A translation of an article as published (`translateFrom.published`) and a new article have no in-place languages.
   - In phase `translate` or `update`, a result that holds none of the languages to write is refused (`writesNone` in `delivery.ts`, `articles.draft.othersMissing`), so `task result` tells the Agent instead of passing the approved primary as the next version (T-53: a failed script submitted the primary-only file an earlier run had left in the workspace). A version that holds them unchanged is accepted; the review card says which languages have no changes and, when none changed, offers Update again (a change request with a fixed comment), Request changes and Publish the primary only (`reviewRound` in `client/pages/task-detail/article-model.ts`).
   - Translate into other languages (2026-10-25, the built-in `sync-translations` and copies of it, `translatesArticle`): an article that exists is translated without a primary round. `startDelivery` (`startTranslation`) takes the linked article as it is published as the approved source: `delivery.locales` is the source first, then the languages to write, and `delivery.translateFrom` (`published: true`, no artifact, an empty draft) holds the source language's text with every field it has, since whether a translation is out of date is not known. The first run is in phase `translate`; `byPhase` keeps only the languages to write, so the source is neither rewritten nor reviewed again, and change requests stay translations. Without `delivery.locales` the source is the target's first language the article has, translated into the ones it lacks, or into every other language when it lacks none (`translationDefault`); the start card always sends its choice. A new article (`articles.translateNeedsArticle`), a source without text (`articles.translateNoSource`) or nothing to write (`articles.translateNoLanguages`) stops the start; `also` is ignored. A repository page under the same playbook opens a pull request as before.
6. For 14 days after publishing, the written fields are compared with the target hourly; a difference is recorded as `release.article.drift` and shown on the task.
7. A build pull request touching a file a target's exporter owns cannot be approved (`pr.protected`); the Runner is told the protected templates.

Mock deployments simulate the release as before and never call a target.

## Guarantees and limits

- `http` and `git-files` targets cannot overwrite a concurrent change. `nocobase-api` checks just before writing: a save that lands between the check and the write (about a second) can be overwritten, and an editor who saves an old form after publishing overwrites the published version. The second case is detected afterwards (drift) and shown on the task, not prevented. A database-level revision check in the CMS would remove both; it is not part of this change.
- The NocoBase CMS export to Git is unchanged. Git-only edits to articles other than the one being published can still be replaced by that export, as before.
- Tags, categories, covers and other relations are not written.
