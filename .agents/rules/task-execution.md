# NocoReach: Task execution

Demo online chat uses the Demo plugin's persisted `chat` policy without modifying Agents. Resolve the environment model before entering the conversation transaction; recheck it before model calls and stop active work if it changes. Wrap local reads and explicit source/Runner simulations with `runChatTool` after business authorization. Conversation write rules cover owned general chats and recognized demo projects only; they never expose definition editing. Demo chat always answers from the persistent scripted Demo model; the plugin offers no real-model choice for visitors.

Read the [Agents plugin Skill](../skills/nocobase-app-plugin-agents/SKILL.md) first. The Agent page (`/agents`) shows who does the work above four tabs in setup order: Model services, Runtimes, Local agents (`runner`, behind the `page:agents` grant) and Usage (Model services, Runtimes and Usage are the Agents plugin's own pages at `models`, `runtimes` and `usage`, under the plugin's route grants); each tab renders its own page frame below the tab bar, and `/agents` opens the first tab the reader may open. The tab bar names each tab, so the outlet wrapper hides the plugin pages' `h1` visually (`[&_header_h1]:sr-only`) and Local agents uses a screen-reader heading; every tab opens with its one-line description. `client/pages/agents/roles.tsx` says which work cloud models do (daily analysis and the chat panel, on the model services) and which local agents do (tasks, on a runtime's coding tool), for people who run marketing: each row names the model or agent it uses, where a local agent runs and whether that runtime is shared with the team or owner only, and a status. Every row has one Settings button for administrators, a dialog that changes what the row uses: Daily analysis sets the plugin's system default chat model through `nrOnlineAI.setModel` (application action, administrators only, calling `models.services.setDefaultChat`; the plugin's pages stopped offering it in 0.1.0-beta.11), Chat panel opens the chat agent dialog, and Tasks sets the project default with each agent's state beside it. While a row needs attention, the button is the fix instead. The status follows how the work last ended, not only whether it is set up: the daily analysis reads `nrOnlineAI.status`, and `nrAgent.status` called by the page (with the viewer's machine visibility) adds each agent's `health` from its latest task runs (`agents.runs.list`), naming the failures that last until someone acts (`toolAuth`, quota, model, setup) and how many in a row, plus the chosen agent's runtimes; computer names follow the plugin's `runForViewer` and are listed only to administrators. The task page calls the same status without the viewer and pays for none of this. The Local agents tab (`runner.tsx`) holds the public `RunnerAgentsSection` only; its own heading is hidden visually. When the chosen agent's tool is not signed in or out of quota, the overview offers only agents with another tool (`nrAgent.status` reports each option's `tool`). The chat agent's settings open as a dialog over the page (`/agents/chat/new`, `/agents/chat/:onlineAgentId`, `client/online-agent/edit.tsx`, returning to the outlet context's `back`); there is no list of chat agents. The runtimes tab ends with what each sharing choice means (`runtimes-sharing.tsx`). When a plugin page lacks something people need (the model services table counts a service's models without naming them; its editor lists them), report it to the Agents plugin instead of adding NocoReach panels around or over its pages. `/runtimes`, `/models` and `/usage`, where one release kept these pages in Settings, redirect to the tabs. Enabling a discovered agent on an online runtime and making it the project default is one action (`PATCH /api/agents/:id`, then `nrAgent.saveDefault`), with the catalog's suggestion or a default as its good-at. Actions show only to holders of the matching grants. Agents on a runtime are called local agents everywhere, and the plugin's page descriptions, sharing labels and Chinese term for a runner machine are reworded through locale overrides (`client/locales/overrides/agents.ts`); recheck them after upgrading the plugin. Online access keeps the application member/admin policy. Manage models and keys through official model management; business model calls use `models.gateway`. The legacy local program and key protocol were removed; do not restore legacy credential migration.

Agents are discovered from Runner tool/model reports and explicitly enabled by an administrator. NocoReach contributes task instructions and read/draft actions through `agents.setDefaults`, applies them at startup, and preserves server-side actor, owner, run and task checks. Application-owned online agents are separate from these Runner definitions and use the public model gateway through replaceable ports. Keep their project read tools and scoped task tools in `server/nocoreach/online-agent`; never restore the removed plugin executor compatibility provider or import plugin internals. `query_data` (`query-tool.ts`) reads each data source through the service method its page calls, after `freshFor` on that page's action for the conversation owner, and answers a denied source alone with `accessDenied`. It stays read only: where a page's own read syncs, inspects or buys (Trends' view, the first indexing inspection, AI search questions), it reads the saved state with the page's helpers instead, and competitor research, whose view may start a paid refresh, is left out. Answers are bounded rows with the cutoff, period, total and next offset, cleaned of credential-named fields and kept under the executor's tool output limit; add a source there when a data page gains one. Model services also power application-owned analysis through `models.services` and `models.gateway`. New task › Organize with AI (`POST /nocoreachTasks/draft`, `server/nocoreach/task-draft.ts`) is one such call: the idea, project memory, playbooks and only the pages the idea names, with their saved 28-day figures (`SiteContent.list`, behind `nrSiteContent.list`), go in as JSON data; the answer is checked like a playbook draft (422 when unusable) and a background sentence citing a figure absent from the input is dropped. It saves nothing and needs `nrTasks.draftManual`; the draft's short Why, edited in the form, is created as `evidence.why`.

Runner conversations expose `business actions`, `business action`, and `business task create` through `server/routes/chat-business.ts`. Enabled conversation agents act with the current user's business permissions; do not require an assigned `nocoreachTask` run for ordinary chat operations. Reuse registered business actions and `ManualTasks`, including membership, ownership, revision, and workflow checks. Task mutation commands available to conversations use an explicit allowlist: human reviews, manual execution attestations and publication confirmations hand off to the task page. New task commands remain browser-only until explicitly classified. OAuth, header-based credential setup and connection operations requiring browser session confirmation hand off to the existing connection panels; never synthesize confirmation headers for a run. Assigned task runs retain their snapshot/result boundary and do not inherit the conversation bridge.

See [online task help](../../docs/ONLINE-TASKS.zh-CN.md) for user instructions. Online task tools rebuild the conversation owner's authorization context for every call. `task_list` paginates across authorized projects, with owner, creator, participant, readable and Runner-executable scopes; `task_get` returns bounded metadata and Runner choices, never raw execution snapshots. `task_execute` only allows `setAgent`, `startTask` and `retryStage`, invokes the registered business action with the current account name as well as its ID, and uses a stable per-turn/input request ID for duplicate delivery. Preserve business command grants, ownership, revisions and Runner admission. Human reviews and publication confirmations stay on the task page. Returned task links include the deployment base path and `projectId`; task deep links select only a project present in the current authorized catalogue, with no fallback for an invalid or inaccessible explicit project.

### Enqueueing, selection, and retries

- `server/nocoreach/execution/agents-runtime.ts` registers the `nocoreachTask` subject. Enqueue official runs inside the business transaction, emit events after commit, and synchronize results through `pluginRunId`. Keep review, revision, and cancellation checks in business services.
- `nr-task-agent:<project>` preserves existing Agent defaults and repository constraints. Select the Agent on each task through `evidence.work.agentId`, which overrides any stored default; administrators configure or clear the current project default in the Agent page's Tasks › Settings dialog through `nrAgent.saveDefault`, with revision and enabled-agent checks. Record the actual Agent ID/name in each business run. Only the owner or an administrator may reassign, and never while queued, running, completed, or closed.
- A task an accepted document is handed over to (`approveStage` with `next`, Accept and start) is started once the approval commits, by `startHandedOver` in `service.ts`, with the start card's defaults from `shared/task-start.ts`: the playbook just chosen, the task's or project's Agent or the only one (`startAgent`), and the default publishing target or the article found from its page, with the languages it writes (`defaultDelivery`, `deliveryPlan`, `choiceLocales`, `translationLocales`; a translation playbook passes `translate`). It runs the start card's commands (`setAgent`, `linkArticle`, `startTask`) through `updateTask`, each with its own revision and checks; Agent status and the page lookup are read outside the task lock. Whatever `startBlockers` reports — several Agents and no default, none, several targets with no default, a target that is gone, an article to pick, a repository change without a repository — leaves the task at Start after review, whose card says so (`taskDetail.handoffNotStarted`) and marks each item where it is chosen. A failure is logged and never undoes the approval. Change these defaults only in `shared/task-start.ts`, so the start card and the hand-over agree. Opportunity hand-offs still create tasks that wait for Start (2026-10-08 decision). The parent's `related` entries carry the next task's number and standing for its done card.
- All tasks, including research and drafts, require a Runner Agent. Online agents are chat-only and must never appear in task options or dispatch paths. Evaluate Runner readiness using the current user's official eligibility, outside business transactions to avoid single-connection deadlocks.
- Manual takeover uses `runs.withdrawQueued` in the same transaction to exclude simultaneous official claiming. The read-only subject `assemble` must not change business state. Cancellation must complete even when the Agent is unavailable; record failed PR cleanup and instruct the user to close it manually.
- Task runs are enqueued with one attempt, so a run whose Runner the Agents sweep takes back (`runnerOffline`, `leaseExpired`, `startTimeout`) fails at once. Every deploy restarts NocoReach, and a run working through the restart loses its lease that way. `server/providers/nocoreach.ts` takes the instance's start at registration (Studio restarts the application inside its host process, so not the process start), `TaskService` keeps the latest starts in `nr-app-starts`, and `restarts.ts` attributes such a failure to a start between the run's hand-over and the failure, at most five minutes before it. The business run records `restartedAt`; a `plan`/`build`/`article` run still current on its Agent step is started again once per step for each restart through `queueAgentRun` (`retryAfterRestart`, recorded as the system's `retryStage` with note `serverRestart`, the new run carrying `autoRetry`), acting for the same person after rechecking their authorization. Review, publishing (merge), close and revert runs, a run someone asked to stop, and a step that moved on are never retried this way.
- `server/app.ts` registers `server/routes/agent-retry-guard.ts` before plugin routes, blocking generic HTTP/CLI retry only for `nocoreachTask`. Business retries must go through TaskService to check stage and review state and create new input snapshots. Copying the old subject into a new official run bypasses those checks. Replace this guard only when upstream `SubjectBinding` provides an equivalent retry extension point; other subjects retain official behavior.

### Capabilities, materials, and sources

- `execution/task-business.ts` provides business capabilities, presets, and run-specific `task data` / `task draft` commands. Validate capability grants, caller/owner eligibility, revision, and run state together. `task draft --content-file` accepts complete multiline drafts and stages them without advancing the workflow stage.
- `execution/task-materials.ts` delivers materials through official mounts. Keep bodies in immutable business input snapshots; `nr-task-materials:<pluginRunId>` only references the snapshot. Preserve file locations in prompts. Deliver knowledge and Skills with the input snapshot.
- Paginate long materials by offset. Runners receive complete immutable mounts. Do not let a shared budget crowd out other materials.
- Built-in Skills live in `skills-builtin.ts`; each has a `since` version. Reads overlay missing built-ins and their localized summary keys without writing; mutations persist them under the library lock, and startup upgrades existing libraries. Skip names already present and never restore intentionally deleted built-ins. The marketing Skills are vendored in `skills-bundled.json` from coreyhaines31/marketingskills (MIT) at a pinned commit: regenerate it only with `scripts/sync-marketing-skills.mjs` (it keeps the license and leaves out evals). Built-in playbook steps name Skills by id; a Skill imported under that name stands in for it. Each built-in also has a `summary` i18n key: a Skill that keeps a built-in's original description (or an imported copy of it) is listed with `summaryKey`, and the page shows that short "when to use" in the UI language while the Agent still gets the stored description.
- `execution/community-materials.ts` reads original posts and replies from configured forum connections. Use official briefs prepare outside the claiming transaction to create immutable source snapshots. Limit access to configured forum domains, five topics, 100 posts per topic, and a total body budget. Record missing/truncated content with stable codes and parameters, translate it in the UI, and retain readable explanations for the Agent. Do not relax Runner local tool policies. Isolate sources and candidate drafts by business run.
- `allowedPaths: []` permits the entire repository with no additional directory restriction. Nonempty values permit only matching files or files within matching directories. Keep Runner instructions, repository settings, and `allowedPath()` validation consistent while preserving task scope, repository rules, and Runner policies.

### Results and execution records

- `/results` projects existing task evidence through `nrTaskWork.board` (the dashboard), `results` (`/results/all`) and `result` (the drawer); it has no result table or navigation badge. The dashboard counts only the project's own work — site-wide metrics belong to Insights and the data pages. A result's `phase` is `live` once the observe stage started, `pendingLive` while its flow still has an observe stage ahead, otherwise `delivered`; page totals add each live change's latest checkpoint only when that source's days are all covered. New observation snapshots record valid GSC/GA4 date coverage. Shared comparison presentation treats unknown or incomplete coverage as unavailable and a zero baseline as an absolute difference only; do not backfill old snapshots or infer causality.
- `nrStrategy.createFromResult` freezes the server-read observation in `resultSource`. Strategy JSON stores `resultOpportunities` and `resultSubmissions`; manual cards bypass daily analysis identity merging and expiry. Keep target creation, source and successful submission mapping in the existing strategy transaction. Retry the same frozen request with the same UUID; creation never starts execution. Preserve source when an opportunity is handed off, and keep basic submission deduplication separate from similarity detection.
- Handing off an opportunity creates one task per place to change (`shared/opportunity-parts.ts` `partsOf`): each page a cited change asks to improve or fix (`optimize`/`technical` with a URL, never an `audit-*` issue, which spans many pages), one place for the releases to announce (`distribute`) and one for the posts awaiting a reply (`reply`). Other cited changes are background for every task. Fewer than two places is one task, exactly as before. `nrStrategy.handOffPlan` lists the places with their label, task title, playbook and the open task already covering each (`server/nocoreach/opportunity-hand-off.ts`; a task from before places existed covers the places matching its pages or article slug); `confirmDirection` creates the ticked `parts`, or every uncovered place when none are named, in one strategy transaction. Each task keeps `evidence.part` and `page`, a brief that opens with `opportunityTasks.scope` in the request locale, and its playbook as `suggestedPlaybook`; its proposal keeps `part` and no copy of the evidence. There are no parent tasks: siblings are found through the proposals sharing `insight.id`. Code that reads a task's cited changes uses `ownSignalIds()` so a place's task never claims, numbers, looks up or briefs the opportunity's other pages (`numberPages`, `pageUrlsOf`, `flowRunInput`, `verdict-coverage.ts`).
- Daily analysis keeps a re-raised opportunity's id, number and first-seen day by identity, by a matching `existingId`, or as the same thing in other words (`shared/strategy-pending.ts` `sameOpportunity`): the same cited signals and the same target, or the same title apart from digits. Signals alone never merge, since one digest signal can back different actions; a card whose latest copy was handed off is not reused. An undecided card stays pending for `opportunityKeepDays` (14) after the newest batch that raised it, counted from the latest analysis, unless a later card replaced it: the same opportunity, or the same target, raised again by a newer analysis, whatever was decided on that card. Restoring keeps a card pending. The Opportunities page and the menu count share `opportunityState`. An ignored opportunity keeps the changes it cites off Insights' to-do whichever analysis raised it (`signalDisposition`), since the analysis never raises it again. Every save of verdicts (the daily analysis, `reviewSignal`, `reviewSignals`) runs `settleVerdicts` (`verdict-coverage.ts`): a change judged `do` that no opportunity of the latest analysis cites becomes `skip` with the reason when a task (handed off from it, from an opportunity citing it, or about its page), a pending opportunity (citing it or about its page) or an ignored one covers it; otherwise an opportunity is written from the change (`confidence: verify`), reusing an earlier card for the same thing. Pages compare without scheme, `www.`, trailing slash, query or fragment. Reasons use the project's analysis language.

- The task page is written for the people who run marketing, on one skeleton for every state (`client/pages/task-detail/layout.tsx`, `styles.ts`): a two-line header (the title with its T-number in grey, the status Tag and the menu; then the playbook's steps as a row of Tags joined by chevrons: done steps ticked in green, the current one outlined in violet for a person's step or blue for the Agent's, the rest grey; the highlighted step says where the task stands, so no "Now:" text follows; while an article's other languages are translated, the Agent's step the task went back to reads Translate, here and in Tasks and Tasks › By Agent, through `stageName(stage, work)` in `client/pages/playbook-model.ts`), then on the left the card for what to do now (`StageCard`; only its content changes between states, and the effect shows there once live) and the activity card with the one-line message to the Agent (also where the start's instructions go: the start card has no note of its own, and a run's `notes` keep the messages left before the start, the first five, with the latest five within 6,000 characters, `runNotes` in `execution/flow.ts`), and on the right, always in this order, ✦ Why (the reason and View evidence; Why this change while a change waits for review), Properties and Performance. Below 1280px the columns become one: Why, Properties, now, Performance, Activity. The page uses four text styles only (`text.title`, `text.cardTitle`, `text.body`, `text.muted`; labels are `text.muted`), every card is the shared `Card` with the same radius, padding and spacing, and a card holds a single level of boxes: fields and controls, never another bordered or shaded box (diffs, before/after tables, warnings and reply drafts are drawn with rules and tints). Do not add another size, weight or shade, or a card of a different shape. An article is reviewed as its readers will see it (`ArticlePreview` in `task-detail/article-preview.tsx`: the title, the description as the lede and the body rendered at a reading measure, the one place with its own type sizes), with one Preview | Changes switch per changed language, Changes being field by field against the version it was written from (Preview first when the language's body changed; a new article, or a language the article did not have, has one version and no switch); Markdown is rendered without raw HTML, http(s) images load without a referrer, relative links and images are read against the article's page on its site (`localePageUrl`), and an image that does not arrive shows its alternative text and Could not load. The card opens with tags rather than a sentence: the target by its own name with a mark for its kind, New article or Update article, and the status it is published with (Save as draft, Make draft); a new article adds its address, a changed one names its title and its address only when it changes. Single-value fields never get a diff block (`FieldDiff` in `task-detail/article-field-diff.tsx`, also for conflicts and drift). Language tabs carry no change counts, and a new article is named as one on the live card; an article has no release notes to edit or show, since no target receives them; an article in several languages is reviewed in its primary one first and translated after approval (`translationPending`, `articleLanguages().pending`; flow in [ARTICLE-PUBLISHING.md](../../docs/ARTICLE-PUBLISHING.md)); Read full screen opens the article's reading page, a child route of the task (`/actions/:taskId/article?lang=&view=`, `task-detail/article-reader.tsx`, a `RouteChildPage`) that gets the task, its command function and the step's draft scope through the task page's `Outlet` (`TaskPageContext`), so feedback or an edit started there is the card's own; Back to task and Esc return to the task where it was scrolled; a language with no text is left out of the tabs, with a line saying which. Articles and documents are written in `MarkdownEditor` (side by side with the rendering from 1024px, Write and Preview tabs below). What the Agent says about its work is summary first (`AgentNotes`: the article's `summary`, else the first paragraph of its notes, at most three lines, with Full notes on demand); the page change's What changed shows three lines with Expand. Once live, the card names what changed in one line (`LiveChange`: the article's changed fields or the page change's visible changes) and opens that version's change on demand; the activity's View opens the same (`VersionChange`), with an article compared field by field against the version it was written from (`ArticleReview` with `settled`, which leaves out review-time conflicts). Keep pull requests, branches, file paths, check output, Runner/model details and error codes off it. They belong in the Technical details dialog (`?details=result|runs`), which reuses official `RunHeader` / `RunTranscript`; `?run=` selects a historical run and opens that dialog on its runs. Only participants and administrators may read transcripts. Show the actual model/Runner, tool inputs/outputs, and permission denials there. Business failures take precedence over tool-turn completion. A failed run's card (`failureOf` in `client/pages/task-detail.tsx`) explains the official `failureReason` in plain words and may name the computer and the coding tool from the run's latest execution snapshot when the failure is about them (sign-in, connection, network, quota), never a machine hidden from the reader; the tool's own `failureDetail` goes to Technical details only, for those who may inspect the run. Where trying again cannot help (sign-in, setup, model), Try again stays available but is not the primary action. The card is an error notice (`StageCard` with `error`) whose other actions are Switch Agent (opens the Agent picker in Properties) and Message the Agent (focuses the composer), shared through the `TaskActions` context; completing the step by hand is in the ⋯ menu, never on the card. Copy never points at a position (above, below, top right): it names the card or field, because the columns reflow below 1280px. The Why card reads `evidence.why` first (plain text, at most 300 characters; hand-off drafts send it as `why`, else the opportunity's `reason` is kept), then falls back as `whyText` in `task-detail/evidence-model.ts` lists, ending with `firstSentence` of the objective or brief. A run with `restartedAt` says NocoReach was updating instead of naming the computer, and is left out of the card's failures in a row; a run with `autoRetry` says it started again after the update, and Technical details › Runs gives the restart time and the official reason.
- Validate `report.kind` separately for research, community replies, and content results. Preserve `sources`, `asOf`, and `uncertainties` before human review. `report.asOf` allows up to 1000 characters; do not truncate timing notes covering multiple sources. Instructions and validation share the limit, and oversized-result errors identify the field and limit.
- Runner guidance fails a step only for what it cannot do without: a missing credential or tool the step needs (gh not signed in for a build or merge, no access to the repository) or a conflict, never by bypassing limits or installing software. The task's own Skills come first; a tool another Skill on the computer suggests never fails a step (T-35, 2026-10-24). An Agent that cannot finish reports `error` as `missing_tool`, `tool_signed_out` or `quota_exhausted` (else `agent_failed`) with a one-line `message`, and keeps what it got in `content`. These codes and the official failure reasons are grouped in `shared/run-failure.ts`; keep the result rules, `client/pages/task-detail/failure-model.ts` (the task page's wording) and `AgentStore.health` (Agent › Who does the work, which reads the business run because an Agent that fails a step itself completes its official run) in step. Failures every Agent on a computer shares (missing tool, tool sign-in, network, setup) never offer Switch Agent; after the same cause twice in a row the card says what to fix first instead of suggesting Try again.
- A failed run keeps why and what it got. `TaskService.finish` records the official `failureReason` on the business run and stores content from the Agent's `ok=false` answer, or from a result it submitted before the Agents plugin failed the run, under `nr-task-partial:<project>:<task>:<run>` (`partialAt`). `partialOf` falls back to a `task draft`; `nrTaskWork.get` returns it as `partial` for the latest run, shown on the failure card and in Technical details › Runs. `queueAgentRun` hands the step's latest failed runs' content to the next run as `unfinished`; a stopped run or a success ends the search. It never becomes an artifact by itself: Finish this step with it goes through `recordManual`.
- `task result --content-file result.json` uses the existing `nocoreach.tasks/propose` capability. It validates and stores one immutable result per business run; identical submissions are idempotent. Corrections happen before acceptance, with at most two correction retries instructed to the Agent. The official completed event consumes this snapshot; cancellation/failure never consumes it. The final summary remains a fallback for Agents without the command. Do not add a second executor, change plugin-owned run storage or parse arbitrary prose for JSON.
- Result sources are either `{title,url}` (HTTP/HTTPS without credentials) or `{title,material}` (`context`, `sources`, `knowledge`, `skills` within the producing run). Only exact historical mount aliases and that task's `nocoreach://task/<id>` normalize to materials. Render materials as text, never filesystem links. The compatibility parser removes only the exact `Local continuation saved: <path> (<40-hex commit>); not pushed.` footer; retain the original official summary for diagnostics.
- `recoverResult` is an explicit revision-checked task action, limited to the latest `invalid_agent_result` plan run at the current Agent step with a following human review. Read official completion outside the business transaction, then recheck owner/admin authorization, actor/owner eligibility, cancellation, current stage/artifact, and absence of active work inside it. Preserve the original failure, audit the recovery and never replay build/merge/revert operations or grant approval automatically. See [task result help](../../docs/TASK-RESULTS.zh-CN.md).
- `execution/agent-result.ts` manages result validation and Runner instructions. Build results must include release notes, page validation evidence, and change comparisons, returning explicit empty values when verification is unavailable. They also carry `visibleChanges`, the before/after a visitor or search result sees, in plain words, for the owner's review. It stays optional at the result boundary, so older Runners keep working, and `TaskService` drops malformed entries instead of rejecting the build.
- Business tests live in `tests/nocoreach/`. `agents-app.test.ts` covers the official Runner protocol against real plugins and a database. Check relevant coverage when changing enqueueing, materials, cancellation, retries, or CLI distribution.

### Article publishing

See [ARTICLE-PUBLISHING.md](../../docs/ARTICLE-PUBLISHING.md) for the model, states and limits, and [ARTICLE-API.md](../../docs/ARTICLE-API.md) for the `http` protocol.

- Publishing targets are per-project settings sealed in `nrVariables` (`server/nocoreach/articles/targets.ts`); credentials never reach the browser or the Runner, and changing a target's address or repository requires its key again. Saves need the browser confirmation session, like collector credentials. Validate the complete settings before persisting them, including the ten-target limit, so rejected additions leave existing settings readable. Editing a target keeps its position; `defaultTargetId` (`setDefaultTarget`, cleared when that target is removed) decides which target a new task starts with, falling back to the first. `playbookTargets` (`savePlaybookTargets`) overrides it per playbook with a target id or `'repo'`; removing a target drops the entries naming it, and no new target may take the id `repo`.
- A task's delivery is frozen at start in `work.delivery`. Article change steps run in mode `article` without a repository; the source article is an immutable snapshot delivered as the `article.json` material, and the proposal is validated against the target both by `task result` and on acceptance. Keep target I/O (link, the slug lookup in other targets at start, rebase, publish, export and drift checks) outside business transactions and recheck state under the task lock before recording an outcome. A release to several targets keeps one record per target and derives `release.state` from them; touch a record's state only through the leg helpers in `article-flow.ts` (`legsOf`, `stateOf`, `settle`) so single-target releases from before keep working.
- An article's language is never the project's: the run input's `language` (`flowRunInput`) is what the Agent writes its notes, summary and reports in, while the article is written in `article.languages` (`runInput` in `article-flow.ts`), which every article run gets. A task started without chosen languages names the target's first language as its primary in phase `all` (every language at once, as before). A new article needs a title and body in the task's primary language, whichever the person chose, on its own target; another target is checked once the article has every language (`primaryOn`, passed to `cleanDraft` as `primary`). Keep the Agent's article rules saying so in `agent-result.ts`.
- A draft a target cannot take throws `DraftRejected` (`delivery.ts`): its message is a code for logs and tests (`missing:en`, `locale:fr`, `field:zh.description`, `slug`, `draft:<path>`), its `problem` an `articles.draft.*` message that says what to change, naming languages in Chinese with their code in full-width brackets. `task result`, the article editor and Review again all return `draftRejection(error)`; never send the bare code to the Agent, which took `locale:en` for a setting to fix (2026-10-27, T-47). The client reads such language lists back in the reader's language (`languageList` in `client/i18n/index.tsx`).
- A translation playbook (`translatesArticle` in `shared/playbook-catalog.ts`: `sync-translations` and its copies) starts an article task in the translation phase from the article as published (`startTranslation` in `article-flow.ts`), reusing the languages flow rather than a separate one: never reintroduce a primary round for it, and keep the start card sending the source and the languages to write. Whether a language is missing comes from the article's own text (`articleLocales`); NocoReach does not know when a translation is out of date, so do not mark one as stale.
- Publishing writes only the approved artifact's changed fields, adopts a write that already landed, treats a field both sides changed as a conflict, and blocks on a Git-only edit when the target exports to Git. Never publish from a later draft than the approved artifact, and never mark a release live from a CMS save alone: export and page checks are separate states.
- A failed publish says where it stopped and why (`PublishFailure` in `delivery.ts`, recorded on the leg by `article-flow.ts` and logged at warn level). The detail comes from `errorDetail()` in `provider.ts`: an `ArticleError`'s own message, the network layer's code, reason and host, or another error's name and message, one line, clipped and with credentials masked. Provider catches of a request that got no answer keep the transport error as the cause (`unreachable()`); do not drop it with a bare `catch`. The task card keeps the plain-words reason; step, code and detail appear in Technical details only.
- `nocobase-api` is check-before-write and cannot prevent a stale editor form from overwriting a publish; the overwrite watch only reports it. Do not describe it as guaranteed. Build changes to files a target's exporter owns are blocked (`pr.protected`).
- Export and overwrite checks compare every written field against the approved artifact, including its normalized publication status. Manual draft edits preserve the existing draft status when editing content fields. New articles on a target that stores a status default to `draft` on the server; publishing one directly is an explicit choice in the editor. Omitting status from that baseline falsely reports a new draft as overwritten.
