# NocoReach: Outbound networking

When changing collection, OAuth, connection tests, or project-scoped background network calls, check this section and the transaction constraints above.

- `server/nocoreach/proxy-profiles.ts` seals global Profiles, the deployment's default proxy and project/connection references together in `nrVariables`. A live deployment routes a connection through the project's choice, or the default proxy when there is none; `DIRECT` keeps one connection off it. Mock deployments and connections read through collectors (Bilibili, Xiaohongshu, YouTube) never take the default. Design: [NETWORK-EGRESS.md](../../docs/NETWORK-EGRESS.md). `outbound-network.ts` uses instance-scoped AsyncLocalStorage. Inject this transport layer into new collection services. Wrap all project-ID-bearing background/internal entry points in `network.bind`; URL-only previews inherit project scope from the route.
- Explicitly pass the project fetcher to Google OAuth/sync. Derived Google/DataForSEO features share the actual connection's settings. Project icon homepage and image requests share the website egress. The connection switch (live) and profile choice (mock) live in `client/components/connection-network.tsx`; Settings › Network is `client/pages/network.tsx`, which shows the Profile list in `client/pages/proxy-profiles/` in mock deployments. A live deployment shows `proxy-profiles/network-settings.tsx`: the proxy's state, edited in the `proxy` child-route dialog, then every proxy-capable connection of the current project with its switch and an on-demand check. Checks call `testConnection` per connection and are cached under `checkKey` by route, so changing a switch or the proxy re-checks only what changed. `testConnection` returns an unanswered request as `reachable: false` with a `reason` (timeout, reset, refused, dns, certificate, other) and whether it went through the proxy; configuration and shutdown errors still fail the call. Keep the list in `networkSources` in step with `CONNECTIONS`.
- A request that gets no answer fails with `networkFailure()` from `outbound-network.ts`: status 502, the original diagnostic `code` and `name`, plus `reason`, `proxied` and the `host` it was for (the site's name, never a pinned IP). Its message is the NETWORK-EGRESS §3.3 sentence for that reason and route, keyed in `shared/network-failures.ts`; a rejected redirect or an oversized body keeps its earlier message. Direct public reads in `public-sources.ts` (DNS, socket, TLS and the 15-second timeout) fail the same way; cancellations and other errors pass through unchanged. Do not change codes or retry predicates to add hints. A caller that wraps a failure keeps it as `cause` and reads it with `unreachableOf()` (Google's `googleJson` and connection routes, website-content discovery). The client recognizes these sentences in either language, alone or behind the part that failed (`client/lib/network-failure.ts`), and `$legacyText()` translates them there too. Connection panels and the Skill link dialog show errors with `ConnectionError` (`client/components/connection-error.tsx`), which adds a link to Settings › Network and the certificate ⓘ; saved collection errors use `NetworkSettingsLink`; Google's code-only `network_*` errors pass `network`.
- Fixed APIs reuse bounded pools by origin and Profile version; public fetching and connection tests use separate dispatchers. Do not change global fetch/dispatchers or Studio environment variables. Profile updates send new requests through new connections; release old connections after in-flight requests finish. Close pools on application shutdown.
- Decode numeric HTML character references from collected or displayed external text only after validating the Unicode code point. Preserve out-of-range references as text so a malformed title, plain-text response or sitemap cannot throw during collection or rendering.
- Public fetching must use `download` public-IP validation and fixed-IP tunnels while retaining TLS verification for the original hostname. Proxy failures must not fall back to direct connections.
- `socks-proxy.ts` establishes SOCKS tunnels: `socks5` resolves locally and `socks5h` through the proxy. Public fetching connects to validated IPs with either protocol. Clean up sockets during connection establishment and retain bounded pools.
- Collector HTTP responses, subprocess output and browser-extracted output are capped at 20 MiB across both application and Collector boundaries. Automatic content ingestion retains its JSON string-length check with a 20,000,000-character cap and 500-record batch limit. These are per-response/batch limits, not cumulative site storage quotas.
- Collector connections can be configured by administrators through `nrCollectors` and the shared Data connections card. `CollectorConnections` seals project/platform overrides in `nrVariables`; deployment-owned `browserCollectors` remains the fallback only when no override exists. Saves are session-bound and revision-checked, reserve against source operations before awaiting I/O, and atomically invalidate verification with the credential write. Never expose tokens or reuse them at a changed address. See [connection setup](../../docs/COLLECTOR-CONNECTIONS.md).
- Collector platforms (Xiaohongshu, Bilibili, YouTube) show their saved records on Community data pages (`client/pages/data-<platform>.tsx`) through a `<resource>/report` action built with `collectorPeriod()` in `server/nocoreach/collector-views.ts`. Collectors return a publication date and the counts read at collection time, never a series: count records by publication date (first-collected date when unknown) and present counts as latest snapshots, not growth. Connection panels keep configuration and collection controls with a saved count and a link to the data page; do not render result lists in them. Reports compute metrics, the publishing `trend` (daily, weekly or monthly by window length) and origin `groups` over every saved record of the period, but return only the first `limit` records in the requested `sort`/`order`; sort on the server, never the shown page. A Bilibili video counts under its search terms; only a video found by link alone counts under that link (detail reads add a `video` source to searched videos). Pages share the layout in `client/pages/collector-content.tsx` (trend card, sortable table with Agent hand-off, origin card) like the other Community pages. While a collection runs, poll the lightweight `status` (YouTube `summary: true`) and read the report again when it ends. Grant each new `report` action through the platform's `use` capability and add the page to `REACH_PAGES`.

- Collector connection panels (not the data pages) expose project/platform-scoped `clear` actions under each platform's `configure` capability. Keep two sequential confirmations bound to the initiating session, project, revision and permission lifetime; the dispatcher requires the confirmation-session header for all three platforms. Clearing rejects active collection, reserves against new reads before awaiting storage, rotates the source revision, and removes saved records plus collection/analysis metadata while retaining connection credentials and discovery criteria. YouTube also removes captions and pauses automatic collection. Reload the panel status after success and never reuse a previous project's report as mutation input.
- Collector data page reports use the authenticated `WorkspaceCache` under `collectorReportKey(resource, project)`, keyed by period, limit and order. Reuse a report read the same local day when the page opens again; read again on a new day, an explicit read/search, Retry, or the end of a polled collection. Connection-panel changes (including clearing) invalidate the platform's keys for that project. Keep data page headers to the single read/search action used by the other Community pages.
- Bilibili sync refreshes saved video details independently of the first search page, oldest collection first, and enriches up to 20 search discoveries. Deduplicate BV requests within a batch, retain the shared deadline and refusal handling, and preserve known values on incomplete refreshes. Successful saved-record refreshes adopt the current configuration revision and new metric timestamps; never carry old freshness metadata onto newly fetched values.
- YouTube production collection uses `HttpYouTubeProvider` and project Collector overrides or deployment-owned `browserCollectors` entries with the `youtube` platform. Select exactly one project-eligible entry; require protocol-v1 identity/freshness/field validation and keep the source/library transaction boundary intact. Production YouTube collection is metadata-only: Collector omits subtitle fields from yt-dlp output and never selects or downloads captions. The protocol-v1 empty transcript is a compatibility placeholder, not evidence that captions are missing. Do not show caption status in the UI. All yt-dlp I/O belongs to Collector. Never reintroduce a local process, direct-caption, alternate-collector or proxy fallback. The default proxy never applies to YouTube; an explicitly selected YouTube proxy left from before fails with migration guidance until an administrator turns it off in the YouTube connection, the only place its switch appears. Fixture normalization requires injected I/O and must remain isolated from production. See [YouTube deployment](../../docs/YOUTUBE.md).
- Runner execution and application model calls do not use these proxy settings. Do not turn them into a host-wide network policy.
- `shared/connect-sources.ts` is the one list of data sources with what each needs, whether a command may connect it (`via`) and its state (`connectionState`, shared with the Data sources cards); keep it in step with `getCatalog()` (the parity test in `tests/components/nocoreach-locale.test.tsx`). `server/routes/connect.ts` publishes `nocoreach connect guide|list|discover|preview|add` to people (not runs) for their own coding agent. Each command runs the panel's own NocoReach action as the person, behind `db.access.require`, `requireAccess` and the project's network route like the generic dispatcher, so a person without a grant is refused the same way. Only `via: 'cli'` sources connect; any other answers with its panel address and needs, and the commands accept no credential fields. Data sources › Use an agent on your computer, beside Find data sources on your website, opens the same `AgentSetupDialog` as the account menu with `connections`, whose prompt sends the agent to `nocoreach connect guide`. The website findings open in a component-state dialog: they come from one homepage read and represent no record.
