# NocoReach: Upgrades and releases

Read the [application upgrade Skill](../skills/nocobase-app-upgrade/SKILL.md) before upgrades and the [deployment Skill](../skills/nocobase-deployment/SKILL.md) before building deployment packages or investigating production issues. Read the [CLI reference](../skills/nocobase-app-development/references/cli.md) before running `pnpm nocobase` commands. The following points differ from the general workflow.

Do not overwrite this application with a fresh template or advance the marker without a corresponding source merge.

Framework packages now follow the `@nocobase/*` versions in Default Template `1.0.0-beta.76` (App Server `3.0.0-beta.2`, App Client `4.0.0-beta.1` without Refine, i18n `2.0.0-beta.1`, Notification `2.0.0-beta.0`), installed together with Agents `1.0.0-beta.18` without merging that template's source. Demo Mode `0.2.0-beta.2` retains the framework baseline introduced by `0.1.0-beta.3`: App Server `3.0.0-beta.3`, App Client `4.0.0-beta.3`, App CLI `1.0.0-beta.27`, DB `1.0.0-beta.22`, Authentication `2.0.0-beta.14`, Authorization `1.0.0-beta.31`, Agents `1.0.0-beta.24` and Jobs `0.1.0-beta.4`; Runner `0.1.0-beta.19` and CLI Client `0.1.0-beta.16` match the Agents protocol update. The Demo-only upgrade preserves these resolved companion versions; the higher peer declarations and coordinated follow-up requirements are recorded below. The Demo Mode server integration with Agents is unchanged from `0.1.0-beta.3`; verify model/chat and Agent simulations with the demo integration tests. These dependency updates do not advance the template source marker. Keep `react-i18next` pinned consistently in the root manifest and workspace override so the host and mock plugin resolve one i18n/App Client identity. Keep the local mock plugin's framework peers aligned and verify it resolves the same App Client instance; installing framework changes in separate passes can retain incompatible peer contexts. See [the integration record](../../docs/AUTH-SESSION-PREPARATION.md) before the next full template merge.
- `README.md` and its `README.zh-CN.md` / `README.ja-JP.md` translations introduce the product and are application-owned. The template's README lives in [APP-TEMPLATE.md](../../docs/APP-TEMPLATE.md); merge upstream README changes there.
- README images are the NocoBase website's NocoReach figures (fictional Acme data, rendered from the product's compiled CSS by the website's `html/_src/reach` scripts), copied as WebP into `docs/images/readme/`; refresh them from there rather than capturing the app. They and `public/assets/` are linked through jsDelivr (`https://cdn.jsdelivr.net/gh/nocobase/NocoReach@main/<path>`), because GitHub serves repository images from `raw.githubusercontent.com`, which is often unreachable from mainland China. After replacing an image under the same name, purge it at `https://purge.jsdelivr.net/gh/nocobase/NocoReach@main/<path>`.
- The README intro videos are the website's films (`nocoreach-intro-en|zh.mp4`) re-encoded to 1280×720 WebM under 10 MB, GitHub's attachment limit for this organization's plan, with the duration and cues a browser recording lacks. They are uploaded as GitHub attachments (dropped into a new issue's comment box, never submitted), and the README puts each `github.com/user-attachments/assets/…` URL on its own line so GitHub renders a player. Re-upload and replace the URLs when the film changes.
- Hub CLI and official Workflow were removed; do not restore them for releases or business features. AI employee, local Agent, and configuration references in old port records are historical.
- Agents `1.0.0-beta.24`, Runner `0.1.0-beta.19` and CLI Client `0.1.0-beta.16` are pinned. The application CLI release is `1.0.0-beta.72`; the template source marker remains unchanged. Runner and CLI Client use Agent Protocol `0.1.0-beta.15` (wire protocol 14), adding conversation output-block previews. Deploy the application before updating runners: a runner newer than the server's supported protocol cannot claim work. Existing supported runners can continue basic tasks during rollout, but need the new Runner for output-block previews. Agents migrations retire the conversation start/fallback/restore operations and add `showInChatList`; conversations created before `1.0.0-beta.15` stay readable but read-only, and their owner can still stop an unfinished run. Keep historical IDs and snapshots; invalid project/task defaults require explicit reselection, never silently map them to a discovered agent. Application response types should name tool IDs as strings instead of leaking the plugin's transitive `AgentTool` type into generated declarations. Drain active runs and back up the database before deployment.
- `client/extensions/nocobase-agent-chat/` and the `agent-composer`, `attachment-list` and `markdown-view` components are the Registry `agent-chat` block, merged three-way to the UI Library at Agents `1.0.0-beta.18` (base: the block at `0.1.0-beta.11`). NocoReach keeps its own `agent-choice` and `agent-picker` (online and Runner agents in one menu), and does not adopt the block's native model picker: online chat stays on `server/online-agent`. The plugin lists a built-in `online` agent whenever a default chat model exists; `runnerAgents()` keeps it out of the panel, which only starts Runner conversations. Runner conversations follow the block: the composer is disabled while a run is open, and messages are AI SDK `UIMessage` parts rendered through `chatMessageSegments`.
- Online conversations use `server/online-agent`, the public model gateway and typed application records, with read-only project/webpage tools from `server/nocoreach/online-agent`. `daily_analysis` reads the saved daily analysis (notes, opportunities with their current standing, verdicts on changes, watches) after rechecking `nrStrategy.state` for the conversation owner; `project_data` metrics add the Insights tiles' totals against the previous period when the owner may read `nrDataViews.overview`. Initial messages and follow-ups share submission and idempotency checks. A conversation started from Insights carries a `subject` (the analysis day, and the opportunity when asked from its line), one opened from a page's AI entry a page subject; `OnlineAgentService` hands the conversation's subject to the host on every turn. `GET /onlineAgents/threads?projectId=` lists only the caller's Insights conversations in a readable project, each with its first question and latest answer, for Insights. Insights keeps one conversation per analysis day (`client/pages/strategy/threads.tsx`): its own input sends to the day's latest conversation or starts one with the subject; a quoted opportunity travels as a Markdown link on the message's first line, which the page and the side panel transcript show as a quote (`client/online-agent/quote.ts`). While the side panel is open the conversation lives there and the page shows no second input. `analysis_rules` reads AI team › Analysis rules through `AnalysisRules.view` after `nrAnalysisRules.view` (with the latest changes each rule found, after `nrStrategy.state`); `propose_rule_changes` (`rules-tools.ts`) checks one kind of change at a time — switches and numbers through `applyRuleChanges`, a new or changed custom rule through `customRuleInput` — and saves nothing. It needs the grant its Confirm uses (`apply`, `addRule`, `updateRule`) and answers `accessDenied` or `rejected` with what to fix; the proposal carries the revision it was read at, so the page action refuses it once the rules changed, and the card then reads as out of date. Store each turn's input once and reconstruct completed history in sequence order. Retain owned history, session isolation, cancellation and crash fencing. No online task adapter, saved `ai` stage or legacy `startRun` support exists. `OnlineProvider.complete` independently serves analysis helpers.
- Repository tasks use GitHub CLI for PR operations; since Runner `0.1.0-beta.15` the workspace notes also tell agents to use the code host's command line, so no application `pr open` command is expected. NocoReach registers no repository access provider, so runs carry no repository credential and `gh` keeps using the runner machine's own login; the runner's `gitTools` wrappers apply only to repositories with a credential in the payload. Do not add alias commands or replace the platform system prompt.
- `agents.runs.retentionDays` defaults to `0` in NocoReach to preserve task transcripts. Deployments may explicitly configure retention. This intentionally overrides the plugin's new 14-day default.
- Declare runtime dependencies in `dependencies`; client libraries, build tools, and type-only dependencies in `devDependencies`. All application plugins, including client-only and disabled plugins, still belong in `dependencies`. Keep `@nocobase/db` and its driver as runtime dependencies. Synchronize manifests and the lockfile; client/server/cli composition roots remain authoritative for plugin registration.

### Continuous integration

- `.github/workflows/ci.yml` runs independent `tests` and `build` checks on pull requests, `main` pushes, and manual runs using Ubuntu 24.04, Node 24, and the pnpm version in `packageManager`. Both jobs use frozen dependency installation. Tests run with two workers and fail if no tests are found; the build targets Linux x64 and includes the existing CLI/Runner build hooks.
- CI runs only `vitest` (`tests/**/*.test.{ts,tsx}`). The `tests/nocoreach/*.browser.ts` scripts start their own disposable development server and are not run by CI, so a UI or authorization change can silently break them. When changing the pages they drive (members, roles, invitations, keys), update and run them: `NOCOBASE_DEV_ALLOW_MULTIPLE=true PLAYWRIGHT_CHROMIUM_EXECUTABLE=$(which chromium) pnpm exec tsx tests/nocoreach/<name>.browser.ts`. Both variables are optional: the first allows them beside a running `pnpm dev`, the second uses an installed Chromium instead of Playwright's download.
- Snowflake IDs count whole seconds and a new process restarts the sequence for the same worker, so a test that closes and boots the application again on the same database within one second can reissue an ID (for example a duplicate session primary key at sign-in). Wait for the next second before booting again, as `schedule-timezone-app.test.ts` does. Await asynchronous permission or effect checks with `waitFor` rather than asserting right after the first render; the deploy workflow runs the suite again on a slower runner.
- CI's two workers on a small runner starve the event loop: React may run a render's passive effects (`useEffect`) after the test, or a person, has already clicked a control that render showed. A ref that a handler reads to check a permission (the connection panels' `accessRef`, Disconnect's confirmation owner) is therefore updated in `useLayoutEffect`, which runs before anything can reach the new controls. Likewise, a page must not decide from a list it is still reading: Insights asks the server for the day's conversation when its list has not arrived, rather than starting a second one (`client/pages/strategy/threads.tsx`).
- Application tests that count NocoReach rows stop NocoReach's background work first: `taskExecution.stop()` and `shutdown()` of the `nocoreach` schedule executor (`jobExecutorServiceToken`), as `classic-import-app.test.ts` does. The timers act on a project as soon as it exists; the analysis timer, at second 10 of every minute, catches up a missed day and writes `daily-analysis:<id>` and `signals:<id>`.
- SQL cost assertions must scope shared-client query events to the measured operation with `AsyncLocalStorage`; application background jobs can open unrelated transactions during a request. Keep zero-transaction/lock assertions, verify that queries were actually observed, and calibrate with both unrelated and operation-owned transactions. Create the measured project's fixture locally rather than relying on an earlier test's data.
- Authentication beta.13 requires full-mount cookie names in `server/config/session.ts` and root-path handling in `server/config/app.ts`; dependency installation alone does not update application configuration. Root and nested mounts must retain distinct session names. App Client beta.2 stores the language under `nocobase.locale:<public mount>`; browser fixtures must use their configured mount.
- Agents beta.20 only auto-creates recommended Runner models. Integration fixtures must explicitly call `createFromAvailable` for other reported models, then apply the enabled state required by the scenario; never assume every reported model already has an Agent.
- Demo Mode `0.2.0-beta.2` shows read-only data status, the deployment reset schedule and system accounts together on one page. Data mutations remain available through the CLI and API. Remove the former `DemoAccountMenu`, `accountSwitcher`, `showFloatingAccountSwitcher` and unused `CardAction`/`CardFooter` adapters when upgrading. Do not pass tab slots, `activeTabLabel`, the removed `chatTools` option or adapter/tool label kinds. Let the plugin preserve the executing administrator during clear/reset and reuse its tracked identity; application cleanup owns business records only. Registered simulations and integrated chat default to enabled, while saved overrides still apply through the configuration APIs. Declare local chat reads (`task_list`, `task_get`, `project_data`, `daily_analysis`, `query_data`) at the server boundary and provide mocks for external work. Preserve collection exceptions and simulation policies during upgrades. Migrate desired reset timing to deployment variables; saved schedules, including disabled ones, no longer apply. The published beta.1 code matches the validated compact-menu preview, but its peer declarations require Authentication `2.0.0-beta.15`, Authorization `1.0.0-beta.32`, Users `2.0.0-beta.10` and optional Agents `1.0.0-beta.26`. This focused Demo upgrade retains the application's existing pins and verifies their integration; do not treat that as satisfying the declared peer ranges. Upgrade the companion packages separately with their account-role source adaptations, permission seed and Agent-retirement migration review.
- CI reports pass/fail status and execution logs directly in GitHub. It does not upload artifacts or deploy the application; no Studio credentials are required. Repository administrators can require the `tests` and `build` checks before merging. GitHub does not re-run a pull request's checks when `main` moves, so after merging `main` into a branch, merge the pull request only once CI passes on that commit: a change on `main`, such as a new interface language, can make the branch fail.
- Pull requests record their change in `changelog/unreleased/<branch>.md` (`/` written as `-`) rather than at the top of CHANGELOG.md, where every open pull request conflicted once another merged and then needed `main` merged in and CI run again. `pnpm changelog:fold` moves the notes into CHANGELOG.md, the latest merged first by their commit on `main`, in a pull request of its own; `tests/logic/changelog.test.ts` checks the notes and fails when CHANGELOG.md gains an "Unreleased" section. The [notes README](../../changelog/unreleased/README.md) shows the form.
- `.github/workflows/deploy-studio.yml` deploys automatically on every push to `main`, including merged pull requests, and also supports manual dispatch. Its job and deployment script both reject non-`main` refs. It tests and builds the triggering commit on one runner, then uses pinned `nb-studio` to upload directly to the `nocoreach` app, track deployment or approval, and verify release identity and health. Studio can reuse the first release stored for an app and commit even when a rebuild produces different archive bytes. The shared deployment script requires the local archive's exact checksum for fresh uploads; only `reused === true` selects the existing release's valid SHA-256, confirmed by a separate `release get` of the same release ID, app and source commit before accepting approval or polling deployment. Pin that checksum through deployment and the final release read, and label the rebuilt archive and reused release separately in the summary. This applies to the `nocoreach-demo` and Solutions `reach` deployments too; do not bypass checksum checks or automatically retry an uncertain upload. It uses the `studio` GitHub environment and never stores GitHub Artifacts.

- `.github/workflows/deploy-studio-demo.yml` uses the same build and nb-studio deployment script, but only through manual `workflow_dispatch` on `main` or a `demo/` branch. Its fixed target is `nocoreach-demo`; the script also rejects non-manual demo invocations. It uses a separate concurrency group, so it cannot replace or cancel the regular application's deployment.
- The pinned Studio CLI (`@nocobase/studio-cli@1.0.0-beta.56`, `@nocobase/app-cli-client@0.1.0-beta.5`) permits 30 minutes for ticket uploads. The deployment wrapper intentionally caps the complete upload command at ten minutes, including command discovery and ticket creation; read commands retain a three-minute process limit. Both deployment jobs allow 75 minutes overall, with a separate ten-minute window for starting deployment polls after upload; an in-flight read and the final identity/health checks retain their own timeouts. Studio reports success before the app has finished restarting, so the health check retries network errors and non-2xx responses every 10 seconds for up to three minutes (never past the ten-minute polling window) and then fails with the last status; an answer with `ok` other than true or another app's identity fails at once, and nothing is redeployed or rolled back. A process timeout means the upload/deployment outcome is unknown, not that Studio rejected it. Before any retry, inspect Studio releases and deployments for the recorded commit and checksum; do not automatically upload again or treat an older healthy deployment as proof of success. Raw CLI output remains suppressed because it can contain upload tickets. A terminal deployment failure includes the polling phase and bounded app/release/deployment IDs in the job log as well as the summary, so read-only log tooling can locate the matching Studio record. Unknown status values and remote error messages, URLs, and log payloads are not echoed. A fixed terminal message in the job log distinguishes pending approval from a succeeded deployment whose active release and health have been verified. These identifiers locate the failure; determining its cause still requires the matching Studio deployment logs.

- Both deployment workflows use the `studio` GitHub environment and its `NB_STUDIO_API_KEY` secret, `NB_STUDIO_SERVER`, `STUDIO_TARGET=linux-x64`, and `STUDIO_NODE_MAJOR=24` variables. Configure `STUDIO_APP_URL` for `nocoreach` and the separate `STUDIO_DEMO_APP_URL` for `nocoreach-demo` (currently `https://studio.v2.test.nocobase.com/nocoreach-demo/`). The shared credential must be authorized for the selected app. Health verification checks the returned application identity as well as readiness.
- To deploy the demo, after this workflow is present on `main`, open **Actions → Deploy demo to Studio → Run workflow** and select `main` or the reviewed `demo/` branch. It tests and builds that exact commit; pushes and pull requests never trigger demo deployment. Keep demo runtime configuration (`nocoreachMock.enabled: true`, `environment: demo`), its existing database and storage managed in Studio. The workflow changes only the application release, not those settings.

### CLI and Runner distribution

- The account menu opens an application-owned, transient CLI setup dialog (`client/components/agent-setup-dialog.tsx`), matching the requested Studio interaction. It is read-only help rather than a record route; tokens are discarded on close. Browser URLs use the runtime application base path and public browser origin. The CLI uses the existing `nocobase-cli` device client ID; rebuild the served CLI after changing its manifest configuration.

- Application-owned `afterServerBuild` hooks in `cli/plugins.ts` build both the NocoReach CLI and Runner universal archives into `dist/runners`. Do not build only in local storage and omit them from deployment packages. Rebuild both distribution products when deploying dependency upgrades.
- `server/config/agents.ts` resolves the distribution directory relative to the configuration module. Do not assume Studio's rootDir is dist. Explicit `agents.dist.dir` overrides remain supported. Before deployment, confirm the actual distribution directory contains matching manifests and archives.
- Fix the Runner application identity and CLI name to `nocoreach`, matching `package.json`'s `nocobase.cli.bin` and published archives. Do not derive them from `/main` or the deployment path.
- CLI release versions are immutable installer cache keys: changing CLI branding, authentication, or packaged code requires a new application version (or an explicit `nocobase.cli.version`). Rebuilding under the same version does not replace existing installations, even when the archive checksum changes. The browser-auth release is `1.0.0-beta.67`; the template source marker is independent and unchanged.
- Validate distribution by downloading into an empty cache, verifying, unpacking, and executing. Also test upgrading an existing earlier installation: confirm the new archive is fetched, `current` switches to the new version, the packaged brand includes `auth` and `login` reaches the device-code endpoint in an isolated transport test, and old versions and user state remain intact. Help text alone is not evidence of runtime authentication support. Verify embedded Studio deployments through the actual application; standalone success does not establish correct host paths. See the [CLI distribution record](../../docs/CLI-DISTRIBUTION-beta63.md) for steps and historical context.

### Configuration and static assets

- Do not hard-code deployment prefixes in routes. Use `resolveAppUrl` for pages, APIs, and dynamic artifacts, and `resolveAssetUrl` for static files. Use shared `AppPaths` on the server and preserve configuration, host logging, and lifecycle binding through `createAppFromRuntime(runtime)`.
- The browser origin must match `app.publicOrigin` / `APP_PUBLIC_ORIGIN`. Do not disable origin checks to resolve authentication failures. Writes through a remote development proxy affect the target backend.
- `CDN_BASE_URL` is a build variable requiring a full HTTPS URL and trailing `/`. It defaults to `./` and is ignored in development. Precedence is process environment, `.env.local`, then `.env`. Upload the complete `dist/client/` assets and configure CORS; the application server still retains its client directory and HTML injection. Docker source builds use the same build-arg name; runtime changes cannot alter compiled asset URLs.
- Development watching excludes this application's entire `dist/`, but not linked workspace dependencies. Auxiliary Vite tests use isolated temporary `cacheDir` values; never clear or rewrite the cache of a running development server.

### Classic data import

`pnpm nocobase app import-classic` is implemented in `cli/commands/import-classic.ts`. Run it on a machine that can access classic Postgres through `CLASSIC_DB_*`. It calls the target application's `nrImport` actions over HTTP with a root user's `NOCOREACH_API_KEY`, rather than connecting directly to Studio's database. Decrypt classic secrets on the source machine and reseal them at the target. Import is a separate data migration task, not a routine deployment step; consult the [port record](../../docs/PORT-PLAN.md) before proceeding.

While an import writes, `ImportHold` (`server/nocoreach/legacy/app.ts`) keeps NocoReach's background work off the data, which would otherwise act on a project as soon as its snapshot lands. Every `nrImport` call except `plan` takes or renews a five-minute lease at its start and end; `finish`, or a `begin` that fails, releases it, so a CLI that dies midway lets the timers run again five minutes after its last call. The provider runs each timer firing through `LegacyApp.tick()`, which skips (does not queue) a firing while held; the Scheduler's daily analysis firing completes as `cancelled`, and the minute timer catches the day up afterwards. `begin` waits up to 30 seconds for work already running before it clears or writes anything, and answers 409 otherwise: timer firings, the analysis job, and the run `DailyAnalysis.start()` leaves in the background, all registered with `importHold.track()`. Register any new background work that outlives the tick or request that started it the same way, or `begin --replace` can clear tables under it. The hold is in memory and assumes NocoReach and its timers run in one process, as on Studio; requests people make in the application during an import are not held.
