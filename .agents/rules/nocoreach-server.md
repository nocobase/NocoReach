Follow the application Skill references for [routes](../skills/nocobase-app-development/references/server-routes.md), [HTTP contracts](../skills/nocobase-app-development/references/http-api.md), [services](../skills/nocobase-app-development/references/services-and-jobs.md), and [data access](../skills/nocobase-app-development/references/database-and-data.md). ### Compatibility layer and authorization

- `server/nocoreach/*.ts` contains ported classic services, retaining dense formatting and `// @ts-nocheck`. Put NocoBase 3 adaptations in `server/nocoreach/legacy/` and business behavior in services. Do not rewrite the entire compatibility layer as incidental cleanup.
- The compatibility layer rebuilds repositories, filters, transactions, resource actions, timers, and other classic interfaces. Classic advisory locks use keyed in-process locks. Store settings in `nrVariables` and seal secrets. Users come from NocoBase 3 accounts; transactional reads use the caller's connection.
- `server/providers/nocoreach.ts` assembles the layer and manages timers. `server/routes/nocoreach.ts` dispatches `/api/nocoreach/<resource>/<action>`. Each action checks current framework permission-set assignments through `server/access/service.ts` and `server/nocoreach/policy.ts`. The retained `nr-members` snapshot is a migration/rollback artifact, never a runtime role source. System administrators retain business access; scoped keys still constrain them. Page or collection grants do not replace business authorization. See [Access](../../docs/ACCESS-DEVELOPMENT.md) and the Chinese [cutover procedure](../../docs/ACCESS-CUTOVER.md).
- Notifications use the official Notification plugin and its configured in-app channel; inbox adaptation lives in `legacy/notifications.ts`. Daily analysis is the Scheduler target `nocoreach.daily-analysis`, with runs available through the official Scheduler API/CLI. `pm.get('workflow')` and `workflows` are compatibility names in `legacy/schedule.ts`; official Workflow was removed and must not be reintroduced.
- Google OAuth callbacks require the current signed-in account to match the state initiator. Re-read enabled account status and current NocoReach administrator eligibility before token exchange and after upstream I/O, before saving credentials. Callback attempts consume state once and clear the nonce cookie; signing out or switching accounts requires restarting authorization.
- Server routes own their authorization; page `auth`/`authz` is not server protection. Register background work through providers rather than directory discovery.

### Transactions and synchronization

- Reddit collection persists its fixed query scope, business cutoff and per-term request keys in the existing snapshot before paid I/O. Successful terms are retained during a partial round. Only explicit terminal errors allowed by DataForSEO's [error reference](https://docs.dataforseo.com/v3/appendix/errors/) and [live endpoint guidance](https://dataforseo.com/help-center/best-practices-live-endpoints-in-dataforseo-api), with an explicit zero total cost, retry automatically (at most twice, after 1h and 6h). Transport, malformed and missing-cost failures require reconciliation and remain blocked across cache expiry. Legacy failed snapshots also pause because their billing evidence is missing. Manual checks obey the same limits; pre-request connection/budget refusals can recheck the original key after settings are corrected. Polling and not-due scans only compute scheduling; an executing batch adds one short snapshot transaction before its existing final transaction. No HTTP runs inside either transaction, and no new lock or scheduler is introduced.

- SQLite uses one connection. Do not wait for another database connection inside a business transaction. User reads must use the caller's transaction. Keep model gateway requests outside business transactions.
- Google sync claims work in a short transaction, collects outside transactions, then validates and commits in another short transaction. Never wait for OAuth or Google APIs while holding a transaction. A single-instance `busy` guard protects in-flight batches. Pausing cancels the old batch; its results must not be committed even if immediately resumed. Limit collection to two minutes per batch and retain bounded retries.
- `transactionContext()` in `legacy/database.ts` isolates snapshot caches and construction promises. A transaction must neither wait for snapshot construction outside its scope nor publish uncommitted results to shared caches.
- Do not edit executed migrations or migration history tables to silence checksum errors. Collection files are generated caches; see the [migration reference](../skills/nocobase-app-development/references/migrations.md). Preserve compiled migration and seed `.manifest.json` generation; do not regenerate manifests for installed dependencies.
- Data health (`server/nocoreach/data-health.ts`) gives each row needing attention a `fix`: `retry`; `settings` for a refusal only a changed setting cures (Google `invalid_grant` or `resource_changed`, a refused GitHub token, X's spending cap, a paused daily analysis, a competitor refusal with a 4xx status other than 408, 422 and 429, recorded as `lastRun.configError`); `verify` for an uncertain DataForSEO result (`lastRun.uncertain` from Rank tracking and Trends, retried with `retryUncertain`); or `wait` while Google retries by itself. Settings › Data sources › Data health runs Retry all on `retry` rows the person may retry and asks before a `verify` retry. A source that adds a failure kind records it where the error is caught; do not classify by message text. Competitor activity keeps each competitor's errors in its `track` and derives `lastRun` from the competitors still listed (`runOf` in `competitor-watch.ts`, also on read), so removing or correcting one clears its error at once; a website without a readable sitemap (422) is a `noSitemap` note on that competitor's card, never a failure.

### Database compatibility

SQLite remains the default. PostgreSQL and MySQL drivers are pinned in `devDependencies` for development and tests; promote the selected driver to `dependencies` before building a deployment. Keep SQLite installed and pass `config init --dialect postgres` or `mysql` explicitly. A development connection does not prove that the production archive contains its driver. Deployment steps: [Chinese](../../docs/DATABASE-DEPLOYMENT.zh-CN.md) or [English](../../docs/DATABASE-DEPLOYMENT.md).

Use the Repository for typed business reads and writes. The classic services use `server/nocoreach/legacy/database.ts`, which adapts their inputs to the same Repository and resolves Collection metadata through the caller's transaction. These are the query rules on all three engines:

| Concern       | Database difference                                                                                   | NocoReach convention                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| ------------- | ----------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| JSON          | PostgreSQL does not support `LIKE` on a JSON column. JSON text encodings also differ.                 | Store native JSON values, not `JSON.stringify` inside a JSON column. Use Repository `filter.json('payload').path(['tags']).has(value)` or other typed JSON operators; the driver compiles them for each engine. Existing snapshot searches read structured JSON after narrowing by project/key and search it in code. Never use raw `LIKE` or classic `$like` on JSON. There is no need for NocoCRM's helper for matching its double-encoded JSON text. |
| Search        | PostgreSQL's ordinary `LIKE` is case-sensitive; SQLite and MySQL depend on character range/collation. | User searches must explicitly use Repository `.includes(term, { mode: 'insensitive' })` (through `filter.string` or `filter.text`). The bridge preserves classic `$iLike` as `mode: 'insensitive'`, including exact, prefix and suffix patterns. Existing JavaScript searches normalize both sides with `toLowerCase()`. Ordinary `$like` is for structural string keys, not human search. Keep authorization/project filters in the same query.        |
| Boolean       | PostgreSQL uses native booleans; SQLite/MySQL may store them numerically.                             | Write `true`/`false`, never `0`/`1` or their strings. Let the Repository encode storage and reject numeric input. The bridge maps classic boolean conditions to `$isTruly`/`$isFalsy`; do not manually convert values before writes.                                                                                                                                                                                                                    |
| String length | SQLite does not enforce `VARCHAR(n)`; PostgreSQL and strict MySQL do.                                 | Validate or intentionally truncate at the business boundary. The bridge also validates `string`/`char` fields against resolved schema lengths on create/update, including transactional calls and hook-generated values. Count Unicode code points, leave TEXT/JSON intact, and never silently truncate IDs, keys or URLs. Direct Repository/query callers must enforce their own declared bounds.                                                      |
| Stable order  | Rows tied on a timestamp have no guaranteed order.                                                    | Append a unique ID to ordered lists and paginated reads. The bridge appends ascending `id` unless an explicit `id` order exists, and uses `id` when no sort is supplied. Direct queries must add their own tie-breaker. This gives deterministic ordering for unchanged data; it does not make offset pagination a snapshot under concurrent writes.                                                                                                    |

`tests/nocoreach/database-queries.test.ts` exercises case-insensitive scoped search, native JSON predicates and rejection of JSON text matching, boolean round trips/numeric rejection, Unicode length boundaries and tied pagination. `database-dialects.test.ts` installs the real business migration history and verifies JSON, booleans, large IDs, absolute timestamps, rollback, reconnection and repeat migration.

`NOCOBASE_TEST_DB_DIALECT=sqlite|postgres|mysql` selects the engine; unset means SQLite. PostgreSQL provisioning reads `PGHOST`, `PGPORT`, `PGUSER`, `PGPASSWORD`, `PGDATABASE` and creates isolated schemas. MySQL reads `MYSQL_HOST`, `MYSQL_PORT`, `MYSQL_ADMIN_USER`, `MYSQL_ADMIN_PASSWORD` and creates isolated databases. Use disposable database servers. Run the same checks on each engine, with its provisioning variables:

```sh

  tests/nocoreach/database-dialects.test.ts \
  tests/nocoreach/database-queries.test.ts \
  tests/nocoreach/legacy-date-filters.test.ts \
  tests/nocoreach/schedule-timezone-app.test.ts \
  tests/nocoreach/manual-tasks-app.test.ts \
  tests/nocoreach/project-access-app.test.ts \
  --maxWorkers=1 --testTimeout=120000 --hookTimeout=120000
pnpm exec vitest run tests/nocoreach/demo-data-app.test.ts \
  -t 'imports the demo through the API' --maxWorkers=1
```

`.github/workflows/database-compatibility.yml` runs these on SQLite, PostgreSQL 16 and MySQL 8.4, including installation, authentication, task/media authorization, project isolation, demo import through HTTP and cleanup. This is all of `tests/logic` plus the named business suites, not every historical SQLite-specific test under `tests/nocoreach`.

After building with the selected production driver, run `NOCOREACH_TEST_DIST=1 pnpm exec vitest run tests/nocoreach/deployment-artifact.test.ts --maxWorkers=1` with the same provisioning variables. It extracts the archive outside the checkout, runs compiled `config check` and `db apply`, starts `dist/server/standalone.js` at `/reach-test`, and checks built assets, authenticated API documentation, project/task writes, session persistence and reauthentication after restart. Its configuration, storage and database are isolated and removed afterwards.

Merged migrations are immutable unless the responsible maintainer explicitly approves a necessary compatibility correction, whose SQLite behavior must remain unchanged. The historical `202610140002_absolute_business_timestamps` needed a narrow MySQL extension because its unconditional dialect rejection prevented an empty installation from reaching any later migration. Its SQLite/PostgreSQL branches retain their behavior. MySQL projects raw DATETIME values as text and writes normalized UTC values before updating metadata, avoiding client timezone decoding. Preflight finishes before writes; MySQL DDL implicitly commits and is not transactionally reversible. Existing installations may review the documented checksum repair; never automatically repair history, suppress drift or rewrite unrelated migrations.

### Google report caches

- Default unfiltered web search totals read durable `nrSyncPartitions` overview rows, independently of report-cache expiry. Missing partitions, successful empty arrays (Google returned no record), and numeric zero rows are distinct. Never generate zero rows from omitted dates.
- `nrGoogle/syncNow` retains the existing administrator check. With `{scope:'gscOverview',startDate,endDate,mode:'missing'|'refresh'}` it queues only final, unfiltered web overview work, clamped to the last 16 calendar months and the Los Angeles final cutoff (today minus three days). Reject filters and non-web types. Without `scope`, the existing 7/28/56-day combined sync remains. The response contains `jobs`, `earliest`, and `cutoff`; `history-fill` and `history-refresh` are persisted trigger values in the existing job table. Missing mode subtracts stored days and active/paused/failed job intervals; explicit retry/resume uses `syncControl`. History jobs do not update the combined sync timestamps or schedule and never create query-page partitions.
- `nrDataViews/search` returns summary/coverage by default; `details:true` queries separate query/page aggregates. `coverage.current` and `coverage.previous` expose requested bounds, recorded/no-record/missing days and intervals, plus last-save time; `coverage.earliest` describes the default overview backfill boundary. Both periods need daily records for comparisons. `history.jobs` and `history.scheduleEnabled` are read outside the six-hour report cache. Active pages poll this read endpoint every five seconds; only the initial administrator view or an explicit action submits writes. Detail/breakdown/row comparisons use the summary's `compare` qualification, and live date queries are not clipped to locally stored days.
- Each active poll repeats the report request: authorization and connection checks, snapshot-version reads, preliminary-cache reads where applicable, and the current-resource job read. A cache miss may also read partitions or stored report caches. This is more than one database query; polling itself does not enqueue work or refresh Google. Connection changes invalidate both versioned summary keys and JSON-scoped detail keys only for the affected project.
- `GoogleReportCache` retains GA4's existing `ga4-reports:<project>` snapshots and uses separate GSC/local namespaces. It shares pending reads only within the service instance, clones responses, and bypasses shared reads/writes inside a transaction. Keep authorization and `sync.link()` checks before cache access. Include project, resource, captured authorization identity, actual dates/filters, and `network.mockCacheKey()` in applicable identities; concurrent token refreshes use the same captured scope.
- Upstream historical reports expire after six hours; partial dimensions/sitemap children retry after five minutes. Successful empty reports are cacheable. Reused reports preserve their original `cacheExpiresAt`; synced aggregate versions invalidate when partitions change. Cache aggregated live search tables rather than raw query-page matrices. Limits are 2 MiB per entry, 8 MiB per project/namespace snapshot (32 entries), and 16 MiB per cache instance in memory (128 entries). These are serialized-byte budgets, not process heap limits; oversized results are returned without retention.
- Frontend reports use the authenticated `WorkspaceCache` and its session storage. Search performance, overview, content and sitemap views have a one-minute freshness window; index progress/details use thirty seconds and retain running-job polling. Historical breakdowns/details honor server expiry. Include the selected properties in report keys and invalidate Google reports after resource/authorization changes, and affected local views after website-content mutations. Do not cache mutation responses or use long report TTLs for job state.

### Demo data

- `demo-data/samples.ts` exports `generateNocoReachSamples`, the shared business generator. The demo dataset calls it through `generate(context)`; weighted stages remain internal to the generator. A future ordinary sample registration may call the same function with an application-owned context, but must not call demo reset/import. This application does not automatically populate ordinary installations. Demo resets never modify sample seed history, ordinary initialization seeds or migrations.

- `demoConfigurationToken` owns the persisted revisioned collection exceptions and mock switches. Daily reset is always enabled after generation and comes from deployment configuration, not persisted policy: `NOCOBASE_DEMO_RESET_HOUR`, `NOCOBASE_DEMO_RESET_MINUTE`, `NOCOBASE_DEMO_RESET_TIMEZONE` and `NOCOBASE_DEMO_RESET_LANGUAGE` default to `3`, `0`, `UTC` and `en-US`. Restart after changes; old saved schedules are ignored, and the configuration API/service accepts no schedule writes. Register mocks and the Demo Agent in `demo-data/adapters.ts`. A demo deployment (`NOCOBASE_DEMO_MODE=true`) refuses request writes except the collections an administrator opens through the configuration API or deployment configuration (logical names such as `nrOnlineAgentRecords`, `nrSnapshots`, `nrTasks`); the plugin has no per-operation or per-record write capabilities, so normal business authorization decides who may write what. Never trust a client demo flag. Request policy is snapshotted before business transactions to avoid nested SQLite connection deadlocks; updates apply to subsequent requests.
- Skills list/detail and Agent material reads overlay missing built-ins in memory, including an older library's pending additions. Persist those additions only during mutation or the existing startup upgrade; browsing Playbooks or project knowledge must not write snapshots or require a demo write exception. Preserve user edits and deletions when merging built-ins.
- Keyword detail market/SERP reads persist provider results in `nrKeywordRuns`. Demo deployments must allow this collection through the configuration API or deployment configuration before exercising those pages; mocked outbound responses alone do not bypass the database guard. Preserve the other selections when updating the revisioned configuration, and verify response-level `ready` statuses, not just HTTP 200.
- Configuration read/configure and data read/manage are independent settings grants. The route checks the `page:demo-data` grant like every other page, which roles get with `app.settings` together with both settings grants; inside the page, the plugin's read-permission checks decide which sections show, and every server action checks its own grant and enabled environment. Keep demo checks out of the shared navigation. Custom policy editors must handle revision conflicts, stale identity responses and unsaved navigation through the public navigation guard; the built-in reset schedule is read-only.
- Daily freshness uses `context.clock.seed/sample(key)` and relative dates; the plugin resets daily at 03:00 UTC in English by default, independently of manual generation language and the dataset time zone. Mock adapters fail closed when disabled, and proxied demo runs never create official Agent executions. Interrupted running simulations settle as failed after five minutes; queued simulations replay through the same authorized adapter.

- Settings › Demo management (`/demo-data`, `client/pages/demo-management/index.tsx`) mounts the plugin's `DemoModeSettings` page with NocoReach's dataset count names (`label`); do not rebuild the page here. Wrap its route declaration with the plugin's `demoModeRoutes` helper so both the route and menu are absent outside Demo Mode, including for root; `defineDemoModeConfig()` publishes `demoMode.enabled` without application configuration patches. Direct URLs outside Demo Mode use the existing landing-page redirect. Anonymous home-page visitors automatically enter an existing Super Admin before dataset generation; existing sessions are retained. Quick sign-in lists all enabled person accounts, including accounts outside the dataset, and preserves passwords and permissions. The plugin preloads the account list for its standalone header menu. `demoMode.quickSignIn: false` disables both quick sign-in and automatic entry. Demo visitors switch accounts from the standalone `DemoModeMenu` (`client/layouts/app-layout.tsx`, with `demoMode()` in `client/plugins.ts`); the avatar menu has no demo submenu. The dataset creates five business accounts; administration uses the existing Super Admin. Do not generate a separate `admin` account or `nr.demo-admin` Permission Set. Activity fixtures that refer to an administrator use `context.actorId`. Install the published plugin version declared in `package.json`; plugin implementation and build artifacts belong to its upstream repository. The route must bypass `ProjectGate` so a new installation can view its demo status before projects are imported through the CLI or API. Administrators hold `settings:demoMode.data` through `app.settings` (`server/access/roles.ts`); the plugin checks that grant before each action. Authorized import, clear and reset handlers run outside the request's async-local write guard; concurrent requests remain guarded. The dataset provides one full-business `clear`, so all lifecycle mutations require an enabled demo deployment in the lifecycle service, including CLI and Scheduler calls.
- The dataset lives in `server/nocoreach/demo-data/`: `steps.ts` writes through the business services (projects, roles and accounts, the real connection and collection flows, tasks, knowledge, opportunities); `content.ts` holds both languages (the Chinese one reuses `demo-content.ts` and `demo-opportunities.ts`); `answers.ts` is what the simulated model says. Demo projects carry `demo: { dataset: 'nocoreach' }` in their project record; `demoProjectsOf()` reads it before the services load, and each process checks the persisted marker before an unknown project can send a request. A lookup failure refuses the request; a cleared demo stays blocked in that process so queued work cannot fall through to live networking.
- The demo world (`demo-data/world/`) answers every upstream a demo project calls — Google (GA4, Search Console), DataForSEO, GitHub, Discourse, Slack, Discord, X, Hacker News, npm/PyPI/Docker, the sites and the browser collector — in the imported language (`demo.language` on the project, carried by `DemoProject`). `script/` holds what exists (pages, queries, sources, issues, topics, posts, media), each text as `t(zh, en)`; the responders turn it into the providers' response shapes. Keep the script consistent with the tasks and opportunities: their paths must be pages, and a scripted change (`Change`, `Query.rank`) is how a result or opportunity's movement shows in the data. Times are days or hours before now and daily variation comes from `Seeded`, so a day reads the same all day; changing the seed or its hash changes generated IDs such as the GA4 property, and an existing import then needs a reset. GA4 visits are allocated per day from source down to browser (`World.visitsOn`) so every report adds up; the world is cached per project and hour and memoizes per-day facts, because read-only demo mode refuses the report caches' snapshot writes and pages read GA4 live each time. Running totals (stars, Docker pulls) grow with the calendar so daily samples move. `tests/nocoreach/demo-world.test.ts` checks report consistency, language and scripted moves.
- A demo project never reaches the network. `OutboundNetwork.useDemoUpstream()` answers its `fetch`, `send` and `fetchCollector` calls in process from the demo world (`demo-data/world/`), and `download()` in `public-sources.ts` takes the same path instead of resolving DNS. Unmatched requests fail with `NR_DEMO_OFFLINE`. A new outbound path must go through these entry points or await `network.inDemoProject()`. Runner dispatch uses the typed application-owned `demoAgent` proxy in `agents-runtime.ts` for analysis, build drafts and article drafts. The demo Agent (`demo-data/demo-agent.ts`) scripts a Runner-like transcript from the run's own materials — thinking, `Bash`/`WebFetch`/`Read`/`Write` tool calls whose results come from the task input, the demo site fixtures and the project knowledge, the summary and usage — and the runtime plays it back over about half a minute, appending each event to the business run's `transcript` and stopping between events once the run is asked to stop. `nrTaskWork.get` returns that transcript in the official progress shape, so Technical details renders it with `RunTranscript`; the task view leaves transcripts out. `NOCOREACH_DEMO_AGENT_PACE` scales the pauses (tests use `0`). Persist the proxy ID with queued runs and reload policy on recovery; disabled proxies never fall back to real runners. Demo task status exposes a virtual demo choice without modifying official agents or project defaults. Reviewed demo changes end with `release.state=simulated`, never a merge or live receipt. Business AI in demo scope always answers in process through `demoModels.complete()`, regardless of the selected default model. Reload the demo model binding before in-process generation; the HTTP model route reloads it before authenticating each call.
- `demo-data/activity.ts` writes the records a working team leaves besides its stories: page-change tasks in every release state (failed Agent run, review, `merge_failed`, `verifying`, `not_seen`, `simulated`, `live` — live and simulated tasks are `stage: 'done'`, as the service leaves them) with their run records, online conversations in `nrOnlineAgentRecords` (ids shaped `online-chat-…`/`online-run-…`, as the routes validate), in-app inbox items with past times and read states, and the business AI's `agModelUsage` rows. Inbox and usage rows are tracked for rollback; inbox items carry the `nocoreach-demo-` notification id prefix.
- All clear/reset and failed/interrupted-import recovery use `demo-data/clear-all.ts`. Remove project business rows, visitor additions, orphan rows, snapshots, inbox items that link to a task or carry the demo prefix, owned blobs, credentials and execution history; preserve system identities, global configuration and the persistent environment model. Cleanup must tolerate partial imports and refuse while work is active. `clear.ts` retains the collection/namespace catalog and scoped cleanup helpers; it is no longer the lifecycle rollback contract.
- Demo models are provisioned at environment startup and survive data operations. Demo Agents use environment mode (`demoConfiguration.enabled`, then `proxy.prepare()`); record markers choose fixture content, not whether real execution is permitted. Unknown projects in a demo deployment remain offline. Daily reset timing and language come from deployment configuration; the management UI displays them read-only.
- Automatic daily analysis (the minute tick and the Scheduler run in `daily-analysis.ts`) skips demo projects, so their hand-written insights and opportunities stay until someone runs an analysis by hand; the daily demo reset refreshes them.
- The public demo is embedded in the website's NocoReach page, a cross-site iframe. A demo deployment therefore sets its sign-in cookies with `SameSite=None; Secure; Partitioned` (`server/config/auth.ts`, from `NOCOBASE_DEMO_MODE`); the plugin's quick sign-in expires the unpartitioned cookies they replace. Keep other deployments on the default `SameSite=Lax`, and test a change to the demo's sign-in inside an iframe on another site.
- Demo roles use member scope and join only the two demo projects. Never grant a published demo account access to all projects. The plugin records account ownership separately from import tracking: only owned accounts may be re-enabled; a pre-existing username aborts the import.
- Register the plugin CLI in `cli/plugins.ts`; `demo-mode data` uses the same lifecycle service as HTTP and Scheduler. Standalone builds install it as a regular production dependency. Do not copy plugin builds into the application or edit generated Skills.

The Agent proxy is registered through `demoConfiguration.registerAgent({ id, title, execute })`; the application owns its input/output schema. Opportunity handoff and task mutations keep their project/task ownership checks; in a demo they write only when `nrTasks` and `nrSnapshots` are opened.

- Allow authenticated Agent configuration, model checks, conversations, and task execution through the official plugin. Simulate the final NocoReach release after review, record `release.state=simulated`, and never enqueue or assemble merge/revert work in a simulated deployment.
